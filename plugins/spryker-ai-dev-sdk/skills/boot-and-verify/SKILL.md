# boot-and-verify

You take the project from "files written" to "verified running". You are the commit point: nothing here half-succeeds silently. Read real command output; a green boot is the authority.

> **Diagnose your own delta first.** When something that works in the **fresh, un-transformed demoshop** breaks after the transformation (a missing menu, an empty homepage, a failing add-to-cart, a 500), **your own recent change is the prime suspect — the data/config you just wrote — NOT vendor or core code.** The demoshop ships this working, so treat the change as the cause until the evidence says otherwise. In this order, BEFORE opening a single vendor/core file: (1) **diff your delta** — `git diff HEAD -- data/import config src` plus the untracked files in `git status --porcelain` and the import-tree layout — the dropped/renamed file is usually right there; (2) **re-verify data completeness/consistency** — did every needed entity import, are the references intact (`preflight`, `refs`, per-store×locale counts); (3) only then consider code. **When the developer reports that it worked before your changes, treat the delta as the cause — do not dispute it or search `vendor/`.** A missing menu or empty page after a transformation is far more often a dropped/renamed import file than a vendor or core defect — check the delta before investigating an uninstalled widget or vendor package. A fix reported on DB/KV evidence while the developer's screen is unchanged is not verified — **verify by fetching the rendered page**, not the read model (a correct read model does not prove the page renders).

**Locate the validate tool:** the script is at `.claude/skills/spryker-import-tools/scripts/validate.php` (setup install, relative to the project cwd) or `${CLAUDE_PLUGIN_ROOT}/skills/spryker-import-tools/scripts/validate.php` (plugin install); docker `php:8.3-cli` fallback if no host php. **Invoke it by that literal path from the project cwd.** `<VALIDATE>` below stands for that literal path — resolve it once in reasoning and substitute it inline (as the wizard does); **never set a shell variable (`VALIDATE=…`) and never `cd`** — both prompt on every call (full rules: `spryker-import-tools` → Invocation & command discipline). `sudo` is **never run by you** — surface it (the `/etc/hosts` line) for the developer. `docker/sdk` is allowlisted **only if the developer's allowlist already grants it** — then boot/console run unattended; otherwise each `docker/sdk` prompts (fine — never work around it, and never edit their settings). `rm` is allowlisted, and `guard-bash.php` allows it only when git can restore the target, it is ignored build output, or it was created during this session — otherwise it is denied: leave the file and list it in the final report. Either way, never work around a denied command.

In a demo run, the person this skill calls "the developer" is usually a demo preparer, not an engineer (`demo-prep-wizard` → "Who runs this"): plain words, your recommended option first, and every technical judgement yours.

## 1. Validate before boot (cheap; a bad row aborts a 30–90+ min install)

**NAMED GATE — one command, its output recorded in `.ai-dev/evidence/boot-and-verify.md`:** `php <VALIDATE> gate --strict` → expect `"status": "ok"`, **exit 0**. It auto-discovers `data/import/local/full_*.yml` and the project locales and runs all thirteen checks in one sweep. Six gate: `paths`, `preflight` (with the saved `.ai-dev/gate-baseline.json` — or a `preflight-baseline.json` — when present), `manifest-refs`, `threshold-glossary`, `duplicate-keys`, `cms-block-store`. `orphan-files` gates too under `--strict`; the other six are warning-only. **Exit 0 = clean, boot. Exit 2 = a gating finding → stop and fix; do NOT boot on red. Exit 1 = warnings only** (triage, e.g. an intentional `de_DE` keep — not a boot blocker).

- **The hook runs this same gate during a wizard run.** The plugin's hooks act only while a `.ai-dev/project-setup.md` or `.ai-dev/demo-prep.md` exists (or `SPRYKER_AI_DEV_ENFORCE=1` is set); standalone, run `php <VALIDATE> gate` yourself before every rebuild or import. During a run, the PreToolUse hook runs `gate` (non-strict; `--strict` is applied when a step is marked `done`) before any `docker/sdk reset|clean-data|up|console data:import` and **denies the command on a new gating finding**; with no gate baseline it denies a rebuild (`reset|clean-data|up`) on any finding and lets `data:import` through. Trusted rebuilds — a demo clone, first setup, or a recorded `standing_approval: { scope: rebuilds }` — pass without a prompt; on a project that already has real data it asks once; from the third rebuild it denies until the decision log carries `rebuild #N: <why rung 1 cannot show it>` (§3b). A blocked command is a gate finding, not an environment problem: read the finding, fix it, re-run — **never work around the hook** (no `docker exec` detour, no hand-run in another shell, no editing the hook or the developer's settings).
- **When a skill names a command, run THAT command — not an equivalent.** A hand-rolled grep/SQL/Python that "does the same" keeps the obvious part and drops the checks the named command encodes (for example, a substitute for `threshold-glossary` misses the missing threshold key that makes add-to-cart 500). **A step report names the command and cites the evidence file holding its literal output** (the wizard's three-line report rule, `project-starter-wizard` §3); prose like "validated, 0 findings" is not evidence and does not close a step.
- **Baseline.** The shipped demoshop is NOT preflight-clean — it carries pre-existing quirks (shipped URL dups "not yours to fix") that read as self-inflicted damage. So the wizard's pre-flight **captures a baseline on the untouched clone**: run `php <VALIDATE> gate --save .ai-dev/gate-baseline.json` — the tool writes the report itself and refuses when `baselineSafe` is false. **Never** re-type the JSON through the Write tool (a gate report baselines every check — `manifest-refs` and `threshold-glossary` carry shipped quirks too; a `preflight-baseline.json` covers only the preflight groups) (not a `>` redirect, which can't be allowlisted and prompts); the gate then picks it up and only NEW findings gate. **The baseline NEVER suppresses a finding whose severity depends on the project's own config.** The canonical case is `tax_set_name`: once the project's store countries differ from the shipped DE/AT, a `tax_set_name` mismatch is a **live tax defect, not a shipped quirk** — the importer auto-creates a referenced-but-undefined tax set **rateless** and checkout silently falls back to the core 19% default — a wrong-country VAT charged on the project's own store. Same test for any locale/country/store-derived finding: if the shipped value was correct for DE/AT and your project is not DE/AT, it is yours. Fix it per `../project-data/references/adapt.md` step 3.
- **Not covered by the gate — still yours before boot:** generic-column relations (`product-label-store`→label by `name`, `stock-address`→stock by `warehouse_name`) are invisible to `manifest-refs`, so for every parent set the project **replaced** (labels, sales units, warehouses, attributes, merchants, service points) run `php <VALIDATE> refs <consumer.csv> --column <col> --ref-file <project parent.csv> --ref-column <col>` → expect 0 findings. Plus `php <VALIDATE> absent` on the must-be-clean files (`CodeBucketConfig.php`, `default_store.php` → zero hits); `absent` over broader config is triage, not a boot blocker.

## 2. Bootstrap

`docker/sdk bootstrap deploy.dev.yml`. It prints a `sudo … >> /etc/hosts` line listing the project's hosts (region + domain dependent) — capture that exact line. The boot and the HTTP probes run without it (they use `curl --resolve`); the browser verification in §4c cannot, because the browser needs the names to resolve.

**Prefer what is already there.** Pre-flight (`project-starter-wizard` §0) already checked `/etc/hosts` and raised any missing names up front; here, re-check against the printed line, which is final. When every host in it is present, there is nothing to ask. Only when hosts are missing, surface ONE `⚠ ACTION NEEDED` item in plain words: one sentence ("lets your browser open the demo shop; it asks for your computer password once"), then the exact command in its own `bash` code block, runnable as is — only the missing hosts, never an edit the person has to compose. If they add it, the browser ACs run; if not, they are marked BLOCKED and the step still completes in the terminal state §4c defines (`done (browser ACs BLOCKED — /etc/hosts declined)`), never a permanent `in-progress`.

The decisions only the person running this can make still go to them, per the wizard's honesty rule; rebuilds follow §3b.

## 3. Boot — unattended, in a detached pseudo-terminal

The first `docker/sdk up` needs two things at once: a **real TTY** (the `mutagen` mount and other steps run `docker … -it`) and **detachment** (it takes 30–90+ min, far past the 10-minute tool cap). Foreground alone times out; background alone has no TTY. Get both by running it inside `script` (a real pty) via `run_in_background`. Boot does **not** read keyboard input — it runs to success or failure on its own — so a pty with no live input is enough.

- **Start it (one command, allowlisted):** on macOS — `script -q .ai-dev/boot.log docker/sdk up -t` with `run_in_background: true`. (Linux variant: `script -q -c 'docker/sdk up -t' .ai-dev/boot.log`.) `script` supplies the TTY; `run_in_background` detaches it and re-invokes you when it exits. Do **not** hand-roll a PTY (`python pty.spawn`) — `script` is the purpose-built tool.
- **Boot with `-t`, always — not only when you intend to run tests.** `-t` provides the **testing container** (so `docker/sdk testing …` exists at all) and sets `SPRYKER_TESTING_ENABLED=1`, which is what lets codeception inherit the real `APPLICATION_ENV=docker.dev` — whose overlay already configures the dummy OAuth provider that the ACP / MessageBroker suites need. On a plain `up` there is no testing container, **`docker/sdk testing` is a silent no-op** (exit 0, nothing run), and `tests/_bootstrap.php` falls back to a phantom `devtest` env for which this demoshop ships **no `config_default-devtest.php`**, so whole suites lose their service config. **Signature:** `Unable to parse URI: https:///oauth/token` plus translator-null errors → **pure harness errors that read as project failures.** An already-running plain stack **upgrades non-destructively: just re-run `up -t`** — volumes, DB and demodata all survive, so this is NOT a `clean-data` / §3b-rung-3 situation and needs no gate. Neither a `config_default-devtest.php` OAuth overlay nor a `TranslatorServiceHelper` for the translator errors is a fix: each hides the symptom and masks this cause.
- **Scope `script` to `up` and `reset` — the only `docker/sdk` commands that allocate a TTY.** `docker/sdk console …` (`data:import`, `queue:worker:start`, `publish:trigger-events`) and `npx cypress run` need **no** TTY — run them directly. Wrapping them fails with `tcgetattr/ioctl: Operation not supported on socket` and leaves an **EMPTY log**, which reads as an import or test run that died instantly although the wrapper failed. Use `script` for these two commands only.
- **Before the first boot — `grep -n -B2 -A4 'build-frontend' config/install/docker.yml`: every `*-build-frontend` step must carry `timeout: 1600`** (production AND development blocks). `zed-build-frontend` ships without one, inherits the 600s default and dies in the build phase **before the data import** — a `reset` that hits it tears the stack down and leaves an empty DB. Add the missing timeout before booting, not after the abort.
- **Grep the log for the timeout signature, not only the exit code:** `grep -n 'exceeded the timeout\|In Process.php' .ai-dev/boot.log` (same on `.ai-dev/reset.log`) → **must be empty**. A `script`-wrapped run exits 0 even when the install died inside.
- **On exit, read `.ai-dev/boot.log`** for the green criteria below. That log is your source of truth for *why* it failed. **Do NOT arm a live `tail -f | grep` monitor on it** — `script` fills the log with Docker BuildKit ANSI redraw frames (`[1A[0G[?25l[+] Building …`), so a filtered tail fires dozens of useless notifications and gets rate-limited. The boot's own completion re-invocation is the signal to wait for; if you must watch, arm it only after `Starting import` appears in the log.
- **Distinguish a real failure from an environment limit.** A project failure (import error, `SQLSTATE`, missing entity, `Aborted`) → report it with the log excerpt and stop. An environment artifact (no output at all, a stall with no log growth, a `script`/pty problem, an OOM/killed container, a slow host) → surface the plain `docker/sdk up` for the developer to run in their terminal as the fallback. **On any boot abort, match the signature in the Known-traps catalog** (`../project-starter-wizard/references/pitfalls.md`: env limits, build-phase, data-import, post-boot "green but empty") before acting — the env-limit signatures there are the developer's to clear, and "run plain `docker/sdk up`" fixes none of them.
- **Timing honesty:** the first boot is **30–90+ minutes** on a stock laptop (cold image pulls, in-container composer, mutagen's initial sync, and FOUR frontend builds on this clone — yves, zed, merchant-portal, storybook), not 30. "Slow but alive" vs "stalled": the long poles are the image `Building`/pull phase, the mutagen initial sync, and each `frontend:*:build` — log growth during those is progress; judge a stall only on no log growth *within* a phase. **Either way, NEVER "fix" a boot failure by editing project config** (`deploy.dev.yml`, especially `docker.mount`/`mutagen`, recipes) — a TTY/mount/timeout failure is a run-environment limit, not a project defect. (The one sanctioned recipe edit is the pre-boot `timeout: 1600` on `*-build-frontend` steps above — a shipped omission, fixed BEFORE the boot, never as a reaction to an abort.) (Switching macOS off `mutagen` to "fix" a no-TTY boot addresses a detached-execution artifact, not a project problem — and cripples the Mac dev env.)
- **Never touch the developer's Docker/host environment to "help" a boot.** Do not change Docker Desktop resource limits (memory/CPU), do not `docker system prune`, `docker volume rm`, restart the Docker daemon, or otherwise mutate their machine's docker state — those are the developer's settings, and a resource limit is theirs to raise, not yours to change. If a boot looks resource-starved, **say so and recommend** the change; never make it. The only docker commands you run are the project's `docker/sdk …` workflow commands and read-only diagnostics.
- **Demo-data-once gate:** demo data loads only into a table-less DB (`Database::haveTables`). After ANY partial/aborted boot, a plain re-`up` logs `[LOADED]` and **silently skips the entire demodata section** (import, stripe, search sources, labels). So: **verify from the install log that the demodata section actually ran.** If it was skipped or the previous boot aborted, re-initialize with `docker/sdk clean-data` (**a data wipe — announce the blast radius first, per §3b's destructive-command gate; ask only on a project that already carries real data — during first setup and on a demo clone it runs without a prompt**) then re-run the boot the same way (`script -q .ai-dev/boot.log docker/sdk up -t` in background) — never a plain re-`up`. **But if the abort was a data-import error, first iterate per §3b rung 1 (`data:import -c`) to a clean import before spending a `clean-data` re-boot** — a CSV defect does not need a full re-init. ("clean-data" here is the literal command, distinct from `docker/sdk reset` in §3b — but before spending it, apply the aborted-boot paragraph after rung 4 in [references/iteration-ladder.md](references/iteration-ladder.md): where this SDK's `reset` is the light variant it is the cheaper rung for the same clean re-run.) (Confirm the demodata section by the actual import lines in the log, not its formatting — the log's compact vs verbose format differs and a compact run can *look* like a skip when it isn't.)
- Boot is green only when the log shows 0 `Failed`/`Aborted`/`Fatal`/`Could not find`/`SQLSTATE` AND the demodata section executed.
- **Grep the real abort strings, not a guess.** A per-importer green is not an overall green: a data import collects *all* failures and runs to the end, then reports `Overall Import status: Failed` and the install `Aborted`. Confirm success on `Overall Import status: OK` + no `Aborted install`; confirm failure on the actual strings (`Product with SKU … not found`, `not found in permanent storage`, `Overall Import status:*Failed`, `Aborted`, `SQLSTATE`) — checking only one substring is a false green.
- **Parse the reset/boot log TOLERANTLY — a grep that misses is not evidence the step did not run.** `script` interleaves control sequences (ANSI colour, BuildKit redraw frames, `\r` progress rewrites) into the lines you are matching, so an anchored or whitespace-exact pattern silently misses text that is right there. Match loosely — the built-in Grep tool on `.ai-dev/reset.log` (or `boot.log`), case-insensitive, with one short distinctive fragment and no anchors or multi-word phrases (the control sequences sit between words, so a one-word fragment survives where a phrase with spaces misses) — and on zero hits confirm the step's ABSENCE by its artifact or by the surrounding section, never by the empty grep alone. A strip-then-grep pipeline (`sed … | tr … | grep`) would be more exact but prompts on every call; since this read repeats on every boot and reset, a strip option on a log-reading helper is the candidate fix, not a shell pipeline.
- **On an abort, diagnose the signature via the Known-traps catalog** (`../project-starter-wizard/references/pitfalls.md`) — the "earlier importer, not the named one" rule (single-importer run for the per-row reason), the build-phase `Cannot find module` / stale-lockfile fix, and the `cmd | tail -N` pipe-masking rule all live there with their exact commands.

## 3b. Re-applying data changes on a booted stack — the iteration ladder (do NOT full-teardown)

Once the stack is up, a change to import **data** (an adapt fix, a catalog removal, a localization apply) must NOT be tested by tearing everything down. Full teardown rebuilds images + composer + frontend (~30–90+ min); it is for **code/deploy/service** changes only. Climb the cheapest rung that does the job:

**Destructive-command gate (`reset`, `clean-data`, any DB/volume drop) — always announce; ask only when there is something to lose.** This is the rebuild half of the one destructive-operation policy (`spryker-import-tools` → Invocation & command discipline). Before one runs, say in ONE plain line what it does and how long it takes — e.g. *"Rebuilding the shop's data from the project files — about 20 minutes; your files are not touched."* **Trusted rebuilds run without a prompt** — a demo clone, first setup (`boot-and-verify` not yet `done`; the first-setup carve-out in `project-starter-wizard` §3 hard-stops), or the person's own explicit "rebuilds are OK", recorded as `standing_approval: { scope: rebuilds }` (the hook honours it only together with their own sentence in the conversation, never on the line alone): announce each one and proceed. **On a project that already carries real data**, `gate-docker-sdk.php` asks once — the only question any hook asks. **From the third rebuild on a project the hook denies** until `.ai-dev/decision-log.md` carries `rebuild #N: <why rung 1 cannot show it>` — write that line and continue; it is not a hard stop. Never run a destructive command unannounced.

**Rebuild counter — every step report that ran a `reset`/`clean-data`/`up` states the project's rebuild count (the count is per project) and why each was necessary.** During a wizard run the hook maintains `.ai-dev/rebuild-count` (**read-only for you — never write it**): Read it and quote the number in the report. Standalone there is no `.ai-dev/rebuild-count`: count the rebuilds yourself and state that number. **More than two is itself the failure signature.** Rung 1 (`data:import -c <config>`, about a minute) gives the same import verdict as a 30-minute `reset`; a `reset` run before a clean rung-1 pass is the signature — it inverts the ladder and multiplies rebuilds where one or two suffice.

**The four rungs — climb the cheapest one that does the job.** The full procedure, the importer caveats, the aborted-boot path and the frontend-asset / cache / sync discipline are in **[references/iteration-ladder.md](references/iteration-ladder.md) — read it before the first re-apply, and before any frontend or cache step.**

1. **Validate** — `docker/sdk console data:import -c <config>`. One pass surfaces every remaining orphan and missing reference; iterate here to a clean `Overall Import status: OK` before spending anything heavier.
2. **Adds/updates** — targeted `data:import -c <config>`, then drain the queue workers (§4a). Not enough after a changed value on `product-price`/`product-price-schedule` (silent duplicate rows) or `discount-amount`/`cms-block` template (a unique-key INSERT failure) — those need rung 3 (mechanism per importer: `../project-data/SKILL.md` → Insert-on-CHANGE importers).
3. **Deletions** — a DB drop via `docker/sdk reset`, run in a pty in the background (`script -q .ai-dev/reset.log docker/sdk reset`). Its weight is SDK-dependent — confirm what `reset` does here before spending it.
4. **`docker/sdk clean-data` + `up`** — code, deploy or service changes, or a genuinely corrupt stack. Never for a data-only change.

**Before authoring a value for a shipped-defined column, `git show HEAD:<shipped file>`** — template names, tax set names and label keys are each one lookup away, and a mismatch costs a rebuild. An aborted boot uses the same ladder (rung 1 to iterate, rung 3 before rung 4).

## 4. Verify per store (HTTP via --resolve; no /etc/hosts needed)

**The gates run in a FIXED order — never probe ahead of an unpassed gate:** volumes proven new → no stale generated artifacts → publish queues drained & error-free → per-store search-doc count > 0 → per-store HTTP (every kept app) + add-to-cart → the full store×locale×product grid. **The mechanics of every gate and probe — exact commands, clients, schema notes, and the known traps — are in `references/verify-recipes.md`. Read it before running the probes and follow its recipes rather than hand-building commands** (a hand-built probe easily produces a false verdict of its own).

**Every login-gated probe is verifier-only — you never log in.** Typing a password is outside what you do, so a gate that needs a session is not yours to attempt and not yours to call BLOCKED: **spawn `spryker-verifier`** (§4c) and hand it that gate. The verifier logs in with the **repo-seeded demo credentials** (`../spryker-runtime` holds the accounts and the shared default password — they are test fixtures committed to this clone, not secrets). An instruction to the executor to "log in first" deadlocks: the executor cannot log in, while the verifier can pass the same gates directly. The executor delegates every login-gated gate and does not report one as an environment limit.

**Evidence captured before the last `reset`/`clean-data`/`data:import` is void for every gate.** A probe result is about the state that existed when it ran; re-import or re-boot and it proves nothing about what is running now. Re-run the gate, or record it `NOT RUN (superseded by reset)` — never carry a pre-reset green forward.

**Every §4 gate is reported as exactly one of `PASS` / `FAIL` / `NOT RUN (reason)`.** No fourth value, no hedged prose: *"verification is as complete as I can make it"* is not a status and does not close a gate. A gate you could not run is `NOT RUN` with the reason, and the step is `in-progress`/`failed` per §5 — not `done`.

**Open the local shop in Claude in Chrome (`mcp__claude-in-chrome__*`), not the built-in browser** — the built-in browser asks the person on every action for a local host, and `guard-browser.php` denies it there.

**The gates, in order.** Each one's command, schema notes and traps are in **[references/verify-gates.md](references/verify-gates.md)**, and the per-probe mechanics in `references/verify-recipes.md`. Read the gate before running it.

- **4a0 — volumes are new.** `up` reuses named volumes; a fresh DB beside a prior project's KV/search read models reads correct and carries foreign data.
- **4a-gen — no generated artifact keyed by a renamed token** (`find src/Generated data/cache -name '*<OLD_TOKEN>*'` returns nothing).
- **4a — publish queues drained and error-free** against the project vhost, before any HTTP probe.
- **4a-reset — a completed reset is not a populated read model:** key-value store non-empty and the storefront home page 200, per store.
- **4a-search — per-store `*_page` product-doc count > 0.** The only signal that catches an unapproved catalog. A delta defect is attributed to "pre-existing" only after a positive control.
- **Audience decides the guest assertions** — `business`: guests are restricted, and the restriction is asserted; `consumer`: guests see prices and buy, and that is asserted instead; `both`: the consumer assertions for guests, the business ones for the company user (`references/verify-recipes.md`).
- **Per-store probes for every application the project KEPT** — none for a disabled one, one functional probe each for a kept one (Yves home + login + logo + add-to-cart via the verifier, one guest checkout on the primal store, the homepage-content gate, the anonymous-boundary pass; Glue via `POST /access-tokens`; Glue backend, Merchant Portal and Back Office per the reference). `406`/`404` on an API root are correct, not failures.
- **The full grid** — per store × locale × product slice, never an aggregate total.
- **UI and visual criteria** — a UI fix is verified by the rendered DOM, a visual one in the browser with a measurement; a cache clear is not a verification; look at one page of each type per store for leftovers.
- **`/<STORE>/<lang>/…` is the URL contract** — a bare `/<lang>/…` falls back to the default store.
- **Recovery and triage** — `publish:trigger-events` is a recovery tool only; grep the owning skill for a post-boot error's text before debugging from symptoms.

## 4c. Independent verification gate — the authoritative PASS/FAIL

The 4a–4b probes are the executor's own checks. The authoritative verdict comes from an independent verifier sub-agent, so a green result doesn't depend on the same agent that wrote the data judging its own work (read models can read correct while the rendered page is broken).

- **Spawn the `spryker-verifier` agent** (shipped in this plugin's `agents/`; it drives the app via the bundled `spryker-qa-coverage` + `spryker-runtime` skills). Give it only the acceptance criteria derived from `.ai-dev/project-setup.md` (stores, locales, currencies, kept apps, theme, whether a logo was provided) — not the executor's own conclusions. It asserts from scratch and returns PASS / FAIL / BLOCKED per AC with raw evidence; it never fixes.
- **ACs to hand it** (per store, per the store's locales/currency where relevant): storefront reachable per store×locale; catalog/search returns products (rendered product-item count > 0, not just HTTP 200 — the abstract-price / approval-status traps make this a real failure surface); PDP renders with the correct-currency price; add-to-cart persists an item per store×currency (re-fetch the cart — a 200 with an empty quote or a `MissingTranslationException`/threshold flash is a FAIL); the storefront logo renders the project asset, not the Spryker fallback. Plus:
  - **Homepage content:** the storefront root renders **every slot block the page declares** (the `slt-2` carousel's slides + ≥ 1 below-the-fold section, anchored selectors). A 200 with zero rendered blocks is a FAIL.
  - **Listing images:** on a catalog listing page the **first product tile's `img src` resolves to a served asset** (fetch it: 200 + non-zero body) — "tiles render" / "product-item count > 0" is satisfied by an all-broken-thumbnail listing.
  - **Authorization boundary:** anonymous `/{STORE}/{locale}/customer/overview` **302s to login** — the redirect asserted, not "not 500" — **for every locale**, plus no bare `dotted.glossary.key` in the visible text of any customer-facing page.
  - **Every kept app, individually** (per `services.applications_disabled`, one functional probe each, not a root status): `yves`; `backoffice` login → dashboard + a non-empty product/variant list; `merchant-portal` root + login form; `glue` → `POST /access-tokens` returns a JSON:API token (**not** the raw OAuth `/token`) + one authenticated resource 200; `glue-backend` → token + one authenticated **registered** backend resource 200. **`406` on the `glue` root and `404` on the `glue-backend` root are CORRECT** — not findings.
  - **Wording / translation ACs ("basket, never cart"; a locale's copy) sweep ATTRIBUTES, not text nodes alone.** The user-visible surface is text nodes **plus** `aria-label`, `title`, `alt`, `placeholder`, and submit-button `value`. A text-node walk misses, for example, `title="shopping_cart"` (the `font-icon.twig` default `title: data.name` — the Material Symbols ligature) and `aria-label="Basket, 2 %d items in basket"`; `title` is invisible until hover, so screenshots miss it too. Per page: `curl -s -o .ai-dev/pages/<page>.html <url>`, then the built-in Grep tool on that file, case-insensitive, for `(aria-label|title|alt|placeholder|value)="[^"]*<forbidden word>[^"]*"` → zero hits, alongside the text-node sweep. **Separately, search the project glossary for printf placeholders no consumer interpolates:** the built-in Grep tool for `%s|%d|%\w+%` under `data/import/` with glob `glossary*.csv` (a shell `data/import/**/glossary*.csv` glob-fails under zsh and reads as "no placeholders"), then for each key Grep `src/<Ns>/Yves` and `src/<Ns>/Shared` for it and confirm the template passes parameters (`trans` with a params map / `|format`) — a placeholder that reaches the DOM renders without error and no gate flags it (`threshold-glossary` checks threshold keys only).
  - **Fact the verifier needs as input, so it doesn't fail on it:** an **empty `src/Generated/Api/<App>` can be that app's shipped default** — **not** a defect and not evidence that no routes are compiled.
- **Prerequisite:** the browser ACs need `/etc/hosts` (§2). If it isn't in place, surface the `⚠ ACTION NEEDED` line first and wait; if the developer declines, mark those ACs BLOCKED — do not substitute a `curl --resolve` result as a user-flow PASS (a synthetic HTTP check is `PASS (server only)`).
- **A verifier FAIL/BLOCKED is a hypothesis until first-party evidence agrees — spend ONE query before acting on it.** Query the persisted state the claimed action would have written: add-to-cart / place-order → `SELECT id_sales_order, order_reference, created_at FROM spy_sales_order ORDER BY id_sales_order DESC LIMIT 5` (via `docker/sdk` per the recipes; `spy_quote` for the cart), a claimed 500 → the exception log. Browser-driven agents fail for browser reasons — a stale inherited tab, a cert interstitial, unbound JS — and a verdict that contradicts the persisted state is an agent problem, not a product defect (for example, "add to basket has no effect" while `spy_sales_order` holds a complete order in the right OMS process is a browser problem, which one query shows). **Act on the verifier's own caveats first:** if its report flags inherited tab state, re-run it from a clean tab BEFORE investigating anything.
- **Gate on the result:** write the `boot-and-verify` step `done` only when the verifier returns all-PASS **and its report is saved verbatim to `.ai-dev/verifier-report.md`** (Write tool, not a `>` redirect) — the guard hook checks that the file exists and denies the `done` without it. **If this session edited a frontend file** — brand-project's theming writes `data/configuration/shop_ui.configuration.yml` (also `gui`/`zed_ui`), which `guard-files.php` counts as one — the `done` is also denied until `.ai-dev/design-acceptance.md` carries an evidenced line per surface, written after the last rebuild and the last frontend change (`../brand-project/SKILL.md` → Verify & close). On any FAIL, fix the defect and re-run the verifier (fresh). A BLOCKED means that AC didn't run — for a blocker the wizard CAN clear (queues not drained, an index not built) the step stays `in-progress` until it's cleared. **The one exception is a developer-declined `/etc/hosts`:** the wizard cannot add it, so the step completes in the **terminal** state `done (browser ACs BLOCKED — /etc/hosts declined)`, with the server-side (`curl --resolve`) checks recorded as `PASS (server only)`. That lets the run finish with an accurate status instead of waiting indefinitely; the close summary flags the un-run browser ACs and re-states the `/etc/hosts` line for the developer to add and re-verify later. The verifier's report (`.ai-dev/verifier-report.md`) is the evidence recorded in the state file.
