# Verify gates — the §4 gates in full

Run in the order `SKILL.md` §4 lists them; never probe ahead of an unpassed gate. Per-probe commands are in `verify-recipes.md`.

**4a0 — volumes are NEW (before trusting ANY KV or search assertion).** `docker/sdk up` recreates the DATABASE but **reuses named volumes** — a namespace collision leaves a fresh DB beside an earlier project's KV/search/broker read models, and every signal reads *correct* while carrying foreign data. Check **age** (KV `_timestamp` / index `creation_date` vs boot start) and **identity** (`spy_store` ids vs ids embedded in KV payloads) per the recipes. On a hit, resolve it via the wizard's **ranked fix hierarchy** (developer removes their own stale volumes / override only the deploy `namespace:` / a different project name — never force a rename), all ranked above `clean-data`/`reset`. No KV/search verdict until this passes.

**4a-gen — NAMED GATE: no generated artifact keyed by a token the transformation RENAMED.** `docker/sdk cli "find src/Generated data/cache -name '*<OLD_TOKEN>*'"` **must return nothing** — run it once per renamed store / region / code-bucket / namespace token. It takes seconds and covers the whole class: `src/Generated/**` and `data/cache/**` are gitignored build output, so no literal sweep, no `git diff` and no preflight sees them. Signature: after a fully green boot every API Platform request 500s with `Validation cache is enabled, but cache file is not found` → a `validation<OLD_TOKEN>.cache` left behind by a renamed code bucket. On a hit, delete the stale artifact and re-run the generator that owns it, then re-probe; never patch the consumer to accept the old name.
- **Build-section-ordering trap — the pattern, with its three known instances.** A recipe step in the `build` section runs **before** the prerequisite it needs exists (an init'd DB, generated transfers, the resolved bucket), **exits 0, and produces nothing or a wrong-keyed artifact** — so the boot log is green and the artifact is absent. Named instances: **`rest-request-validation-cache-warmup`** (this gate), **`generate-transfer-databuilders`** (the DataBuilders check in `test-infrastructure.md`, `SKILL.md` §4c → Test-infrastructure checks), **`configuration-sync`** (`../../project-starter-wizard/references/pitfalls.md`). **Any `build`-section step whose output you depend on is verified by its ARTIFACT after boot — never by the boot log.**

**4a — publish queues drained and error-free (before ANY HTTP probe).** A green boot ≠ publish-and-sync finished; a storefront hit before the queues settle is a **false 500**, not a project defect. Check counts against the **project vhost, not `/`** (the default vhost lists nothing — a false "drained"); drain with `docker/sdk console queue:worker:start --stop-when-empty` and re-check to 0. **In DMS (dynamic multi-store), `queue:worker:start`, `queue:task:start` and `publish:trigger-events` resolve the store from `APPLICATION_STORE` — without it they print the env banner, exit 0 and process NOTHING.** Run the drain **once per store**: `docker/sdk cli "APPLICATION_STORE=<STORE> vendor/bin/console queue:worker:start --stop-when-empty"` (same prefix for `publish:trigger-events`). **Pair every drain with a broker depth assertion — a queue counts as drained only when its depth fell:** discover the broker container by running `docker ps --format '{{.Names}}'` and reading the `broker` entry from its output (it is `<namespace>_broker_1`; never hardcode `spryker_broker_1`), then `docker exec <broker> rabbitmqctl list_queues -p /<project vhost> name messages` before and after. **Signature: the worker exits immediately with only the env banner while the queues stay full → missing `APPLICATION_STORE`, not a broken publisher** — otherwise it reads as a stale read model. Inspect error queues (a small STABLE `publish.*.error` count can be a benign duplicate-key race — verify the underlying rows exist before treating it as a failure). Commands + traps: the recipes.

**4a-reset — a reset that COMPLETED is not a populated read model. Assert both, per store, before calling the boot good:** (1) the **key-value store is non-empty** — `docker exec <ns>_key_value_store_1 valkey-cli -n <N> dbsize` (the project's numbered DB per the recipes; `0` is the finding, not a timing quirk) — and (2) the **storefront home page returns a page**, `/<STORE>/<lang>` → 200 with the anchored `<html lang=`. Either one failing is a FAIL of the reset, reported as such and fixed before anything else is probed. An empty key-value store with 500s on the storefront is reported as a failed reset.

**4a-search — NAMED GATE: per-store `*_page` product-doc count > 0** (via `/<index>/_count`, never `_cat`). The **only** signal that catches an unapproved / 0-search-doc catalog (missing `product-approval-status` → the publisher writes NOTHING while import, queues, and DB all read correct). A 0 here with a green everything-else = an invisible unsellable catalog — fail the boot on it.

- **Attributing a failure to "pre-existing" requires proof.** On a generate-mode run, **"search dead + PDP dead while everything else is green" is the known signature of a DELTA defect**, not a platform one (`../../project-data/references/generate.md`: a missing `product-approval-status` passes every other signal). The delta-first rule in `SKILL.md` applies; **this is how to rule the delta out.** Rule out the delta **in this order**: (1) `product-approval-status` present and non-NULL for every abstract; (2) `category_store` rows for every category; (3) an **abstract-level** price row per store×currency (a concrete-only price filters the product out of catalog and search); (4) per-store `*_page` `/_count`. **Then produce a POSITIVE CONTROL** — reproduce the same failure on an **untransformed demoshop**, or on a **freshly rebuilt index**. **The words "pre-existing", "platform bug" and "unrelated to our data" may not appear in any report until that control exists** — without a control they are unsupported.

**Per-store probes — the list is driven by what the project KEPT, symmetrically.** Read `services.applications_disabled` from the state file and **run an own functional probe for EVERY application that is NOT in it** (probing a disabled app is a false failure; *not* probing a kept one is a false green). **Glue is not the fallback for a disabled Yves** — a kept `glue` is probed even when `yves` is kept, and `glue-backend` is on the list in its own right: modelling Glue as the headless alternative lets total Storefront-API breakage (500 on every API Platform endpoint) pass every other gate in this skill. Per the recipes:
- **if `yves` kept:** `/<STORE>/<lang>` → 200 with the anchored `<html lang=`; login/register → 200; the storefront logo renders (see the logo gate below); and a real add-to-cart per store×currency — **login-gated, therefore VERIFIER-ONLY: hand it to `spryker-verifier`, never attempt it yourself** (the recipe below is what the verifier follows; the action is guest-restricted, so it needs a session and you do not open one) — follow the recipe exactly (pick a company user that holds a role; take the POST URL + field names from the rendered form; POST with `-L` on one cookie jar and read the flash). Add-to-cart is green only when the item is persisted: after the POST, re-fetch the cart (or the quote via authenticated call / SQL) and confirm the SKU is present and the quote is non-empty. A 200 is not success — a 200 with an error flash or an empty quote is a FAIL (a missing store×currency `sales-order-threshold.*` glossary key throws `MissingTranslationException`; a mis-valued threshold rejects the item silently, both while returning 200). Assert with anchored selectors (`data-qa=`, `itemprop="price"`), never bare substrings; verify prices via the KV key or an authenticated call, never guest HTML (B2B hides guest prices by design).
  - **Logo gate (`yves` kept).** brand-project sets `theme:logos:logos:yves_logo_url` to the project's served logo asset. Confirm the storefront header renders that asset, not Spryker's `build-with-logo` fallback icon — fetch the rendered header and check the logo `src` points at the project asset path. If it still shows the fallback, the config value didn't take (empty `:root { }` = `configuration:sync` ran before the DB existed — re-run it; a `type: file` setting may otherwise need the Back Office media upload); resolve it rather than noting "logo missing". **Then assert the logo's rendered box is non-zero** (`getBoundingClientRect()` width/height > 0 in the browser), not just that the asset returns 200: the theme's configured-logo branch renders a bare unsized `<img>` (only the SVG-icon fallback branch carries a size via `.icon--logo`), so a correctly-configured logo can still render at **0×0** with every server-side signal green and the page showing nothing. The fix — a `logo__image` class + explicit dimensions in `logo.scss` — is brand-project's; the gate is measuring the rendered box.
- **if `yves` kept, additionally — one GUEST CHECKOUT JOURNEY for the primal store** (cart → checkout → place order → `spy_sales_order` row + OMS initial state + one transactional mail rendered). The add-to-cart probe stops short of the three things this skill set curates but otherwise never exercises — checkout tax, the `cms-block-email--*` bodies, and the T&C page. Primal store only (cost-bounded); recipe + honesty rules in the recipes file.
- **HOMEPAGE-CONTENT GATE (`yves` kept) — a 200 alone does not prove a homepage.** The rule is in `../../project-data/references/generate.md` (repeated in `pitfalls.md`); this gate is its **assertion**, because a wholly block-less homepage passes the "200 with the anchored `<html lang=`" probe above. So on the storefront root **count the RENDERED slot blocks and require ≥ N** (N = the number of home slot→block wirings the project actually authored): anchored selectors for the **`slt-2` carousel** (its slide elements) **plus at least one below-the-fold section** (`slt-3`/`slt-4`/`slt-5`/`slt-home-bottom`). **A 200 with zero rendered blocks is a FAIL**, and a hero-only homepage with nothing below the fold is a partial-restore FAIL too.
- **ANONYMOUS AND BOUNDARIES pass (`yves` kept)** — a handful of **unauthenticated** requests, once per store×locale, no cookie jar. Every other probe here is authenticated and happy-path, so nothing else asserts that the authorization boundary is still enforced. Three assertions, each about **behaviour**, not reachability:
  - **(a) `/{STORE}/{locale}/customer/overview` must 302 TO LOGIN** — assert the redirect itself (302 + a `Location` pointing at the login route), explicitly **NOT** "it didn't 500". `CustomerConstants::CUSTOMER_SECURED_PATTERN` hardcodes the language segment to `(en|de)`, so on a project with any other locale `CustomerPageSecurityPlugin` **never engages** and `customer`, `wishlist`, `cart`, `checkout`, `company`, `multi-cart` are all unguarded — an unguarded `/multi-cart` returns **200 and renders** while broken, so a "not 500" assertion passes the defect outright. Because `en_US` is always kept the `en` path keeps working: **the break is visible only on the project's own locale — probe every locale, never just `en`.**
  - **(b) No customer-visible page renders a bare `dotted.glossary.key`.** Regex the **visible text** (not tags/attributes) of each fetched body for an unresolved key — `[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]+){2,}` — and require **zero hits** on the home, PLP, PDP and login pages. A raw key on the page is a FAIL (a missing per-locale glossary layer), not cosmetic.
  - **(c) At least one PDP renders a product image** — an `<img>` in the product-media block whose `src` is non-empty **and resolves to a served asset** (fetch it: 200 + non-zero body).
- **if `glue` kept (whether or not `yves` is):** `POST /access-tokens` must return a **JSON:API token document** (`data.attributes.accessToken`) — **not** the raw OAuth `POST /token`, which answers 200 even when API Platform is entirely broken — **then one authenticated resource fetch** (e.g. `/catalog-search`, `/abstract-products/<sku>`) → 200 with a JSON:API `data` payload. Glue selects the store per request from the **`Store`** header (or `?_store=<STORE>`), so probe each store with `-H 'Store: <STORE>'` on the single host (recipes). When `yves` is disabled (headless) this probe also carries the per-store storefront verification.
- **if `glue-backend` kept:** token, then **one authenticated backend resource** → 200 with a JSON:API payload. **Derive the resource from what the app REGISTERS** (command in the recipes) — a 404 on a resource the project never registers is not evidence of anything.
- **A bare-root status code is NOT a probe for either API — `406` and `404` are the CORRECT root responses for `glue` and `glue-backend`.** Never record either as a failure, and never record a root response as evidence the app works.
- **if `merchant-portal` kept:** MP root → 200 with its login form — its Angular frontend builds independently of Yves, so a green Yves proves nothing about MP (recipes).
- **if `backoffice` kept:** BO root reachable (yours) **+ — VERIFIER-ONLY, both login-gated — a BO login with the installer admin → dashboard 200** (a 200 on the nginx vhost is not evidence the app works) **and opening a product in the BO to assert the concrete/variant list is non-empty** (per admin locale) — "login → dashboard" is not a Back Office check. A project whose store locales exclude `en_US`/`de_DE` renders empty product lists: the admin can only pick `en_US`/`de_DE`, which have no localized-attribute rows, and `VariantTable` inner-joins on the admin locale (see define-stores → Back Office interface language; fix = the `getBackofficeUILocales()` override). + DMS store rows via read-only SQL (always — DB-direct, app-independent). Route SQL/console through `docker/sdk` (allowlisted), not bare `docker exec`; clients and schema traps (`mariadb` not `mysql`, `valkey-cli` in the KV container, `DESCRIBE` before guessing columns) are in the recipes.

**Verify at the granularity that can BREAK — never trust an aggregate total as "verified".** An "all verified ✅" on an aggregate total can hide a broken per-locale or per-product slice. Assert the full grid: per store **× each locale** (localized attributes + `*_page` search docs non-zero and roughly-equal per locale) and per store **× product** for prices (empty-or-`0` = missing). When you write "verified", name the grid you checked (`<stores> × <locales> × <products>`), not a total. A rendered widget does not prove its backing data imported — confirm by row count, never by the DOM.

**A UI fix is verified by the rendered DOM, never by a synthesised request.** Verified = the rendered page shows the control **NOT inside a hidden container** (`is-hidden`, `display:none`, a collapsed wrapper) and **NOT `disabled`**. A hand-built POST the server accepts tests the endpoint, never the fix — it supplies by hand exactly the value the UI could not produce (for example, a POST carrying `servicePoint[uuid]` returns `302 → /checkout/shipment` while every selector sits inside `is-hidden`). **The verification cart must be built the way the user builds it** — through the configurator/UI, not a hand POST: a cart assembled by POST passes the shipment step and fails at place-order (`Produktkonfiguration ist nicht abgeschlossen`).

**Clearing a cache is not a verification step.** A change is verified when a fetched page shows the intended result — the clear only makes that fetch meaningful (a template with a syntax error 500s every page, and only a fetch after the clear shows it). After any clear: fetch the page, assert the change, THEN report. **When two pages render the same component differently, the component is the least likely cause — diff the wrapper chain (slot → block → layout region) before concluding the markup is identical and blaming the viewer's cache.** For example, two byte-identical product tiles render differently when the PDP slot renders in `contentBottom`, outside the `.container` wrapper: the block goes full-bleed and clips the last carousel tile — the elements match, their parents do not, and a browser hard-refresh changes nothing. Compare the parents: in the browser `el.closest('.container')` / `el.parentElement` on both instances, or `grep -n "{% block\|slt-\|contentBottom" <layout twig>`.

**For any VISUAL acceptance criterion — layout, spacing, imagery, responsive behaviour — a fetched HTML body is not evidence.** Open the page in the browser (needs `/etc/hosts`, §2 — declined → the AC is BLOCKED, never PASS), screenshot it, and compare against the reference (design mock, the developer's screenshot, the un-transformed demoshop) before reporting; measure with `getBoundingClientRect()` / `getComputedStyle()` instead of estimating. `grep` on markup answers "is it present", never "is it right": a block can contain the right string and still be misaligned by tens of pixels, which a `getBoundingClientRect` call shows. **Failure signature: the developer sends a screenshot right after you reported a visual change complete — the visual verification was skipped.**

**Look at one instance of each page type per store — home, category, PDP, search — and hunt leftovers before `done`.** Visual defects coexist with HTTP 200 on every URL, clean imports and clean read models. Per store, check: **CMS block TITLES as well as content** (shipped headings survive a content swap), **slot→block mappings**, **footer glossary strings**, and **`configurable:false` on the footer logo include** (it makes the configured logo unreachable). A leftover found by the developer's screenshot is a FAIL of this gate, not cosmetic feedback.

**The URL contract is `/<STORE>/<lang>/…`** — on the one region host every store is browsable via its **path prefix**; a bare `/<lang>/…` silently falls back to the DEFAULT store+locale and produces convincing false negatives. Never conclude a store unreachable until you've probed it WITH its store prefix (mechanics + the Glue host-resolution contrast: the recipes).

**Recovery (only when a read model is genuinely out of sync):** `publish:trigger-events` is a recovery tool, never a routine post-import step — and it can NOT rebuild a storage whose events were never emitted — unless the entity's storage writer prunes orphans itself (the `pairRemaining…`/`deleteStorageEntity` check in [iteration-ladder.md](iteration-ladder.md) rung 1: a `*_store` relation-row delete + `-r <resource>` re-publish recovers; a deleted parent row does not, and only a DB drop + re-import restores coherence). Search-index rebuild steps and the resource-name trap (**`price_product_abstract`**, not `product_abstract`, for price KV) are in the recipes.

**Post-boot triage signatures — grep the owning SKILL.md / `pitfalls.md` for the error text BEFORE debugging from symptoms:**
- **Category pages 500 `failed to find nested object under path [integer-facet]`**, or `search:setup:sources` fails `analyzer [suggestion_analyzer] has not been configured in mappings` → the index was created **implicitly** (a sync ran before search setup, e.g. after an aborted first boot) WITHOUT the analyzer settings, and setup cannot add them to a live index. Fix (announce — it drops search data; the sync rebuilds it): delete the `<namespace>_*` indices → `docker/sdk console search:setup:sources` → `docker/sdk console search:setup:index-map` → sync (drain the queues / re-publish per the recipes). The 500 surfaces far from the cause.
- **`Class "…" not found` that greps clean in `src/`, `config/`, `vendor/`** → stale generated artifacts in TWO places: `src/Generated/**` leftovers (host side, incl. `OpenTelemetry/Hooks/*` + its classmap) AND the container-side compiled DI container `/data/data/cache/Zed` + `/data/data/cache/console/command-map.php`. **`cache:empty-all` does NOT remove them** — clear both (`docker/sdk cli "rm -rf /data/data/cache/Zed /data/data/cache/console/command-map.php"` + the `src/Generated` leftover), then re-run the owning generator and re-probe. This is the one sanctioned case for clearing the compiled container: a stale container after generated-code changes — never as a Twig cache clear, which goes through `src/Generated/Yves/Twig/codeBucket` ([iteration-ladder.md](iteration-ladder.md) → frontend-asset changes).
