# Iteration ladder — re-applying changes on a booted stack

The full procedure behind `SKILL.md` §3b. The destructive-command gate and the rebuild counter in §3b apply to every rung below.

**Before authoring a value for a shipped-defined column, read the shipped file: `git show HEAD:<shipped file>`** (template names → the category-template source, tax set names → the tax source, label keys → the product-label header). Typical mismatches, each of which costs a rebuild: `Default Category` vs `Catalog (default)`, `Standard Tax` vs `Standard Taxes`, `product_label_key` vs `name` — each one `git show` away. After the first such mismatch, diff the header of every authored file against its shipped counterpart (it takes seconds).

1. **Validate the edit first — cheap, no teardown:** `docker/sdk console data:import -c <config>`. It re-runs the import, collects every importer failure, and runs to the end — so **one pass surfaces every remaining orphan/missing-ref at once** (read the `Overall Import status` + the abort strings in `SKILL.md` §3). This is the fast feedback loop for "did my CSV edit leave a dangling reference?" — use it to iterate to a clean import **before** touching the DB — don't spend a `reset` until the import is clean.
2. **Adds/updates only, no deletions:** targeted `docker/sdk console data:import -c <config>` (it upserts, and the importers **emit publish events automatically** via event-behavior) → **drain the queue workers** (§4a) so the KV/search read models catch up → re-verify. Nothing dropped. **Do NOT routinely run `publish:trigger-events`** — the import already queued the events; a manual re-publish is a *recovery* tool (`verify-gates.md` → Recovery), not a normal step. **Two importer caveats (either one otherwise surfaces only after a reset):**
   - **Not every importer upserts — some are INSERT-only.** `discount-amount` is confirmed insert-only (`spy_discount_amount` keyed `(fk_discount, fk_currency)`, no store dim); re-importing existing rows fails with `Unable to execute INSERT`. **`cms-block` is insert-only too** — re-importing a block whose template changed fails with `Unable to execute INSERT … spy_cms_block_glossary_key_mapping`. If a re-import throws a unique-constraint INSERT error on an entity you did **not** add rows to, that entity is insert-only — it needs rung 3 (`reset`), not a data fix. Don't read the constraint failure as a CSV defect and start "fixing" correct data. **A targeted SQL `DELETE` bypasses the event behaviour that queues publish events — but whether the read model recovers depends on the PUBLISHER, so check the storage writer before assuming a reset.** `grep -rn 'pairRemaining\|deleteStorageEntity' vendor/spryker/<module>-storage/src/` → a writer that pairs orphaned storage rows with `null` and calls `deleteStorageEntity()` pushes the removed key to the sync queue, so delete + re-publish prunes KV correctly; a writer without that pattern leaves the read model stale and **`publish:trigger-events` does NOT rebuild it**. Two concrete cases on one entity: deleting a **`spy_cms_block_store` relation row** + `docker/sdk console publish:trigger-events -r cms_block` is **safe** (`CmsBlockStorageWriter::pairRemainingCmsBlockStorageEntities()` prunes `spy_cms_block_storage` and Redis); deleting a **`spy_cms_block` row** and re-importing is **not** (`kv:cms_block:…` keeps the pre-delete payload through a targeted re-publish, a full `publish:trigger-events`, and fully drained queues — only a DB drop + re-import restores coherence). **General rule for `*_store` relation tables (`CmsBlockStoreWriterStep` and its peers use `findOneOrCreate()`): the importer ADDS, only a reset or a manual delete REMOVES** — a per-store split of already-imported entities needs one of the two, and the CSV row is removed regardless so a later reset reproduces the state. Insert-only + a needed VALUE change → rung 3.
   - **Changing the VALUE of an already-imported row is NOT an update here — it duplicates.** `spy_price_product_store` has no unique key on (price_product, store, currency), so a re-import of a changed price *adds* a second row instead of updating (symptom: row counts grow after a re-import meant to update in place). **A value change to already-imported data requires rung 3 (`reset`)** — only genuinely new rows are safe via targeted import.
3. **Deletions must be reflected — `docker/sdk reset` gives the DB drop, but its weight is SDK-dependent and it needs a TTY.** A plain `data:import` only upserts and won't delete already-imported removed rows, so reflecting a removal needs a DB drop, which `reset` provides. But:
   - **Don't assume it's lightweight.** In some SDKs `reset` re-imports on the running stack (drop tables → migrate → import, no teardown); in others it is a full destructive teardown — removing containers, networks, and volumes (wiping DB + search data) then rebuilding images/deps/frontend, as heavy and destructive as `clean-data`+`up`. Check what `reset` does in this project's SDK (its help/output) before running it.
   - **During first setup or on a demo clone the variant does not change the decision** — there is nothing to lose: announce it with its expected duration and run it. **On a project that already carries real data**, if you cannot confirm it is the light variant, say so and ask before running it. Either way, apply the destructive-command gate in `SKILL.md` §3b.
   - **It needs a real TTY** — run it via the sanctioned pty + background, like the boot: `script -q .ai-dev/reset.log docker/sdk reset` with `run_in_background`. Never a plain background shell — that dies at the rebuild with `ERROR: failed to get console: provided file is not a console`, and a destructive `reset` will already have wiped the data before the rebuild fails.
   - **Then drain the queues + re-verify** — the reset re-runs the install, which re-emits the events (no manual `publish:trigger-events` needed).
   - Targeted deletes are impossible via `data:import` (upsert-only), so removing rows needs a `reset` (or a developer hand-run) — say so rather than looping.
4. **`docker/sdk clean-data` + full `up`** removes volumes/containers/networks and forces the long rebuild — reserve it for code/deploy/service changes or a genuinely corrupt stack, never for a data-only change — this ladder exists so that CSV edits are never tested with a full `clean-data` + `up` each time.

`demodata` is the last install section, so an abort there means every build/frontend/scheduler/storage section already completed — iterating the import is cheap (no rebuild). Use rung 1 (`data:import -c`) to iterate the CSVs to a clean `Overall Import status: OK`. **Once the import is clean under rung 1, re-run the whole recipe from a dropped database — §3b's ladder applies to an aborted boot too, so reach for rung 3 before rung 4:** `docker/sdk reset` (`script -q .ai-dev/reset.log docker/sdk reset`, background pty) where this SDK's `reset` is the **light drop-and-reimport** variant; `docker/sdk clean-data` then `script -q .ai-dev/boot.log docker/sdk up -t` (background pty) where it is the **full teardown**. **Determine which FIRST, never assume:** `docker/sdk help reset`, or read the `docker/sdk` script — a `reset` implemented as `Compose::down` + `Compose::cleanVolumes` + `Compose::up --build …` IS the full teardown (same blast radius and cost as `clean-data`+`up`; the current demoshop SDK ships this variant), and only a reset that drops tables → migrates → imports on the running stack is the light one. Either way it is destructive → §3b's gate (announce the blast radius and expected duration; a question only on a project that already carries real data) and it counts against the rebuild counter. **Why the tail cannot be hand-run, whichever option you pick:** the recipe runs the post-import steps in a defined order, and replaying a subset after an abort leaves an inconsistent stack (a later step whose earlier dependency never ran, or read-model state auto-created with the wrong shape) — a green run means the recipe ran to completion, not that the tail was hand-assembled. (Rung 1 iterates the fix; the clean re-run produces the final state. Prescribing `clean-data`+`up` here without first checking what `reset` does picks rung 4 for a rung-3 problem.)

Rule of thumb: **adds → targeted `data:import`+publish (no teardown, no TTY); deletions → a DB drop via `reset` (weight SDK-dependent — light re-import or full destructive teardown; always TTY-pty + background, never a plain background shell); code/deploy change → `clean-data`+`up`.** Always run the cheap `data:import -c` validation rung first, and confirm what `reset` does in this SDK before spending it.

**Frontend-asset changes and the sync/cache discipline (a separate axis from the data ladder above):**
- **Asset change (`.scss`/`.ts`) — the check decides the rung: `docker/sdk cli "ls -d /data/node_modules"`.** **Present** → `docker/sdk console frontend:yves:build` (seconds; expect `webpack compiled successfully`). **Absent** → `docker/sdk up --assets` (minutes; re-runs the whole `build-static*` section — non-destructive: no volumes, no DB, demodata stays `[LOADED]`). Reserve `up --assets` for Zed/MP/Storybook asset changes or a fresh container (no `node_modules` yet); never `clean-data`+`up` for an asset change. (Clones typically ship `/data/node_modules` in the running `cli` container — do not assume `frontend:*:build` dies `Cannot find module`; run the `ls` and read the answer.)
- **`.twig` changed and the page still shows the old markup → clear the compiled Twig cache inside the container: `docker/sdk cli "rm -rf src/Generated/Yves/Twig/codeBucket"`**, then `docker/sdk cli "ls -A src/Generated/Yves/Twig"` must no longer list `codeBucket`. That is where `Spryker\Shared\Twig\TwigConfig` puts the compiled templates and the `.pathCache` template map, unless the project config sets `YVES_TWIG_OPTIONS` / `YVES_PATH_CACHE_FILE` (grep `config/Shared/` and read what the running env loads). **Never `rm -rf data/cache/Yves/<env>` as a Twig clear** — that is the Symfony kernel cache (the compiled DI container, `Container<hash>/`), it holds no templates, and deleting it mid-sync produces a transient 500 `Failed opening required '…/Container<hash>/…Service.php'`. **A NEWLY CREATED override template** (not an edited one) stays invisible until the path map is rebuilt — `docker/sdk console twig:cache:warmer` rewrites `.pathCache` for Yves and Zed. `up --assets` clears neither; `console cache:empty-all` clears every `src/Generated/*/*/codeBucket`. Then **re-fetch the page** — the clear itself proves nothing (§4).
- **Do NOT `npm install` inside `cli`** — `/data` is mutagen-synced, so it would push a large `node_modules` onto the host sync.
- **After ANY command that restarts containers (`up`, `up --assets`, `up --build`, `restart`), confirm the mutagen sync is alive before trusting anything** — `mutagen sync list` → the project session must be `Connected: Yes` on **both** alpha and beta (not stuck `Connecting to beta`). A restart can leave the daemon down with no error, and then every host edit silently never reaches the container — invalidating every verification in that window (green console output run against code that isn't there). Running `mutagen sync list` itself restarts a dead daemon, so the first call is also the repair.
- **Verify a file's presence in the CONTAINER, not on the host, before acting on it** — `docker exec <namespace>_cli_1 ls /data/<path>`; a host-side `ls` proves nothing about what the application sees.
- **New project class override — strict order:** write the file → confirm it exists in the container → `docker/sdk console cache:class-resolver:build` → confirm the FQCN is in `src/Generated/Shared/Kernel/<Orgs>/resolvableClassCache*.php`. Rebuilding the resolver cache *before* the sync lands bakes a cache WITHOUT the class, which then keeps the override inactive even after the file finally syncs.
