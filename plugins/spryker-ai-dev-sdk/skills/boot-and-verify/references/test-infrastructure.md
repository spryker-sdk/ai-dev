# Test-infrastructure checks

The full procedure behind the test-infrastructure items in `SKILL.md` §4c.

**Test-infrastructure checks — mandatory checklist items, on par with the endpoint checks (both run post-boot, once the boot's `composer install`/`npm ci` have provided the tooling):**
- **PHP / codeception** (only if a custom namespace was set — skip for `keep-shipped`). `configure-codebase` created the runnable seed module `tests/<Ns>Test/Shared/Example/` pre-boot but could not execute it (no `composer install` yet). Close the loop in **two** steps — the seed run is a pre-check, the full suite is the gate:
  - **Fast pre-check (seed only):** `docker/sdk cli vendor/bin/codecept build`, then `docker/sdk cli "vendor/bin/codecept run -c tests/<Ns>Test/Shared/Example Example"` → expect `OK`. A green run means the namespace's suite is discovered, its actor/support autoloads (`test-autoload.php` branch), and `projectNamespaces: ['<Ns>','Pyz']` resolves `src/<Ns>` — **and nothing more. It proves only the seed suite:** codeception cannot reach `PyzTest` from here, because passing an explicit suite name suppresses `include:` traversal and `-c` re-roots onto the seed module's own config, which has no `include:` key. **A green pre-check is not a test verdict** — never report it as "tests pass".
  - **NAMED GATE — the full inherited functional suite:** `docker/sdk testing codecept run -c tests/codeception.ci.functional.yml`. **Assertion: 0 errors and 0 failures, with only upstream skips** — and **report the counts** (tests / assertions / errors / skips), never the word "green" alone. **This gate runs BOTH test trees — `PyzTest/*/*` AND `<Ns>Test/*/*` — and a run covering only one of them is a misconfiguration, not a pass.** Both are in scope only because `configure-codebase` **added** `<Ns>Test/*/*` to this config's `include` (and `src/<Ns>` to its whitelist) alongside the shipped `PyzTest/*/*`, and swept `projectNamespaces` — that skill owns the greps that prove it. An unpatched aggregate config runs the inherited suites against `src/Pyz` config while the app runs `src/<Ns>`, i.e. green on the wrong values.
  - **Two prerequisites — check BOTH before you interpret a red result:** (1) the **`-t` boot** (§3 — without it `docker/sdk testing` is a silent no-op and this gate reports a phantom pass); (2) the **`en_US` glossary layer kept** (`../../project-data/references/adapt.md` — it is kept because the tests need it). **A red result whose signature matches either prerequisite is a SETUP defect, not a project defect:** `Unable to parse URI: https:///oauth/token` / missing-service-config errors → the boot lacked `-t`; translator-null / `MissingTranslation` errors → the `en_US` glossary layer was removed. Fix the prerequisite and re-run; do not report it as a project failure and never "fix" the tests. A red run that matches neither, and a red/empty pre-check, are `configure-codebase` findings — report them, don't paper over them. (Needs `cache:class-resolver:build` at boot.)
- **E2E / Cypress smoke** (from `cypress-migration`). **Prerequisite — confirm the transfer DataBuilders exist BEFORE `cy:run`:** `docker/sdk cli "ls src/Generated/Shared/DataBuilder | wc -l"` must be non-zero. The vendored suite provisions its test data through the `testify-backend-api` `POST /dynamic-fixtures` endpoint, which executes codeception data helpers server-side, and those helpers need `Generated\Shared\DataBuilder\*`. The build recipe's `generate-transfer-databuilders` step can run and produce **nothing** (the build-section-ordering trap — §4a-gen states the pattern and its three instances), leaving the dir empty after a fully green boot. If it's 0, run `docker/sdk console transfer:databuilder:generate` (regenerates ~all builders). **Triage signature:** `POST /dynamic-fixtures` 500 + `ClassNotFoundError … Generated\Shared\DataBuilder\*` → DataBuilders missing — NOT a project-data defect and NOT a Cypress config problem. Then run its documented command in the vendored dir — `docker/sdk cli "cd tests/cypress-boilerplate && npm ci"` (install is fine in the container) — but **run `cy:run` itself on the host or a CI runner with a display, not via `docker/sdk cli`**: the Alpine/arm64 CLI container has no display and dies with `spawn Xvfb ENOENT`. Drain the publish queues first (per §4a — an un-synced search index makes storefront/PDP specs fail for reasons unrelated to the code). Expect the storefront + checkout smoke green. **Verify ONLY the apps the project kept** — cypress-migration should already have pruned the specs for any disabled app (no `merchant-portal` → no MP specs, no `glue` → no API specs); a spec hitting a removed endpoint is a `cypress-migration` pruning miss, not a project defect. A red smoke on a kept app is a real finding. (`cy:run` needs a booted instance; if the env can't run it, say so explicitly rather than claiming it passed.)
