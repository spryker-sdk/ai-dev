# Per-store verification recipes (boot-and-verify step 4 — the mechanics)

The exact commands, clients, schema notes, and known traps for every gate and probe in `../SKILL.md` §4. The SKILL.md owns the gate ORDER (volumes new → queues drained → search count → per-store HTTP + add-to-cart → the full grid); this file owns how each is actually run. Follow these recipes rather than hand-building commands — a hand-built probe easily produces a false verdict of its own.

## Gate 4a0 — prove the KV/search/broker volumes are NEW (before trusting ANY KV or search assertion)

`docker/sdk up` drops and recreates the DATABASE but **REUSES existing named volumes**, and the deploy `namespace:` is derived from the project name — so a prior project (or a prior run of this one) that claimed the same `<namespace>_*` volumes leaves you with a fresh DB beside **stale read models**, and every search-doc count / KV price payload / queue-health signal reads *correct* while carrying a foreign project's data. This is a severe false green: a "fresh" boot can serve KV payloads listing more stores than the DB holds, with reversed store IDs, sending an add-to-cart diagnosis down a long wrong path. Two mechanical checks catch it, both cheap:
- **Age:** compare a KV `_timestamp` and an OpenSearch index `creation_date` against the boot start time — an old timestamp = a reused volume, not this boot's data.
- **Identity:** compare `spy_store` ids against any store ids embedded in the KV payloads (`kv:*` documents carry store context) — a mismatch (ids reversed, or stores that don't exist in `spy_store`) = a namespace/volume collision → **false green**.

If either fails, resolve it via the wizard's **ranked fix hierarchy** (developer removes their own stale volumes / override only the deploy `namespace:` / a different project name — never force a rename), all strictly better than `clean-data`/`reset`. Do not report any KV/search verdict until this gate passes.

## Gate 4a — publish queues drained and error-free (before ANY HTTP probe)

A green boot means the data imported, not that publish-and-sync finished: events may still sit in RabbitMQ un-written to the Redis KV / OpenSearch that Yves reads, or a queue may have errored. A storefront hit before the queues settle is a **false 500**, not a project defect. So first assert the queues are empty and clean: check message counts (`docker exec <broker> rabbitmqctl list_queues name messages messages_ready`, and inspect any `*.error`/dead-letter queue). **Target the project vhost, not `/`** — `list_queues` against the default `/` vhost returns an EMPTY list, which reads as "queues drained": a dangerous false green. The queues live in the vhost named after the deploy `regions.<REGION>.services.broker.namespace` (e.g. `<region>-docker`), so the correct call is `docker exec <broker> rabbitmqctl list_queues -p <namespace> name messages messages_ready`. (Same class of trap as the "query the RIGHT Redis DB index, not `db 0`" note below — the read model lives in a namespaced location, and hitting the default namespace shows empty.) If non-empty, drain the workers — `docker/sdk console queue:worker:start --stop-when-empty` (or trigger via the scheduler) — and re-check until 0; inspect any failed/error queue. (`rabbitmqctl` flag support varies by version — `--no-table-headers` etc. may error `Invalid options`; just read the raw column output rather than relying on formatting flags.)

- **A small, STABLE count in `publish.*.error` can be a benign duplicate-key publish race, not a failure** (e.g. a `Duplicate entry … for key '…page_search-unique-key'` in `publish.page_product_abstract.error` after a clean boot — two listeners race to insert the same `spy_*_page_search` row, the loser fails, but the row IS written). **Verify the underlying rows exist** (the per-store×locale search-doc count) before treating it as a problem; only investigate if data is genuinely missing or the error count **grows** across reboots.

## Gate 4a-search — per-store `*_page` product-doc count > 0

Assert, per store, that `spy_product_abstract_page_search` (the catalog search docs) is **non-zero** — via `curl -s http://localhost:9200/<store>_..._page/_count` (see the `_count`-not-`_cat` rule below). This is a standalone pass/fail gate, not a line in general search prose, because it is the **only** signal that catches an unapproved / 0-search-doc catalog: with `product-approval-status` missing (`spy_product_abstract.approval_status` NULL), the `page_product_abstract` publisher writes NOTHING, so search is 0 documents while **every other signal reads green** — the import reports `Successful`, every queue drains to 0 with zero `.error` messages, and the DB grid is perfect (abstracts × locales × prices all present). A 0 here with a green everything-else = an invisible unsellable catalog. Fail the boot on it.

## Per-app probes

Verify only the apps the project kept (read `services.applications_disabled` from the state file — a disabled app has no endpoint, so probing it is a false failure). For each store + locale, assert compactly with **single commands, no pipes and no chaining**: `curl -s -o /dev/null -w '%{http_code}' …` for status; to check body content (`<html lang>` / currency), `curl -s -o <tmpfile> …` then the built-in **Grep tool** on that file — never `curl … | grep` and never `curl …; echo; curl …` (a pipe **or** a `;` both prompt, every time). **Same for Elasticsearch checks:** one `curl -s http://localhost:9200/<index>/_count` per command and read the small JSON directly — don't `| grep` it or chain several indices with `;`. One index, one command. **Assert search health with `/<index>/_count` or `/<index>/_search`, NEVER `_cat/indices` `docs.count`** — that column lags the segment merge and reads as near-empty (`_cat` showed `2` while `_count`/`_search` on the same index reported 19). `_cat` is a false "index nearly empty". Don't pull whole pages into reasoning.

- **if `yves` kept:** `/<STORE>/<lang>` → 200, correct `lang` (assert via the **anchored** `<html lang=` attribute), no "all shards failed" on search; login, register → 200. **Add a product to the cart** (the *action*, per store×currency): exercises the store/currency-templated threshold + glossary path that static loads miss (surfaced the add-to-cart `MissingTranslationException`). Assert 200, no error/exception page. **This is a specific recipe — follow it; a hand-built guest curl fails for reasons unrelated to the project and then masquerades as a diagnosis (a failing cart curl is easily misread as a missing-data defect).**
  - **Prefer the developer's real-browser result over a synthetic curl.** A browser exercises the true form contract and has none of the URL/field-construction traps below; if the developer can (or can't) add to cart in a real browser, that outcome outranks your curl. Use curl only when no browser result is available, and treat a curl failure as *possibly* your harness, not proof of a project defect.
  - **(a) Log in first — the action is guest-restricted.** `spy_unauthenticated_customer_access` has `is_restricted=1` for `add-to-cart`, `price`, `order-place-submit`, `wishlist`, `shopping-list` — a guest attempt is invalid by design (read that table first to confirm). Note: `POST /login_check` 500s with `ForbiddenExternalRedirectException: URL home is invalid` unless a `Referer` is sent — the login itself succeeds (audit log `Successful Login`), only the post-login redirect blows up; send a referer.
  - **(b) Pick a customer whose COMPANY USER actually holds a role — verify by SQL, don't assume.** No role → "This action is forbidden", not a project defect. The shipped `company_user_role.csv` assigns roles to company users **3–22 only**; users 1–2 get none (`spencor.hopkin@acme.com` = company user 1 → forbidden). Query `company_user_role` for a user with a role (`andrew@ottom.de` = Admin + Buyer works) before testing.
  - **(c) Take the POST URL and field names from the RENDERED form — never hand-build them.** `/cart/add/{sku}` needs the **CONCRETE** sku — the abstract 404s with `Product … not found`. Take the concrete from the rendered PDP form action, or derive one with `csv distinct product_concrete.csv --column concrete_sku --plain | head` (shipped example: abstract `C2235` → concrete `1001454`; see `../../spryker-import-tools/references/demo-facts.md#skus`). The form mixes conventions: the CSRF token is **namespaced** (`add_to_cart_form[_token]`) while the payload fields are **plain** (`sku`, `quantity`, `productOfferReference`) — guessing namespaced field names fails silently with a 302 back to the PDP and an empty cart.
  - **(d) POST with `-L` on the SAME cookie jar and READ THE FLASH.** A silent 302-back-to-form is never information-free — Spryker pushes the rejection reason into a flash message. `curl -L` on the POST (same session, follow the redirect in one hop) renders the flash so you can read the actual reason; **fetching the redirect target as a separate request consumes/destroys the flash** and leaves you reasoning blind (a separate fetch discards the explanation and sends you guessing at absent data). Read the flash FIRST; only if it's empty should you start diffing data. On success `spy_quote` holds the sku/quantity/price and the cart page renders the correct gross+currency+separator.
  - **Assert with ANCHORED selectors, never bare substrings** ("SE renders 5 prices" was `kr` inside "bac**kr**est"). Use `data-qa=`, `itemprop="price"`, `<html lang=` — a bare currency code/symbol (`kr`, `zł`, `PLN`, `SEK`) collides with ordinary page text and gives false signals both ways.
  - **Price visibility is NOT a valid guest-fetch assertion on a B2B shop** — this storefront shows "Please login to see the price" to anonymous users, so "no price on the guest page" is expected, not a defect. **Verify prices via the KV storage key** (`kv:price_product_abstract:<store>:<id>`) or an authenticated call — not the guest HTML. (The real net-only/`gross=0` price bug from a mis-seeded store is caught by the per-store price-completeness check in `project-data` (adapt)/SQL, not the storefront.)
    - **Query the RIGHT Redis DB index — not `db 0`.** The key-value store is namespaced per store/region into numbered Redis DBs (per the deploy `key_value_store` config), so `db 0` is often **empty** while the data lives in `db 1` (or another index). Read the project's namespace from the deploy config and pass it with the client. **`valkey-cli` is NOT in the CLI container** — `docker/sdk cli valkey-cli …` returns `valkey-cli: command not found`. It lives in the **KV container**: `docker exec <ns>_key_value_store_1 valkey-cli -n <N> …` (e.g. `-n 1`; `redis-cli` may be absent). (This is the one KV exception to the "route through `docker/sdk cli`, not bare `docker exec`" rule below — the client simply isn't in the CLI container.) For example, "KV db 0 is empty" was misread as missing data when the project was on namespace 1 — a false negative from checking the wrong DB. This applies to every KV assertion here.
- **if `yves` disabled (headless):** verify via `glue` instead — Glue selects the store per request from the **`Store`** header (or the `?_store=<STORE>` query param), so no per-store hosts are needed; probe each store with `-H 'Store: <STORE>'` on the single host (see the store-header note below). Skip the Yves probes.
- **if `backoffice` kept:** Back Office root reachable. DMS store data correct (`spy_store`/`spy_locale_store`/`spy_currency_store`/`spy_country_store` per store) via a read-only SQL check — always (the SQL check is DB-direct, independent of any app).
  - **Route DB/KV/console through `docker/sdk` (allowlisted) — NOT bare `docker exec` (prompts on every call).** Run SQL as **`docker/sdk cli "mariadb -h database -u spryker -psecret -D <db> -e 'SELECT …'"`** — one allowlisted command — not `docker exec <project>_dev_database_1 mariadb …` (which prompts every time; a whole verification pass of these is a wall of prompts). KV is the one exception (the client isn't in the CLI container — see above): `docker exec <ns>_key_value_store_1 valkey-cli -n <N> …`. Console/data/search/publish: `docker/sdk console …`. The only thing without a `docker/sdk` wrapper is the RabbitMQ broker inspection (`docker exec <broker> rabbitmqctl …`) — draining goes through the allowlisted `docker/sdk console queue:worker:start --stop-when-empty`, so reserve bare `docker exec` for the broker count/error read (or allowlist `docker exec <broker>`).
  - **In-container clients + schema (wrong name/column = wasted tries):** the DB client is **`mariadb`**, not `mysql` (absent → `executable file not found`); KV client `valkey-cli`, not `redis-cli`. And **inspect the schema before writing verification SQL — `DESCRIBE <table>` is the cheap first move; don't guess column names** (e.g. `spy_glossary_key`'s column is the reserved word `key`, not `key_name`; **`spy_cms_block`'s column is also the reserved word `key`** — needs backticks; `spy_price_product_store` has no `fk_merchant_relationship`; **`spy_currency_store` has no `is_default`**). A verification query that errors on a wrong column tells you nothing about the data.

- **if `merchant-portal` kept:** probe MP's endpoint (`mp.<region>.<domain>` per the deploy file) → 200 with its login form present (anchored selector, not a substring). MP's Angular frontend (`frontend:mp:build`) builds independently of Yves — a green Yves storefront proves nothing about MP, and MP is precisely the app whose build fails on its own. A deeper MP login/journey is out of scope here (merchant users are demo data — flag if the project dropped them).
- **BO login (if `backoffice` kept):** a 200 on the BO root is an nginx vhost answering, not a working app. Log in with the installer admin (shipped in `src/Pyz/Zed/User/UserConfig.php::getInstallerUsers()` — demo credentials, flagged for rotation at go-live) and assert the dashboard renders → 200. Same form discipline as Yves: take the login form's action + field names from the RENDERED page, never hand-build them; one cookie jar; read the flash on failure.

## Guest checkout journey — primal store (the gate add-to-cart stops short of)

Add-to-cart proves the cart; it never touches the three things the transformation curates but nothing else exercises: **checkout tax** (`tax.csv` regenerated per project country), **transactional email** (the kept `cms-block-email--*` bodies), and the **T&C page** (`gtc` stub). One guest-journey per primal store closes that: cart → checkout (address → shipment → payment → summary) → place order, then assert by DATA:
- **Order row:** `spy_sales_order` gained a row (store = primal store, currency correct, totals non-zero and tax ≠ obviously-wrong — a German 19% on a non-DE store is the classic leak).
- **OMS state:** the order's items sit in their process's INITIAL state (`spy_sales_order_item` → `spy_oms_order_item_state`) — proves the OMS wiring, not just persistence.
- **Mail:** one order-confirmation mail rendered — if the mail catcher was kept, assert via its API/UI endpoint (mailpit exposes an HTTP API; read the deploy file for the endpoint); if dropped, assert the mail renderer didn't throw (the Yves/Zed exception logs are clean) — a missing `cms-block-email--*` body throws exactly here.
- **Discipline (same as add-to-cart, doubled):** take EVERY form action + field name from the rendered pages — checkout is multi-step and its forms are namespaced inconsistently; a hand-built POST failing is your harness, not the project. Use the same logged-in company user that passed add-to-cart. A developer's real-browser checkout outranks the synthetic one.
- **Honesty note:** unlike the add-to-cart recipe, this journey is **not yet exercised end-to-end** — treat the first execution as discovery: if a step's mechanics surprise you (an unexpected required field, a payment-method precondition), record the finding rather than forcing it, and fall back to asking the developer to click through once while you assert the DATA side (order row / OMS state / mail), which is the part that matters.
- Scope: **primal store only** (cost-bounded); other stores are covered by the per-store add-to-cart + the data-grid checks.

(Keep it token-light — status code + a targeted Grep-tool check on the saved body; never read whole pages into reasoning.)

## Verify at the granularity that can BREAK — never trust an aggregate total as "verified"

This is the single most important verification rule, and the one most often gotten wrong — an "all verified ✅" on healthy aggregate counts routinely hides a broken slice. An aggregate hides a hole: a store can have a full `product_abstract_store` total while one *locale* has **zero** localized content (skipped-locale bug), or a full abstract count while a few products have no price (net-only-seed bug). Both pass every total-based check.
- **So assert coverage across the full grid, not the sum:** per store **× each locale** (`spy_product_abstract_localized_attributes` + `*_page` search docs non-zero and roughly-equal for every locale — a locale at 0 among full siblings = skipped-locale), and per store **× product** for prices (no product missing a gross/net price — the per-store price-completeness check). When you write "verified", name the grid you checked (`<S> stores × <L> locales × <N> products`), not a total. A number that looks healthy in aggregate is the classic false green.
- **A rendered storefront widget is NOT evidence its backing data was imported or is required — verify by DATA, not by the rendered DOM.** The inverse of "verify by data, not the guest HTML": when a widget renders but its backing entity was never imported, treat that as a **finding**, not scenery (a `data-qa="component packaging-unit-quantity-selector"` rendered on every PDP with **zero** measurement/packaging data imported — the selector renders regardless and falls back to a plain quantity, so its presence "proved" nothing and nearly sent a diagnosis the wrong way). Confirm the entity by row count in the DB/import, never by the fact that a component drew itself.

## The URL contract — `/<STORE>/<lang>/…` on one region host; Glue selects store by the `Store` header

**The URL contract on one region host is `/<STORE>/<lang>/…` — EVERY store is browsable; omitting the store prefix is what breaks.** On the shipped one-host-per-region dev topology all project stores are browsable at the single region host — the store comes from the **URL path segment**, not the host: `/<STORE>/<lang>/…`. This follows from `CodeBucketConfig::getDefaultCodeBucket()`, which parses `$parts[1]` against the code buckets — the very array `define-stores` sets (e.g. `[<STORE1>, <STORE2>, …]`). So probe each store as `/<STORE>/<lang>/…` and assert its own `<html lang>`/currency. **A bare `/<lang>/…` (no store segment) silently falls back to the DEFAULT store+locale** — which produces convincing false negatives about store and locale coverage (a store gets reported 404/"unreachable" or given a bogus "`<html lang>` is wrong" verdict when it was fully browsable at `/<STORE>/<lang>/…`). Do not conclude a store is unreachable until you've hit it with its store prefix.

- **Glue selects the store per request from the `Store` header** (or the `?_store=<STORE>` query param), falling back to `APPLICATION_STORE` then the first store — `vendor/spryker/stores-api/.../Processor/Resolver/StoreResolver.php` (`HEADER_STORE_NAME = 'Store'`, `PARAMETER_STORE_NAME = '_store'`). So Glue verifies any store on the single host: send `-H 'Store: <STORE>'` (or `?_store=<STORE>`). A same-currency-for-every-store result means a missing/wrong `Store` header or a stale read model, not a host-resolution limit. (Yves, separately, resolves the store from the `/<STORE>/` path segment above.)

## Recovery — publish:trigger-events, search-index rebuild, the right resource

**When `publish:trigger-events` IS the right tool — recovery only, and NOT a general "resync from DB" button.** Imports emit events on their own; a manual re-publish is for when the **read model is out of sync or corrupted** — a search index was rebuilt, events were dropped, or KV/search plainly doesn't match the DB. Not a routine post-import step. **And it does not rebuild every storage from current DB state:** after a direct SQL `DELETE` + re-import of `cms_block` rows, neither a targeted `-r cms_block` re-publish nor a full `publish:trigger-events` refreshed the stale `kv:cms_block:…` payload (the SQL mutation never queued the events; the read model is orphaned) — only a DB drop + re-import restored coherence (see SKILL.md §3b). Don't assume it can reconstruct a storage whose events were never emitted.

- **Search-index recovery:** if a `*_page` search query shard-fails or a mapping is wrong, recover: delete the per-store `*_page` indices → `docker/sdk console search:setup:sources` → `docker/sdk console publish:trigger-events`, then re-verify. (DB-touching console commands go through `docker/sdk console`, not bare `docker exec`.)
- **Rebuild the RIGHT publish resource — the intuitive name is often wrong.** `publish:trigger-events -r <resource>` only rebuilds the KV/index for that exact resource. To rebuild **price** KV storage the resource is **`price_product_abstract`**, NOT `product_abstract` (`-r product_abstract` left price KV empty and looked like the data was missing). Match the resource to the storage you're actually fixing.
