# Generate strategy (project-data)

> **⚠ EXPERIMENTAL / TEST MODE — supervised runs only.** Unlike `adapt` and `clean` (the stable, near-hands-off paths), **generate is not stable and cannot be fully automated.** It is interaction-heavy and **requires the developer to be present and to validate the result at each stage** — catalog shape, CMS rendering, per-store×locale grid, and a real add-to-cart. Several required-shape gotchas (see "Generate-mode required-shape gotchas") **fail silently** — passing every validator, booting green, then rendering an empty or unbuyable shop. Treat a generate run as a *test run you watch*, not a transformation you kick off and walk away from. The boot is the authority, but the boot alone does NOT prove correctness here.

> The generate-specific method. Shared tooling, command discipline, current-state reading, the apply/reset ladder, and the cross-cutting invariants live in the parent `../SKILL.md` — not repeated here.

The user wants a shop in their own vertical, not the shipped industrial/pump catalog. This authors a small themed catalog that boots green and is browsable. It is the **generate** sibling of the **adapt** strategy: adapt reshapes the demo catalog; generate authors a fresh themed one.

**These modes are composable operations, not a one-time exclusive choice.** The user may adapt first and later decide to replace, or clean the catalog and then generate onto the cleared base, or run this again to add more — in any order, whenever they want. So this skill does **not** assume the shipped demo is present. **Read the CURRENT catalog state before deciding what to do** (see Method step 0) — never trust `.ai-dev/project-setup.md`, which is a stale snapshot from an earlier step. What "generate" means depends on what's there now: onto a cleaned/minimal base it's a plain add (no collisions); against a full demo catalog it's a replace (drop the demo domain, keep the structural skeleton per the keep-list). Detect the base; don't presume it.

**Demo-grade, not production** — shallow structure, machine-plausible content, user-supplied images. Flag it as such; the boot is the correctness authority, same as adapt.

## The core idea — reuse the skeleton, regenerate only the domain

A Spryker catalog's difficulty is **referential integrity across dozens of interlinked files**, not the product count. So don't re-author the boot-critical plumbing; keep it and swap only the domain.

- **Reuse from the demo (domain-independent, boot-critical — do NOT re-author):** the *structural/wiring* set per `../../define-stores/references/minimal-baseline.md`'s keep-list — cms/category/slot **templates**, the `cms-block-email--*` blocks, payment/shipment methods, warehouse, tax, root category, glossary plumbing — plus the store/locale/currency skeleton (`define-stores`) and the *mechanism* that an abstract product has concrete variants distinguished by attributes.
- **Regenerate for the theme (domain-specific — author fresh):** the **category tree** + its **`category_store`** (per project store, `category_key` + `included_store_names` — categories are store-assigned exactly like products; a tree with no `category_store` rows shows in no store), the **attribute schema** (`product_attribute_key` + `product_management_attribute` + the attribute columns/values on products), **product content** (names/descriptions/meta per locale), plausible **prices** per category×currency, **stock**, unique **URLs**, `product_image.csv` rows pointing at the user's images, the **storefront navigation** (`navigation`/`navigation_node`/`content_navigation` — the demo's ~44 `category` nodes point at the OLD tree; regenerate them for your category keys or the main menu is dead — see step 5 & the parent's navigation invariant), and — **on a marketplace project — the merchants and their offers** (see below).

"Near" themes (industrial → industrial) regenerate little; "far" themes (pumps → dresses) regenerate almost the whole domain layer — both lean on the same reused skeleton.

## Marketplace layer — merchants + offers (the default), not a buyability prerequisite

This is a b2b-marketplace by default, so products are sold through merchants and offers as the shipped model — author the merchant layer as part of the domain. Note the correction to a common wrong assumption: a product is buyable from its own price + stock and does **not** technically need a merchant offer or a `merchant_product` row to check out. So authoring price + stock (§ Method) is what guarantees a buyable catalog; the merchant layer adds the marketplace sellers on top.

The interview decides the seller structure — how many sellers per product (default: the shipped marketplace model), or a simpler single-seller setup if the developer asks.
- **Distinct merchants per product.** If a product has multiple sellers, each offer is a different merchant. Unless the developer explicitly asks for it, don't add an offer from a merchant that already sells the product directly, and don't pair a `merchant_product` row with an offer for the same merchant on one product — that shows one merchant twice in the buy box, each with its own availability.
- **What to author:** `merchant` (+ `merchant_profile`, `merchant_user`, `merchant_store` per store; logos user-supplied), then `merchant_product_offer` / `product_offer` / `price_product_offer` per assigned store×currency (converted like product prices), optionally `merchant_stock`. Skip commissions / merchant-relationships / open-hours for the MVP.
- **Referential integrity:** every offer's `merchant_reference` exists in `merchant`, every offer SKU exists in the generated products, and `(merchant, store)` exists in `merchant_store` (`validate refs --composite`).

## Files-layout — a separate themed folder, NOT in-place stripping

Generate builds *fresh* domain content, so **author the themed domain CSVs into a self-contained folder** (e.g. `data/import/<project>/catalog/`) and point the import config at it — do **not** empty-and-refill the shipped demo product CSVs row by row (that's the orphan-reference minefield adapt has to fight; generate has no reason to). The shipped demo **structural** files are reused in place *while authoring* (kept, per the keep-list); the demo **domain** files are simply not referenced by the config (or bulk-deleted). This is the deliberate difference from adapt (which edits in place because it *transforms* existing data) — generate *replaces*, so a fresh tree is simpler and safer.

Reuse-in-place applies during authoring; it is not the final layout. Generate finishes with the parent SKILL's "Consolidate & clean up" pass: the retargeted structural files move under the one `data/import/<project>/` tree, the manifest is repointed, unreferenced demo files are deleted, and the on-disk tree is verified against the active manifest. Do not report the data step done until the tree matches the manifest.

## Inputs (interview + `.ai-dev/project-setup.md`)

Stores/locales/currencies come from the state file. Collect: **theme** (free text — "women's dresses", "technical books", "car brake parts"); **product count** (default ~20); **category list** (or propose a small tree for the theme); **attribute set** (or propose per theme); **variants?** (default **no**); **prices** — a price range per category **per assigned currency**, OR one base-currency range plus a **currency→rate table** (`rate_table`, same shape as adapt's) to convert with `scale --rates` (one of the two is required — multi-currency prices need a source); **image sources** — TWO separate deliverables: **product imagery** (`product_image_source`) and **CMS/banner imagery** (`cms_image_source`), each a folder path or URL list, plus how to map product images (one-each / by-category / cycle); **content language** (`data.content_language`) — `native` = author the copy directly in the project locale(s) (default), `english` = English placeholders to translate later; and — **if the project is a marketplace** — **merchants** (how many + names, default ~2–3; or one seller) and their logo source (user-supplied).

## Method — author in dependency order, fan out with the tools

0. **Read the current catalog state (not the snapshot)** — before anything, determine what's actually in the shop now: `php "$CSV" count <live catalog import files> --plain` on the active import dirs and/or check the booted search-doc count. Full demo present → this is a replace (keep-list applies). Cleaned/minimal base → this is a plain add. Empty/unclear → ask. This decides the whole approach; `.ai-dev/project-setup.md` may say "full demo, 1178 docs" long after a cleanup stripped it.
1. **Discover the target shape** — `php "$CSV" columns <demo entity files> --plain` for the exact columns of each entity you'll author (`category`, `product_attribute_key`, `product_management_attribute`, `product_abstract`, `product_concrete`, `product_image`, price/stock/url files). Match them exactly.
2. **Author the domain layer in FK order** (Write tool, small files): category keys → `product_attribute_key` (mark `is_super=1` on any attribute that will differ between a product's concretes — see C7) + `product_management_attribute` (translate `key_translation.<locale>` **and** `value_translations.<locale>` — they're display text, not keys) → abstract products (+ concretes if variants) referencing `category_key` + attribute values, with each `attribute_key_N.<locale>` set to the **machine key** (== the unsuffixed `attribute_key_N`, never a label — see C8) → per-product **unique** URLs → images.
3. **Fan across stores/currencies with the tools, not by hand** — `csv duplicate-rows`/`set` to place products in each store; prices per assigned currency — authored directly from that currency's collected range, or authored once in the base currency and converted with `scale --rates` using the collected `rate_table` (never invent a rate that wasn't collected); stock per warehouse. Expand only the **assigned** store↔currency pairs. Author the price at the **abstract level** (a `product_price` row keyed to `abstract_sku`), not only per concrete: the catalog listing, PLP and search read the abstract price, so a concrete-only price leaves the product without a listing price and filtered out of catalog/search — a green boot showing 0 products in listings. **Fan the CATEGORY tree across stores too** — author `category_store` (`category_key` + `included_store_names=<project stores>`) for every generated category, or the tree renders in no store (same store-assignment rule as products; easy to forget because categories aren't a per-currency entity).
3b. **Adapt the reused store-scoped config too.** generate reuses the demo structural skeleton, and `define-stores` seeds each store dir by copying a canonical demo dir — so those files still carry the source store's data. Two of them are boot/runtime blockers that generate handles the same way `adapt` does (see `adapt.md` steps 3–4 for the authoritative procedure):
   - **Strip store-bound demo activity.** Records tied to the old store (orders, carts, comments, quote requests) orphan on a store rename and abort the import. Some live in shared files (`common/common`), not per-store dirs, and some bind via a serialized `quote` JSON cell rather than a `store` column — so scan all of `data/import/**` for both, and remove the file and its `source:`.
   - **Regenerate store/currency-templated glossary keys and values.** Some glossary keys are templated by store and/or currency, and the importer doesn't auto-create them — so the demo's keys only cover the demo's stores/currencies. When the store/currency set changes, author the keys and convert any store/currency-scoped values for each project store×currency. Sales-Order-Threshold is the known example (a miss boots green and surfaces only at add-to-cart), but treat it as a class: check for any store/currency-templated glossary key, not just thresholds.

4. **Locales** — driven by `content_language` (you author fresh content, so unlike adapt you can write it in-language from the start — no author-English-then-translate round trip):
   - **`native` (default): author each project locale's copy directly in that language.** Write the wide files with real in-language values per `.<locale>` column (names/descriptions/meta/CMS); keep `en_US` populated as the universal fallback. Structurally still one `duplicate-columns` pass to *create* the columns, then fill each locale's cells with its own language rather than English copies. This makes `localize-content` unnecessary for generated content.
   - **`english`: author `en_US` only**, then `php "$CSV" duplicate-columns <wide files> --from en_US --to <all project locales> --in-place` (English copies, flagged as translation debt) and hand off to `localize-content` later.
   - Either way: fix each `url.<locale>` prefix and keep it unique (URLs stay language-code-based, not translated).
   - **Strip non-project locales — from the REUSED structural files too, not only what you authored.** "A finished project contains ONLY its own stores/locales/currencies" is a cross-cutting invariant (now stated in the parent `SKILL.md`); generate reuses demo structural files wholesale but has **no** strip step by default, so `de_DE` and other non-project locales survive in files like `cms_block.csv`/`product_label.csv`. Cover both shapes: drop any `.<locale>` column family whose locale isn't in the project set (`drop-columns <all reused + authored wide files> --suffix .de_DE`), **and** remap/drop `locale`-ROW values (files with a `locale` column) the same way. The add half (`duplicate-columns`) and the drop half must be **symmetric** — running one without the other is the exact asymmetry that leaves foreign locales behind. **Also flag the inverse:** a wide file that has `en_US` but is MISSING a project locale imports a silent English fallback (real case: `product_label.csv` shipped only `en_US`+`de_DE`, so NEW/SALE labels rendered English in `pl_PL`/`uk_UA`). Mechanical sweep for both: `php <validate.php> preflight <manifest> --locales <project locales incl en_US>` flags foreign `.<locale>` columns and `locale` rows across every imported file (the `absent` sweep is scoped to `config/`+`src/` and misses `data/import/**`).
5. **Images (user-supplied — never generated)** — `product_image.csv` rows with **real locale names** (`locale=default` is rejected); if fewer images than products, cycle or use a placeholder, and flag the shortfall. **CMS/banner imagery is a DIFFERENT deliverable from product imagery** — the supplied `cms-images/` are inputs for the homepage blocks below, not product shots; author the blocks *from* them, don't just copy them to `frontend/static/` and leave them unused. **Size warning:** supplied hero images run ~2 MB each — copying them raw into `frontend/static/` bloats git (~17 MB in one run); downscale to web dimensions first (a demo catalog does not need 2 MB PNGs).
   - **Homepage CMS blocks — author them; the keep-list strips the non-email blocks and nothing rebuilds them** (a real run shipped an empty homepage). Author the home **content blocks** + their `cms_slot_block` wiring + per-store `cms_block_store`, with the home slot keys called out: `slt-2` carousel, `slt-3`/`slt-5` full-width, `slt-4` grid, `slt-home-bottom`. **CRITICAL — block templates are NOT page templates:** CMS BLOCK templates live under `@CmsBlock/template/*` (`title_and_content_block.twig`, `banner_block.twig`, `banner_grid_column_block.twig`, `section_block.twig`, `jumbotron_block.twig`, `navigation_block.twig`, `product-cms-block.twig`) and are defined **implicitly by `cms_block.csv`'s `template_name`/`template_path` columns** — NOT by `cms_template.csv` (that is for PAGES; a block pointed at a `@Cms/...` page template renders nothing, silently). A `cms_block.csv` `template_path` MUST start with `@CmsBlock/`. Filtering `cms_block.csv` to email-only deletes every content-block template definition — so re-add the home block rows here.
   - **The home PAGE, not just its blocks** — blocks render into the home `cms-page` via `cms_slot_block`; that `cms_page.csv` row must exist AND be assigned to every project store via **`cms_page_store`** (both are actively imported: `cms-page` + `cms-page-store` per store). If the home page isn't store-assigned, its slots/blocks don't render there — authored blocks with no page-in-store = still an empty homepage. Reuse the kept home page and add project-store `cms_page_store` rows; strip non-project stores.
   - **Storefront navigation is a FOUR-layer chain — carrying one file leaves empty menus (a real, whole-menu-lost trap).** The header nav is NOT a widget: `page-layout-main.twig` overrides `{% block navigation %}` with `{% cms_slot 'slt-desktop-header' %}` (chasing `NavigationWidget` is a dead end — that package isn't even installed). All four layers are **structural, keep+retarget them all**, exactly like `cms_slot`/`cms_template`:
     1. `navigation.csv` — the containers (`MAIN_NAVIGATION`, `FOOTER_*`, `SOCIAL_LINKS`, `PARTNERS`…). Carrying only this makes empty `<nav>`s that make the DB *look* populated.
     2. `navigation_node.csv` — the actual menu items (per-locale `title`/`url`/`css_class`). Its `category`/`cms_page` nodes point at the DEMO tree — rewrite them to YOUR `category_key`s / pages, drop nodes for categories you didn't recreate.
     3. `content_navigation.csv` — maps a content key → a navigation container (e.g. the footer "payment methods" strip is `slt-footer-partners` → `blck-nav-footer-1` → `content_navigation('navigation-partners')` → the `PARTNERS` container; leaving `PARTNERS` node-less silently removes a visible page element).
     4. the `blck-nav-*` "Navigation block"s in `cms_block.csv` + their `cms_slot_block.csv` rows.
     - **Enumerate the demo's FULL `cms_slot_block.csv` and account for EVERY row** (the shipped demoshop has **~19 slot→block wirings**) — keep, retarget, or consciously drop with a reason. A partial restore looks fine on the homepage hero and is missing four sections below the fold. Also keep `content-product-abstract-list` (feeds the featured/best-seller sliders) and `content-banner`.
     - **Homepage slot layout (`home.twig`):** only `slt-2` is wrapped in the carousel (one Jumbotron block emitting `content_banner('<key>','home-page')` calls, one banner = one slide); `slt-3`/`slt-5` are plain stacked full-width sections, `slt-4` is the grid. Put hero/promo in the right slot or the layout won't match the demo.
     - **`content_banner` length limits:** `title` ≤ 64, `subtitle` ≤ 128 codepoints — a paragraph subtitle fails the whole import (`[subtitle] This value is too long`). Validate per-locale before spending an import round.
     - Verify: every `category` node key ⊆ your `category.csv`; every `cms_page` node key ⊆ your `cms_page.csv` (parent invariant: "Navigation & content references survive category/page changes").
   - **Localize the kept email CMS blocks** — the inherited `cms_block.csv` placeholder columns ship `en_US`/`de_DE` only; run `duplicate-columns <cms_block.csv> --from en_US --to <project locales> --in-place` (same as the catalog wide files) or transactional emails fall back to English.
   - **Marketplace offers (only if requested — see the "Marketplace offers" section):** author `merchant` (+ `merchant_profile`/`merchant_user`/`merchant_store`) before offers, then `merchant_product_offer`/`product_offer` referencing your products + merchants, then `price_product_offer` fanned per assigned store×currency (`scale --rates`). Merchant logos user-supplied. Products are already buyable from their own price+stock — offers only add sellers, so use a distinct merchant per additional seller and don't add an offer from a merchant that already sells the product.
6. **Validate before boot** — `manifest-refs <import-config.yml>` first for the whole FK graph in one sweep (every offer→product/merchant, `*_store`→parent, category reference — catches orphans a per-relation `refs` would miss), then `validate refs` for anything it leaves unchecked (store/currency vs declared sets), `refs --composite` (any marketplace parent-in-store tuple), `unique` on **every** `url.<locale>` of the **`spy_url`-backed** entities (product/category/cms url families — one dup aborts the install), `required` on `is_searchable.<locale>` (blank imports as silently unsearchable), and `product-refs` to confirm no sku-family column references a product you didn't author. **Do NOT run url-uniqueness on `navigation_node.csv`** — a nav node's `url` is a **link target**, not a URL resource, so the same category URL legitimately appears in both the main and footer menus (the shipped demo `navigation_node.csv` itself has ~8 duplicate `url.en_US`); flagging it is a false positive that trains you to ignore the check. (`preflight` exempts navigation-node sources automatically; this rule is for standalone `unique` runs.) **Also confirm two theme-crossing references the columns don't reveal:** (a) every generated `product_abstract.tax_set_name` matches a **kept** tax set (a name the keep-list dropped imports with broken/zero tax — `preflight` reports it), and (b) every `navigation_node` `category`/`cms_page` target resolves to a category/page you actually authored (dead nav nodes = broken menu, silent past boot).
7. **Assemble the import config** — reference the reused structural files + the store definitions + your themed domain folder. **Keep the shipped dependency order — do not reorder** (base reference `currency`/`country`/`locale` before their `*-store` relations; all store definitions before the catalog; `product-label` before `product-label-store`). Hand off to `boot-and-verify`.
   - **Diff the manifest against the demo's — required, not optional.** Selection-by-intuition silently loses behavioural plumbing that has nothing to do with the theme (one run dropped **86** entities the demo imports; the near-miss was `product-shipment-type`). Enumerate the shipped region manifest's `data_entity` list, diff it against your new one, and **classify EVERY missing entity as intentional-content-drop vs must-keep-structural — written down, not implicit.** Mechanical: `php <validate.php> manifest-diff <shipped full_<SRCREGION>.yml> <new full_<REGION>.yml> [--base dir]` → reports `missing` (with source row counts) + `added`.
   - **Then RANK by coverage density** — names and rendered widgets both mislead (a packaging-unit selector renders even with zero backing data). Compare each missing entity's row count to the product population: rows ≈ population (abstracts/concretes/offers → the demo gives *every* item one) → **structural/required**; rows ≪ population → **opt-in demo garnish, safe to omit**. Worked verdict from a real run (516 concretes / 589 offers): `product-shipment-type` = 527 rows ≈ 1-per-concrete → **REQUIRED, omitting it is a defect**; while `product-measurement-*`/`-packaging-*`/`-quantity`/`product-offer-validity` were 6–20 rows → sparse opt-ins.
   - **Known-structural keep-list for marketplace generate** (theme-independent — no generated catalog has reason to omit these; keep them in the manifest even when you drop the demo domain): `product-measurement-unit`/`-base-unit`/`-sales-unit`/`-sales-unit-store`, `product-packaging-unit`/`-type`, `product-quantity`, `product-offer-validity`, `product-shipment-type`/`product-offer-shipment-type`, `sales-order-threshold`, `merchant-oms-process`, `merchant-product-approval-status-default`, `merchant-commission*`, `merchant-relationship*`, `discount`/`-store`/`-amount`/`-voucher`.

## Generate-mode required-shape gotchas — columns lie about the contract

**Matching the demo's COLUMNS (step 1) does not reveal required-vs-optional, derived-vs-supplied, or enum domains.** In one run all six below passed `preflight` and every `refs`/`unique`/`required`/`product-refs` gate, then failed at import — several silently, surfacing many steps later. Author to these shapes up front:

- **C1 — `product-abstract` requires a `color_code` column.** It's read unconditionally: omit it and **0 rows import, silently**; the error surfaces ~10 steps later in `product-abstract-store` as `getIdProductAbstract() on null`. (Ordinary attribute pairs are fine at any count — they fold into `attributes`/`localizedAttributes`; `color_code` is the one read directly.)
- **C2 — `merchant-stock` DERIVES the stock name and ignores yours.** It writes `<merchant_name> <merchant_reference> Warehouse 1` and discards the `stock_name` column you supply. Every downstream reference (`product_offer_stock.stock_name`, `warehouse_store.warehouse_name`) must use that **derived** string. The demo's own values already match the formula, which hides the rule completely.
- **C3 — `merchant-user` only LINKS an existing Zed user, it does not create one.** Seed `UserConfig::getInstallerUsers()` first (via `array_merge(parent::getInstallerUsers(), …)` so the demoshop admin accounts survive and the Back Office stays unlockable), then `setup:init-db`.
- **C4 — `product_management_attribute.visibility` is an ENUM, not a boolean.** Domain is `PDP`/`PLP`/`Cart` (or empty); `1` fails all rows.
- **C5 — `product-approval-status` is mandatory and its absence is INVISIBLE** (the nastiest). With `approval_status` NULL the `page_product_abstract` publisher writes nothing → `spy_product_abstract_page_search` stays empty → **the catalog is 0 documents in search** — while import reports `Successful`, every queue drains to 0 with zero `.error` messages, and the DB grid is perfect. It defeats every signal the skills say to trust; only a **per-store `*_page` product-doc count > 0** catches it.
- **C6 — `merchant-product` (merchant↔product ownership) is separate from `merchant-product-offer`.** Without it the PDP shows no seller. Author both.
- **C7 — variants need the differentiating attribute marked `is_super=1`, or they are INERT.** If any abstract has ≥2 concretes distinguished by an attribute (e.g. `size`), that attribute's row in `product_attribute_key.csv` MUST be `is_super,1` — and **only** that one; attributes whose value is identical across an abstract's concretes stay `is_super,0`. With `is_super,0` the concretes still import and link (`product_concrete_ids` populates, so every count/`refs` check passes) but `super_attributes`/`attribute_variant_map` come out **empty → no variant selector renders**. The rule is NOT "copy the demo's super list" — it's **`is_super=1` exactly for the attribute(s) whose value differs between concretes of the same abstract.** (This is why the interview's "variants: no" default is a *simplicity* choice, not a limitation — generate DOES author multi-concrete products when asked; it just has to set the super flag. Mechanically checkable pre-boot: for every abstract with ≥2 concretes, the key(s) whose `value_N` differs must be `is_super=1`.)
- **C8 — `attribute_key_N.<locale>` is a MACHINE KEY, not display text — despite the locale suffix.** On `product_abstract`/`product_concrete`, `attribute_key_N.<locale>` MUST equal the unsuffixed `attribute_key_N` (e.g. `material`, `size`) for **every** locale — the same identifier that must exist in `product_attribute_key.csv`. **Never** author a capitalised label (`Material`, `Size`) there; the human label belongs ONLY in `product_management_attribute.csv` `key_translation.<locale>`. The localized attributes map must be `{machine_key: translated_value}`, never `{translated_key: translated_value}`. Getting it wrong is invisible through boot, reset, and every value/total check — then the Back Office product-attribute page **500s for every product** (`Key "Size" … does not exist`). (localize-content carries the matching exception: this is the one `.<locale>` column it must NOT translate.)

- **C9 — `product-concrete` requires the full localized-attribute triplet (`name`, `description`, `is_searchable`) for every store-assigned locale.** It's all-or-nothing per locale: the importer drops the whole locale bucket when one of the three is missing, so omitting any one imports 0 rows — and the error names a *different* column than the one missing (a missing `description.<locale>` reports `Undefined array key "name"`). Do not drop these columns to shrink the file; they must be present, though they may be empty. When unsure, diff your header against the demo's `product_concrete.csv` rather than trusting the reported column name. (This is the general rule for any localized-attribute importer — the mandatory columns are required for every kept locale even when blank.)

## Verify (via boot-and-verify)

Boot green; then the **per store × locale × product** grid, not aggregate totals — every product renders in every store's locale at the right currency, search returns them, URLs resolve. A healthy total can hide a store/locale/product with no content or no price. **On a marketplace: also confirm every product has a buyable merchant offer** (add-to-cart succeeds), or the catalog renders but can't be purchased.

## Honest limits

Demo-grade only (shallow, dev-supplied images, machine-plausible copy). MVP = ~20 products; **simple variants ARE supported** (multiple concretes per abstract distinguished by one super attribute — see C7); deep multi-facet variant matrices are what's out of scope. Onto a cleaned/minimal base this simply adds the themed catalog; against a full demo catalog it **replaces** the demo domain (keep the structural skeleton). Merging a themed section *alongside* a still-full adapted demo catalog — both live at once, sharing category/URL/attribute namespaces — is the one path that's still future (collision-handling not built); clean first, then generate. Variants / deep facets / large scale (100s–1000s) need chunked generation + more validation. **Re-running generate to "add more" is NOT collision-free** — a second pass onto its own prior output collides on `sku` / `url.<locale>` / `category_key` / `merchant_reference` / attribute keys, and `data:import` upserts (so it silently overwrites the colliding rows rather than adding). To genuinely add, namespace the new batch (distinct SKU/URL/category-key prefixes) and check `unique`/`product-refs` against the existing set first; to regenerate, clean the prior catalog first. The first real generate run is discovery — the boot is the authority, exactly as adapt was.

> Reshaping the existing demo catalog is the **adapt** strategy (`adapt.md`); the store skeleton + structural keep-list is `../../define-stores/references/minimal-baseline.md`. See the parent router.
