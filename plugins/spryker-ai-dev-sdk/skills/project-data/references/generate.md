> **⚠ Experimental / test mode — supervised runs only — for `source: authored`.** This warning attaches to *how the content is produced* (interactive authoring), not to *where the catalogue comes from*; `source: dataset: <path>` (a supplied structured catalogue, § Inputs) has no authoring step and is autonomous-safe — the shape gotchas below still apply to it. Unlike `adapt` and `clean` (the stable, near-hands-off paths), **authored generate is not stable and cannot be fully automated.** It is interaction-heavy and **requires the developer to be present and to validate the result at each stage** — catalog shape, CMS rendering, per-store×locale grid, and a real add-to-cart. Several required-shape gotchas (see "Generate-mode required-shape gotchas") **fail silently** — passing every validator, booting green, then rendering an empty or unbuyable shop. Treat a generate run as a supervised test run, not an unattended transformation. The boot is the authority, but the boot alone does not prove correctness here.

> The generate-specific method. Shared tooling, command discipline, current-state reading, the apply/reset ladder, and the cross-cutting invariants live in the parent `../SKILL.md` — not repeated here.

The user wants a shop in their own vertical, not the shipped industrial/pump catalog. This authors a small themed catalog that boots green and is browsable. It is the **generate** sibling of the **adapt** strategy: adapt reshapes the demo catalog; generate authors a fresh themed one.

**These modes are composable operations.** The user may adapt first and later decide to replace, or clean the catalog and then generate onto the cleared base, or run this again to add more — in any order, whenever they want. So this skill does **not** assume the shipped demo is present. **Read the current catalog state before deciding what to do** (see Method step 0) — never trust `.ai-dev/project-setup.md`, which is a snapshot from an earlier step. What "generate" means depends on what's there now: onto a cleaned/minimal base it's a plain add (no collisions); against a full demo catalog it's a replace (drop the demo domain, keep the structural skeleton per the keep-list). Detect the base instead of presuming it.

**Demo-grade, not production** — shallow structure, machine-plausible content, user-supplied images. Flag it as such; the boot is the correctness authority, same as adapt.

## The core idea — reuse the skeleton, regenerate only the domain

A Spryker catalog's difficulty is **referential integrity across dozens of interlinked files**, not the product count. So don't re-author the boot-critical plumbing; keep it and swap only the domain.

- **Reuse from the demo (domain-independent, boot-critical — do not re-author):** the *structural/wiring* set per `../../define-stores/references/minimal-baseline.md`'s keep-list — cms/category/slot **templates**, the `cms-block-email--*` blocks, payment/shipment methods, warehouse, tax, root category, glossary plumbing (**reuse ≠ leave alone** — the shipped glossary still has to be split and replicated per project locale, step 4) — plus the store/locale/currency skeleton (`define-stores`) and the *mechanism* that an abstract product has concrete variants distinguished by attributes.
- **Regenerate for the theme (domain-specific — author fresh):** the **category tree** + its **`category_store`** (per project store, `category_key` + `included_store_names` — categories are store-assigned exactly like products; a tree with no `category_store` rows shows in no store; author one row per category per store, not root-only, because children added on a later import never inherit (`storefront-effects.md`)), the **attribute schema** (`product_attribute_key` + `product_management_attribute` + the attribute columns/values on products), **product content** (names/descriptions/meta per locale), plausible **prices** per category×currency, **stock**, unique **URLs**, `product_image.csv` rows pointing at the user's images, the **storefront navigation** (`navigation`/`navigation_node`/`content_navigation` — the demo's `category`-type `navigation_node` rows point at the demo tree; regenerate them for your category keys or the main menu is dead — see step 5 & the parent's navigation invariant), and — **on a marketplace project — the merchants and their offers** (see below).

"Near" themes (industrial → industrial) regenerate little; "far" themes (pumps → dresses) regenerate almost the whole domain layer — both lean on the same reused skeleton.

## Marketplace layer — merchants + offers (the default), not a buyability prerequisite

This is a b2b-marketplace by default, so products are sold through merchants and offers as the shipped model — author the merchant layer as part of the domain. A product is buyable from its own price + stock and does **not** technically need a merchant offer or a `merchant_product` row to check out. So authoring price + stock (§ Method) is what guarantees a buyable catalog; the merchant layer adds the marketplace sellers on top.

The interview decides the seller structure — how many sellers per product (default: the shipped marketplace model), or a simpler single-seller setup if the developer asks.
- **Distinct merchants per product.** If a product has multiple sellers, each offer is a different merchant. Unless the developer explicitly asks for it, don't add an offer from a merchant that already sells the product directly, and don't pair a `merchant_product` row with an offer for the same merchant on one product — that shows one merchant twice in the buy box, each with its own availability.
- **What to author:** `merchant` (+ `merchant_profile`, `merchant_user`, `merchant_store` per store; logos user-supplied), then `merchant_product_offer` / `product_offer` / `price_product_offer` per assigned store×currency (converted like product prices), optionally `merchant_stock`. Skip commissions / merchant-relationships / open-hours for the MVP.
- **Referential integrity:** every offer's `merchant_reference` exists in `merchant`, every offer SKU exists in the generated products, and `(merchant, store)` exists in `merchant_store` (`validate refs --composite`).

## Files-layout — a separate themed folder, not in-place stripping

Generate builds *fresh* domain content, so **author the themed domain CSVs into a self-contained folder** (e.g. `data/import/<project>/catalog/`) and point the import config at it — do **not** empty-and-refill the shipped demo product CSVs row by row (that produces the orphan references adapt has to resolve; generate has no reason to). The shipped demo **structural** files are reused in place *while authoring* (kept, per the keep-list); the demo **domain** files are simply not referenced by the config (or bulk-deleted). This is the deliberate difference from adapt (which edits in place because it *transforms* existing data) — generate *replaces*, so a fresh tree is simpler and safer.

Reuse-in-place applies during authoring; it is not the final layout. Generate finishes with the parent SKILL's "Consolidate & clean up" pass: the retargeted structural files move under the one `data/import/<project>/` tree, the manifest is repointed, unreferenced demo files are deleted, and the on-disk tree is verified against the active manifest. Do not report the data step done until the tree matches the manifest.

## Inputs (interview + `.ai-dev/project-setup.md`)

Stores/locales/currencies come from the state file. **First the `source` axis** (`data.source` in the state file):
- **`dataset: <path>`** — the project supplies an already-structured real catalogue (masters, variant/colour/size records, image lists, a category tree, related-product graphs — as JSON/CSV/XML). Inputs are exactly two: the **path** and a **field mapping** (source field → import column, per entity; unmapped required columns get a stated default). None of the authoring inputs below apply (no theme, no product count, no price ranges — prices come from the dataset or a stated rule). Conversion goes through the tools: `php <CSV> add-row <target.csv> --set col=value … --in-place` per row, or build a `rows.csv` and `php <CSV> append <target.csv> --from rows.csv [--dedupe-on <key col>] --in-place`. Where a JSON→CSV conversion needs a script, state it in the step report as a deviation with the reason, write LF, and run `php <VALIDATE> preflight <manifest>` immediately after (group `lineEndings` catches CRLF). Everything from step 0 onward — shape gotchas C1–C17, the `sku-coverage` sweep, the consolidation pass — applies unchanged.
- **`authored`** — interactive authoring; the warning at the top of this file is about this path. Collect: **theme** (free text — "women's dresses", "technical books", "car brake parts"); **product count** (default ~20); **category list** (or propose a small tree for the theme); **attribute set** (or propose per theme); **variants?** (default **no**); **prices** — a price range per category **per assigned currency**, OR one base-currency range plus a **currency→rate table** (`rate_table`, same shape as adapt's) to convert with `scale --rates` (one of the two is required — multi-currency prices need a source); **image sources** — two separate deliverables: **product imagery** (`product_image_source`) and **CMS/banner imagery** (`cms_image_source`), each a folder path or URL list, plus how to map product images (one-each / by-category / cycle); **content language** (`data.content_language`) — `native` = author the copy directly in the project locale(s) (default), `english` = English placeholders to translate later; and — **if the project is a marketplace** — **merchants** (how many + names, default ~2–3; or one seller) and their logo source (user-supplied).

## Method — author in dependency order, fan out with the tools

0. **Read the current catalog state (not the snapshot)** — before anything, determine what's actually in the shop now: `php "$CSV" count <live catalog import files> --plain` on the active import dirs and/or check the booted search-doc count. Full demo present → this is a replace (keep-list applies). Cleaned/minimal base → this is a plain add. Empty/unclear → ask. This decides the whole approach; `.ai-dev/project-setup.md` can still claim a full demo catalog long after a cleanup stripped it.
1. **Discover the target shape** — `php "$CSV" columns <demo entity files> --plain` for the exact columns of each entity you'll author (`category`, `product_attribute_key`, `product_management_attribute`, `product_abstract`, `product_concrete`, `product_image`, price/stock/url files). Match them exactly.
2. **Author the domain layer in FK order** (Write tool for a new file; `php <CSV> add-row`/`append --in-place` to add rows to a file that exists — never a second `_extra` file, never a hand-rolled CSV writer): category keys → `product_attribute_key` (mark `is_super=1` on any attribute that will differ between a product's concretes — see C7) + `product_management_attribute` (translate `key_translation.<locale>` **and** `value_translations.<locale>` — they're display text, not keys) → abstract products (+ concretes if variants) referencing `category_key` + attribute values, with each `attribute_key_N.<locale>` set to the **machine key** (== the unsuffixed `attribute_key_N`, never a label — see C8) → per-product **unique** URLs → images.
3. **Fan across stores/currencies with the tools, not by hand** — `csv duplicate-rows`/`set` to place products in each store; prices per assigned currency — authored directly from that currency's collected range, or authored once in the base currency and converted with `scale --rates` using the collected `rate_table` (never invent a rate that wasn't collected); stock per warehouse. Expand only the **assigned** store↔currency pairs. Author the price at the **abstract level** (a `product_price` row keyed to `abstract_sku`), not only per concrete: the catalog listing, PLP and search read the abstract price, so a concrete-only price leaves the product without a listing price and filtered out of catalog/search — a green boot showing 0 products in listings. **Fan the category tree across stores too** — author `category_store` (`category_key` + `included_store_names=<project stores>`) for every generated category, or the tree renders in no store (same store-assignment rule as products; easy to forget because categories aren't a per-currency entity).
3a. **A SKU is four-plus-N files — every new product enters all of them, first batch or mid-project add.** The four every buyable product needs (`product_abstract`, `product_concrete`, `product_price`, `product_stock`) plus the N the shipped model gives every SKU: `product_image`, `product_abstract_store`, `product_abstract_approval_status`, `product_shipment_type` (missing → PDP: **"No shipping types available for this product."**), and on a marketplace `merchant_product` (missing → no "Sold by", the item splits into its own shipment) + the offer files. Outbound checks (`manifest-refs`, `refs`) pass with all of these missing — every key that is present resolves. Close every product add with two mechanical steps: **(a)** `Grep` a shipped/peer SKU of the same shape across `data/import/**` and confirm the new SKU hits the same file list — one diff, in the step report; **(b)** `php <VALIDATE> sku-coverage <manifest> [--base dir]` — reports each SKU missing from files its peers are in (runs inside `gate` as a non-gating warning; read the findings, because a green exit does not mean the check passed).
3b. **Adapt the reused store-scoped config too.** generate reuses the demo structural skeleton, and `define-stores` seeds each store dir by copying a canonical demo dir — so those files still carry the source store's data. Two of them are boot/runtime blockers that generate handles the same way `adapt` does (see `adapt.md` steps 3–4 for the authoritative procedure):
   - **Strip store-bound demo activity.** Records tied to the old store (orders, carts, comments, quote requests) orphan on a store rename and abort the import. Some live in shared files (`common/common`), not per-store dirs, and some bind via a serialized `quote` JSON cell rather than a `store` column — so scan all of `data/import/**` for both, and remove the file and its `source:`.
   - **Regenerate store/currency-templated glossary keys and values.** Some glossary keys are templated by store and/or currency, and the importer doesn't auto-create them — so the demo's keys only cover the demo's stores/currencies. When the store/currency set changes, author the keys and convert any store/currency-scoped values for each project store×currency, with a translation in **every project locale**. Sales-Order-Threshold is one example (a miss boots green and surfaces only at add-to-cart): its key is derived from type+store+currency and looked up unconditionally, so the empty `message_glossary_key` column in `sales_order_threshold.csv` is **not** an exemption. Treat it as a class — check for any store/currency-templated glossary key, not just thresholds — and run the deterministic pre-boot check `php "$VALIDATE" threshold-glossary <manifest> --locales <project locales>` (derived key resolves in each project locale's glossary; exit 2 on any miss).

4. **Locales** — driven by `content_language` (you author fresh content, so unlike adapt you can write it in-language from the start — no author-English-then-translate round trip):
   - **`native` (default): author each project locale's copy directly in that language.** Write the wide files with real in-language values per `.<locale>` column (names/descriptions/meta/CMS); keep `en_US` populated as the universal fallback. Structurally still one `duplicate-columns` pass to *create* the columns, then fill each locale's cells with its own language rather than English copies. This makes `translate-content` unnecessary for generated content. **Correct accents are part of "native".** Content authored for a locale must carry that language's diacritics — `Emilia-Romagna` not `Emilia-Romana`, `Envasado al vacío` not `Envasado al vacio`, `español` not `espanol`. An ASCII-stripped `native` deliverable counts as a **defect** — unaccented copy renders beside a correctly-accented UI glossary on the same page. Checked mechanically in step 6.
   - **`english`: author `en_US` only**, then `php "$CSV" duplicate-columns <wide files> --from en_US --to <all project locales> --in-place` (English copies, flagged as translation debt) and hand off to `translate-content` later.
   - Either way: fix each `url.<locale>` prefix and keep it unique (URLs stay language-code-based, not translated).
   - **Replicate the core glossary per locale — unconditionally, under `native` and `english` alike.** The shipped `glossary.csv` interleaves locales in one file and carries only `en_US`/`de_DE`, so a project locale with no rows renders **raw dot-notation keys** (`cart.checkout`-style) for every piece of UI chrome, on an otherwise correct catalog. Apply the same procedure as adapt and clean (`adapt.md` step 1 glossary bullet, `clean.md` step 7): `filter <bucket>/glossary.csv --where locale=en_US --out <bucket>/glossary.en_US.csv`, then per project locale `set <bucket>/glossary.en_US.csv --column locale --value <locale> --out <bucket>/glossary.<locale>.csv`; **repoint the manifest's `glossary` source(s)** at the per-locale files and **delete the interleaved original** (it still carries every shipped locale's rows as dead data inside an active bucket). Keep `glossary.en_US.csv` **always**, even if no store uses en_US — the runtime needs that glossary layer present (`adapt.md` step 1). English copies are flagged translation debt: an English "Checkout" renders where `cart.checkout` would otherwise show, and this does **not** contradict a declined-localization choice — it is UI chrome, not authored content. Then seed the store×currency threshold keys (step 3b) and the **native** locale display names (`adapt.md` step 1) into each locale's file.
   - **Strip non-project locales — from the reused structural files too, not only what you authored.** "A finished project contains only its own stores/locales/currencies" is a cross-cutting invariant (parent `SKILL.md`); generate reuses demo structural files wholesale and has **no** strip step of its own, so `de_DE` and other non-project locales survive in files like `cms_block.csv`/`product_label.csv`. Cover both shapes: drop any `.<locale>` column family whose locale isn't in the project set (`drop-columns <all reused + authored wide files> --suffix .de_DE`), **and** remap/drop `locale`-row values (files with a `locale` column) the same way. The add half (`duplicate-columns`) and the drop half must be **symmetric** — running one without the other leaves foreign locales behind. **Also flag the inverse:** a wide file that has `en_US` but is missing a project locale imports a silent English fallback (`product_label.csv` ships only `en_US`+`de_DE`, so NEW/SALE labels render English in every other project locale). Mechanical sweep for both: `php <validate.php> preflight <manifest> --locales <project locales incl en_US>` flags foreign `.<locale>` columns and `locale` rows across every imported file (the `absent` sweep is scoped to `config/`+`src/` and misses `data/import/**`).
5. **Images (user-supplied — never generated)** — `product_image.csv` rows with **real locale names** (`locale=default` is rejected); if fewer images than products, cycle or use a placeholder (sanctioned path below), and flag the shortfall. **Populate both URL columns on every authored row — `external_url_small` and `external_url_large`:** the **PLP/listing renders the *small* one and the PDP the *large* one**, so a row with only one filled gives broken thumbnails across every listing while the PDP looks perfect. Same for `alt_text_small.<locale>` / `alt_text_large.<locale>`. A blank in either URL column is a finding (parent invariant: a blank per-locale cell is a finding until proven a legitimate inherit). **CMS/banner imagery is a different deliverable from product imagery** — the supplied `cms-images/` are inputs for the homepage blocks below, not product shots; author the blocks *from* them, don't just copy them to `frontend/static/` and leave them unused. **Size warning:** supplied hero images can run ~2 MB each — copying them raw into `frontend/static/` bloats git; downscale to web dimensions first (a demo catalog does not need 2 MB PNGs).
   - **Sanctioned placeholder path — a generated neutral placeholder does not count as "generated product imagery".** When the supplied set is short or absent, generate **neutral SVG placeholders**: flat background, the product or category name as text, no photographic content, no logos, no brand marks. Convention: `frontend/static/placeholder/<sku|category>-{small,large}.svg` (or one shared `placeholder-{small,large}.svg` cycled across rows), sized to the demo's dimensions (small ≈ 300×300, large ≈ 1200×1200 viewBox), referenced from **both** URL columns. Every placeholder is **go-live debt** — name each one in the step-8 report and hand it to `curate-golive-data` (real imagery is developer-supplied there).
   - **Image rights.** Image sources must be **developer-owned or licensed**. **Never scrape a third-party commercial site's photography** — demo use does not grant a licence. If the developer supplies a public URL, require an explicit one-line rights confirmation ("we own these / we are licensed for these") before using it; without that confirmation, fall back to placeholders and say why in one line.
   - **Homepage CMS blocks — author them; the keep-list strips the non-email blocks and nothing rebuilds them**, so the homepage ships empty unless you author them. Author the home **content blocks** + their `cms_slot_block` wiring + per-store `cms_block_store`, with the home slot keys called out: `slt-2` carousel, `slt-3`/`slt-5` full-width, `slt-4` grid, `slt-home-bottom`. **Block templates are not page templates:** CMS block templates live under `@CmsBlock/template/*` (`title_and_content_block.twig`, `banner_block.twig`, `banner_grid_column_block.twig`, `section_block.twig`, `jumbotron_block.twig`, `navigation_block.twig`, `product-cms-block.twig`) and are defined **implicitly by `cms_block.csv`'s `template_name`/`template_path` columns** — not by `cms_template.csv` (that is for pages; a block pointed at a `@Cms/...` page template renders nothing, silently). A `cms_block.csv` `template_path` must start with `@CmsBlock/`. Filtering `cms_block.csv` to email-only deletes every content-block template definition — so re-add the home block rows here.
   - **The home page, not just its blocks** — blocks render into the home `cms-page` via `cms_slot_block`; that `cms_page.csv` row must exist and be assigned to every project store via **`cms_page_store`** (both are actively imported: `cms-page` + `cms-page-store` per store). If the home page isn't store-assigned, its slots/blocks don't render there — authored blocks with no page-in-store = still an empty homepage. Reuse the kept home page and add project-store `cms_page_store` rows; strip non-project stores.
   - **Storefront navigation is a four-layer chain — carrying one file leaves empty menus.** The header nav is not a widget: `page-layout-main.twig` overrides `{% block navigation %}` with `{% cms_slot 'slt-desktop-header' %}` (`NavigationWidget` is not involved; that package is not installed). All four layers are **structural, keep+retarget them all**, exactly like `cms_slot`/`cms_template`:
     1. `navigation.csv` — the containers (`MAIN_NAVIGATION`, `FOOTER_*`, `SOCIAL_LINKS`, `PARTNERS`…; full list + column in `../../spryker-import-tools/references/demo-facts.md#navigation`). Carrying only this makes empty `<nav>`s that make the DB *look* populated.
     2. `navigation_node.csv` — the actual menu items (per-locale `title`/`url`/`css_class`). **Account for every row, classified by `node_type` — replacing only the category links is not enough** (the same rule as the sibling `cms_slot_block.csv` layer, below). `category`/`cms_page` rows point at the demo tree: retarget them to your `category_key`s / pages, or drop with a stated reason if you didn't recreate the target. `external_url`/`link` rows — footer legal pages (Imprint, GTC, Privacy), social icons, payment/shipment partner logos — are **structural keeps, carried verbatim**, with only their locale columns adjusted (`title.<locale>`, and the `url.<locale>` language prefix where the target is internal). Replacing only the category links removes the entire footer — Imprint/GTC/Privacy, social icons, payment logos — on a green boot, because the surviving rows import fine. Report the counts per `node_type` (in → kept / retargeted / dropped) so the accounting is greppable at the end of the step.
     3. `content_navigation.csv` — maps a content key → a navigation container (e.g. the footer "payment methods" strip is `slt-footer-partners` → `blck-nav-footer-1` → `content_navigation('navigation-partners')` → the `PARTNERS` container; leaving `PARTNERS` node-less silently removes a visible page element).
     4. the `blck-nav-*` "Navigation block"s in `cms_block.csv` + their `cms_slot_block.csv` rows.
     - **Enumerate the demo's full `cms_slot_block.csv` and account for every row** (the shipped demoshop has **~19 slot→block wirings**) — keep, retarget, or consciously drop with a reason. A partial restore looks fine on the homepage hero and misses the sections below the fold. Also keep `content-product-abstract-list` (feeds the featured/best-seller sliders) and `content-banner`.
     - **Homepage slot layout (`home.twig`):** only `slt-2` is wrapped in the carousel (one Jumbotron block emitting `content_banner('<key>','home-page')` calls, one banner = one slide); `slt-3`/`slt-5` are plain stacked full-width sections, `slt-4` is the grid. Put hero/promo in the right slot or the layout won't match the demo.
     - **`content_banner` length limits:** `title` ≤ 64, `subtitle` ≤ 128 codepoints — a paragraph subtitle fails the whole import (`[subtitle] This value is too long`). Validate per-locale before spending an import round.
     - **`content-banner` per-locale column sets are all-or-nothing.** Touching any one `X.<locale>` makes the **whole** locale bucket required, so fill the complete set — `title`, `subtitle`, `click_url`, `imageUrl`, `altText` (confirm the exact set with `columns --plain`) — or leave that locale **entirely absent**. Half a bucket ships a blank/linkless banner or drops the locale silently. Same shape as C9's `product-concrete` localized-attribute triplet, which is the general case; and per the parent's blank-per-locale-cell invariant, a blank cell inside a bucket you touched is a finding, not an inherit.
     - Verify: every `category` node key ⊆ your `category.csv`; every `cms_page` node key ⊆ your `cms_page.csv` (parent invariant: "Navigation & content references survive category/page changes").
   - **Localize the kept email CMS blocks** — the inherited `cms_block.csv` placeholder columns ship `en_US`/`de_DE` only; run `duplicate-columns <cms_block.csv> --from en_US --to <project locales> --in-place` (same as the catalog wide files) or transactional emails fall back to English.
   - **Marketplace offers (only if requested — see the "Marketplace offers" section):** author `merchant` (+ `merchant_profile`/`merchant_user`/`merchant_store`) before offers, then `merchant_product_offer`/`product_offer` referencing your products + merchants, then `price_product_offer` fanned per assigned store×currency (`scale --rates`). Merchant logos user-supplied. Products are already buyable from their own price+stock — offers only add sellers, so use a distinct merchant per additional seller and don't add an offer from a merchant that already sells the product.
6. **Validate before boot** — `manifest-refs <import-config.yml>` first for the distinctive-key relations in one sweep (offer→product/merchant, `*_store`→parent, category, sales-unit refs), then `validate refs` for what it leaves unchecked (store/currency vs declared sets), **plus a targeted `refs --ref-file` for every relation `manifest-refs` can't see — the generic-column ones (`product-label-store`→label by `name`, `stock-address`→stock by `warehouse_name`) and any parent set you replaced** (a green `manifest-refs` is not full referential integrity), `refs --composite` (any marketplace parent-in-store tuple), `unique` on **every** `url.<locale>` of the **`spy_url`-backed** entities (product/category/cms url families — one dup aborts the install), `required` on `is_searchable.<locale>` (blank imports as silently unsearchable), and `product-refs` to confirm no sku-family column references a product you didn't author. **Do not run url-uniqueness on `navigation_node.csv`** — a nav node's `url` is a **link target**, not a URL resource, so the same category URL legitimately appears in both the main and footer menus (the shipped demo `navigation_node.csv` itself has duplicate `url.en_US` values); flagging it is a false positive. (`preflight` exempts navigation-node sources automatically; this rule is for standalone `unique` runs.) **Also confirm two theme-crossing references the columns don't reveal:** (a) every generated `product_abstract.tax_set_name` matches a **kept** tax set (a name the keep-list dropped imports with broken/zero tax — `preflight` reports it), (b) every `navigation_node` `category`/`cms_page` target resolves to a category/page you actually authored (dead nav nodes = broken menu, silent past boot); and (c) every glossary value that is a **navigational path** (`main_slider_*.url`, `page.terms.url`, `checkout.success.to_orders.url`, …) points at a category/page this catalog has — the shipped ones reference demo categories (`office-furniture`/`stationery`/…) a generated catalog won't have, and a dead slug in a glossary key is invisible to both `manifest-refs` and a green boot (`translate-content` re-prefixes the language segment; the target slug is a data concern here). **Plus the cheap ASCII-only scan for `content_language: native`** — for every project locale whose language uses diacritics (es/it/fr/pt/de/pl/cs/uk…), confirm its content columns contain at least one non-ASCII letter: `LC_ALL=C grep -c '[^ -~]' <authored wide file>` on the file, then per column via `php "$CSV" distinct <file> --column <name|description|meta_*>.<locale> --plain`. **A content column with zero non-ASCII letters across the whole file is a fail, not a warning** — it means the copy was authored unaccented.
7. **Assemble the import config** — reference the reused structural files + the store definitions + your themed domain folder. **Keep the shipped dependency order — do not reorder** (base reference `currency`/`country`/`locale` before their `*-store` relations; all store definitions before the catalog; `product-label` before `product-label-store`). Hand off to `boot-and-verify`, then close with step 8.
   - **Diff the manifest against the demo's — required, not optional.** A hand-selected manifest silently loses behavioural plumbing that has nothing to do with the theme, and can drop dozens of entities the demo imports (`product-shipment-type` is one that is easy to drop). Enumerate the shipped region manifest's `data_entity` list, diff it against your new one, and **classify every missing entity as intentional-content-drop vs must-keep-structural — written down, not implicit.** Mechanical: `php <validate.php> manifest-diff <shipped full_<SRCREGION>.yml> <new full_<REGION>.yml> [--base dir]` → reports `missing` (with source row counts) + `added`.
   - **Then rank by coverage density** — names and rendered widgets both mislead (a packaging-unit selector renders even with zero backing data). Compare each missing entity's row count to the product population: rows ≈ population (abstracts/concretes/offers → the demo gives *every* item one) → **structural/required**; rows ≪ population → **opt-in demo garnish, safe to omit**. `product-shipment-type` at ~1-per-concrete is **required** (omitting it is a defect), while `product-measurement-*`/`-packaging-*`/`-quantity`/`product-offer-validity` at a handful of rows are sparse opt-ins.
   - **Known-structural keep-list for marketplace generate** (theme-independent — no generated catalog has reason to omit these; keep them in the manifest even when you drop the demo domain): `product-measurement-unit`/`-base-unit`/`-sales-unit`/`-sales-unit-store`, `product-packaging-unit`/`-type`, `product-quantity`, `product-offer-validity`, `product-shipment-type`/`product-offer-shipment-type`, `sales-order-threshold`, `merchant-oms-process`, `merchant-product-approval-status-default`, `merchant-commission*`, `merchant-relationship*`, `discount`/`-store`/`-amount`/`-voucher`.
   - **Kept in the manifest ≠ authored for the theme.** The marketplace section says "skip commissions / merchant-relationships / open-hours for the MVP" while this keep-list retains `merchant-commission*` / `merchant-relationship*`; both hold, because keeping an entity in the manifest differs from authoring it. Keep them in the manifest (dropping them loses structural plumbing) — **and name their demo-default values in the step-8 report**, or every merchant order shows `Total Commission €0.00` without explanation.
8. **Report what you did not adapt — an explicit list** (the generate counterpart of adapt's "Follow-up flags" line). Close the run with a **"what I did not adapt"** list naming every entity type left at demo defaults, so each lands in go-live debt as a concrete item instead of being silently inherited: **product images** (placeholders / cycled / short set — per step 5), **discounts** (`discount*` — demo names *and* demo thresholds/amounts), **customer addresses** (demo streets; demo `customer_reference` store tokens), **payment-method naming** (demo labels rendered at checkout), **commission** (`merchant-commission*` — see the reconciliation above), **B2B feature data** when `project.audience` is `business`/`both` (cost centers, budgets, their business-unit links and the admin role's `ManageCostCentersPermissionPlugin`: authored, or dropped with the screens named as empty — `storefront-effects.md`), **USP/marketing strips** (footer USP blocks, partner logos, banner copy you did not author). One line each: entity → what is still demo → owner (`curate-golive-data` for go-live items). The data step is finished only when every remaining demo layer is reported.
   - **Inventory before `done` — the parent's four-artifact close-out, not `gate` alone.** Run `php <VALIDATE> inventory <manifest> [--base dir] [--plain]`, paste it, and classify every source `project` / `generic-plumbing` / `demo-leftover`; then diff the interview's `data.existing_data` dispositions against the manifest's entity list. A green `gate --strict` proves only that the tree matches the manifest; the manifest can still import another vertical's SSP assets or demo sales orders the interview dropped. No referential check sees subject matter; reading the sample cells does (parent `SKILL.md` → Consolidate & clean up).

## Generate-mode required-shape gotchas — the header does not show the contract

**Matching the demo's columns (step 1) does not reveal required-vs-optional, derived-vs-supplied, or enum domains.** Every gotcha below passes `paths`/`refs`/`unique`/`required`/`product-refs` and then fails at import — several silently, surfacing many steps later. Where a `preflight` group is named, `php <VALIDATE> gate` catches it pre-boot; the rest surface only in a live import or the rendered shop. Two rules before any of them:
- **Read the shipped row shape before authoring:** `git show HEAD:<shipped file>` on the demo file for each entity you author (header and a few value rows — the contract is in the values: empty `bundled`, `1` not `true`, the real template names). An invented value fails the import and costs a rebuild.
- **Run each importer against a live DB before declaring generated data done:** `docker/sdk console data:import <entity> -c <config>` per authored entity (seconds each; rung 1 of the ladder) — the static gates cannot prove an importer's column contract; only the importer can.

Author to these shapes up front:

- **C1 — `product-abstract` requires a `color_code` column.** It's read unconditionally: omit it and **0 rows import, silently**; the error surfaces ~10 steps later in `product-abstract-store` as `getIdProductAbstract() on null`. (Ordinary attribute pairs are fine at any count — they fold into `attributes`/`localizedAttributes`; `color_code` is the one read directly.)
- **C2 — `merchant-stock` derives the stock name and ignores yours.** It writes `<merchant_name> <merchant_reference> Warehouse 1` and discards the `stock_name` column you supply. Every downstream reference (`product_offer_stock.stock_name`, `warehouse_store.warehouse_name`) must use that **derived** string. The demo's own values already match the formula, so the demo data does not reveal the rule.
- **C3 — `merchant-user` only links an existing Zed user, it does not create one.** Seed `UserConfig::getInstallerUsers()` first (via `array_merge(parent::getInstallerUsers(), …)` so the demoshop admin accounts survive and the Back Office stays unlockable), then `setup:init-db`.
- **C4 — `product_management_attribute.visibility` is an enum, not a boolean.** Domain is `PDP`/`PLP`/`Cart` (or empty); `1` fails all rows.
- **C5 — `product-approval-status` is mandatory and its absence produces no signal.** With `approval_status` NULL the `page_product_abstract` publisher writes nothing → `spy_product_abstract_page_search` stays empty → **the catalog is 0 documents in search** — while import reports `Successful`, every queue drains to 0 with zero `.error` messages, and the DB grid is complete. None of the usual signals shows it; only a **per-store `*_page` product-doc count > 0** catches it. **Every generated abstract needs an approval-status row** — the usual cause is `product_abstract_approval_status.csv` emptied along with the demo catalogue. Pre-boot: `preflight` group `approvalStatusMissing`. Completion check after import: `select approval_status, count(*) from spy_product_abstract group by 1` shows no NULL row.
- **C6 — `merchant-product` (merchant↔product ownership) is separate from `merchant-product-offer`.** Without it the PDP shows no seller. Author both.
- **C7 — variants need the differentiating attribute marked `is_super=1`, or they are inert.** If any abstract has ≥2 concretes distinguished by an attribute (e.g. `size`), that attribute's row in `product_attribute_key.csv` must be `is_super,1` — and **only** that one; attributes whose value is identical across an abstract's concretes stay `is_super,0`. With `is_super,0` the concretes still import and link (`product_concrete_ids` populates, so every count/`refs` check passes) but `super_attributes`/`attribute_variant_map` come out **empty → no variant selector renders**. Copying the demo's super list does not satisfy the rule: set **`is_super=1` exactly for the attribute(s) whose value differs between concretes of the same abstract.** (The interview's "variants: no" default is therefore a *simplicity* choice, not a limitation — generate authors multi-concrete products when asked; it only has to set the super flag. Mechanically checkable pre-boot: for every abstract with ≥2 concretes, the key(s) whose `value_N` differs must be `is_super=1`.)
- **C8 — `attribute_key_N.<locale>` is a machine key, not display text — despite the locale suffix.** On `product_abstract`/`product_concrete`, `attribute_key_N.<locale>` must equal the unsuffixed `attribute_key_N` (e.g. `material`, `size`) for **every** locale — the same identifier that must exist in `product_attribute_key.csv`. **Never** author a capitalised label (`Material`, `Size`) there; the human label belongs only in `product_management_attribute.csv` `key_translation.<locale>`. The localized attributes map must be `{machine_key: translated_value}`, never `{translated_key: translated_value}`. Getting it wrong is invisible through boot, reset, and every value/total check — then the Back Office product-attribute page **500s for every product** (`Key "Size" … does not exist`). (translate-content carries the matching exception: this is the one `.<locale>` column it must not translate.)

- **C9 — `product-concrete` requires the full localized-attribute triplet (`name`, `description`, `is_searchable`) for every store-assigned locale.** It's all-or-nothing per locale: the importer drops the whole locale bucket when one of the three is missing, so omitting any one imports 0 rows — and the error names a *different* column than the one missing (a missing `description.<locale>` reports `Undefined array key "name"`). Do not drop these columns to shrink the file; they must be present, though they may be empty. When unsure, diff your header against the demo's `product_concrete.csv` rather than trusting the reported column name. (This is the general rule for any localized-attribute importer — the mandatory columns are required for every kept locale even when blank.)

- **C10 — importer column contracts the header does not reveal.** Each of these passes every static gate, then aborts a 40-minute install or imports wrong silently:

  | Column | Contract | Check |
  |---|---|---|
  | `category.template_name` | a name from the project's own `category_template.csv` (`Catalog (default)` / `Catalog + Slots` / `Sub Category grid` on the shipped clone), never an invented `Default Category` — a miss fails every category → every abstract → `getIdProductAbstract() on null` three layers away | `preflight` `categoryTemplateUnknown` |
  | `product_concrete.bundled`, `is_quantity_splittable` | a bundle definition exploded on `:`, not a boolean — leave empty, never `false` (→ `Undefined array key 1` on every concrete) | `git show HEAD:<shipped product_concrete.csv>` |
  | `is_active` | `1`, not `true` | same |
  | localized attribute slots | the full set per slot per locale: `attribute_key_N`, `value_N`, `attribute_key_N.<locale>`, `value_N.<locale>` (key = machine key, C8) | `php <CSV> columns <authored> <shipped> --plain` |
  | `product_image.locale`, `product_image_set_key` | `locale` non-empty on every row (`default` is rejected); `product_image_set_key` empty — filled, it causes a nested-transaction rollback that masks its own cause | `validate required <file> --column locale`; `csv distinct <file> --column product_image_set_key --plain` shows only the empty value |
  | `service_point_address.region_iso2_code`, `address2` | `region_iso2_code` is a state/province code (empty for DE/GB); `address2` = house number, required (`12 Berkeley Square` → `address1=Berkeley Square`, `address2=12`) | `validate required <file> --column address2` |
  | every price/money column | integer minor units — decimal major units import, publish and render at 1/100 (£39,640 → £396.40) and nothing flags it | `preflight` `priceNonInteger` |

- **C11 — the root category is `is_in_menu=1, is_searchable=0`, or the tree publishes empty.** The tree walk starts at the root and yields nothing when the root is out of the menu: `spy_category_tree_storage.data` = `[]` for every store×locale while category node storage looks fine — no main menu. `is_in_menu=0` on the root looks plausible (the root is not shown) but empties the tree; the shipped root has `1`. Pre-boot: `preflight` group `rootCategoryNotInMenu`. Post-import: `select length(data) from spy_category_tree_storage` > 2.
- **C12 — the project's override of the rendering component is part of the attribute contract.** Before authoring a super/group attribute, open the project's own copy of the widget template (e.g. `src/<Ns>/Yves/ProductGroupWidget/Theme/default/components/molecules/color-selector/color-selector.twig`) and grep it for hardcoded attribute names — the vendor default (`colorCode` via `data.colorAttributeName`) is not the whole contract. For example, the shipped clone's override also reads `item.attributes.farbe` for the tooltip, so the colour attribute key must match the one the theme template reads; any other key 500s the page (`Key "farbe" … does not exist`).
- **C13 — data that only a suppressed control would expose is debt, not data.** For every product that has offers, name the storefront control that renders them and check the BuyBox render-condition plugins: `grep -n RenderConditionPlugin src/<Ns>/Yves/BuyBox/BuyBoxDependencyProvider.php`. `ConfigurableProductBuyBoxRenderConditionPlugin` hides the seller list for any product with a configuration instance — offers on a configurable product publish fully and are unreachable, so the item enters the cart with no `product_offer_reference`, no service point, and checkout dead-ends on "none of the products are available". Same shape as the colour-code invariant: a control that renders the data needs the data, and data without a rendering control needs a stated reason.
- **C14 — never register the same key in both `product_search_attribute_map.csv` and `product_search_attribute.csv`.** Two collectors read the two tables and both append to the same page-map field, so the attribute lands twice in the nested `string-facet` array and every facet count is exactly doubled — plausible-looking numbers that only a manual count catches. Pre-boot: `preflight` group `searchAttributeOverlap`. **Keep `product_search_attribute.csv`** (it carries `filter_type`, `position` and the localized labels) and drop the key from the map file; deleting the wrong side removes the filter UI and the labels. General form: when two import files configure the same downstream field, overlap is a defect, never a reinforcement.
- **C15 — a new attribute is four files, not three.** `product_attribute_key` + `product_management_attribute` (with `visibility` — the enum in C4, and the mechanism that shows the attribute on PDP/PLP/cart as a Back Office-editable value instead of a Twig override) + `product_search_attribute` (if filterable) + the product values. Three of the four make the storefront fully correct and nothing notices the fourth is missing. Acceptance: the attribute appears in Back Office → Attributes, not only on the PDP.
- **C16 — when matching a customer's live site, inspect the image URL that site actually renders** before assuming a harvested asset is the right one (a source may hold one asset family while the live site renders another; cropping the wrong one changes the size, not the mismatch). Read the real `<img src>` off the live page first.
- **C17 — budgets/thresholds/credit limits vs the catalogue price range** (parent invariant "Money is integer minor units"): before `done`, compare each checkout-gating money value with the catalogue's cheapest/dearest price and paste the comparison in the step report — a gate two orders of magnitude below the cheapest product is a data defect (for example, a `budget.csv` credit limit an order of magnitude below the catalogue prices blocks every order). And purchasing-control data copied from the demo (cost centres, budgets, business-unit mappings — a procurement taxonomy inherited from an unrelated vertical) silently makes cost-centre + budget selection **mandatory** on every order: remove it or retheme it, never inherit it unreported; name it in the step-8 list either way.

## Verify (via boot-and-verify)

Boot green; then the **per store × locale × product** grid, not aggregate totals — every product renders in every store's locale at the right currency, search returns them, URLs resolve. A healthy total can hide a store/locale/product with no content or no price. **On a marketplace: also confirm every product has a buyable merchant offer** (add-to-cart succeeds), or the catalog renders but can't be purchased.

## Limits

Demo-grade only (shallow, dev-supplied images, machine-plausible copy). MVP = ~20 products <!-- count-ok: ~20 is an operator-chosen target, not a demo fact -->; **simple variants are supported** (multiple concretes per abstract distinguished by one super attribute — see C7); deep multi-facet variant matrices are what's out of scope. Onto a cleaned/minimal base this simply adds the themed catalog; against a full demo catalog it **replaces** the demo domain (keep the structural skeleton). Merging a themed section *alongside* a still-full adapted demo catalog — both live at once, sharing category/URL/attribute namespaces — is not supported (no collision handling); clean first, then generate. Variants / deep facets / large scale (100s–1000s) need chunked generation + more validation. **Re-running generate to "add more" is not collision-free** — a second pass onto its own prior output collides on `sku` / `url.<locale>` / `category_key` / `merchant_reference` / attribute keys, and `data:import` upserts (so it silently overwrites the colliding rows rather than adding). To add, namespace the new batch (distinct SKU/URL/category-key prefixes) and check `unique`/`product-refs` against the existing set first; to regenerate, clean the prior catalog first. Generate is discovery-grade — the boot is the authority, exactly as in adapt.
