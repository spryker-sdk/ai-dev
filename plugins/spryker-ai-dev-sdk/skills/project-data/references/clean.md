# Clean strategy (project-data) — pre- or post-boot

> The clean-specific method. Shared tooling, command discipline, current-state reading, the apply/reset ladder, and the cross-cutting invariants live in the parent `../SKILL.md` — not repeated here. The keep-list `../../define-stores/references/minimal-baseline.md` is the authoritative **spec of what the minimal tree must contain** — read it; this file is its build procedure.

The developer wants a shop with **no demo catalog** — an empty product/merchant/customer set, but a shop that still **boots green and every page returns 200**. This is the `clean` strategy; it **replaces** the adapt pass (do not run adapt as well). Runs after `define-stores`, before `boot-and-verify`. There is no catalog to reduce, so the reduce strategy does not apply.

**Method — keep/truncate the shipped structural files in place; NEVER surgically strip the demo CATALOG row-by-row.** The structural/config CSVs are small and worth keeping whole (step 1, in place); the content CSVs are truncated to header-only in place (step 8); you author only the few genuinely-new files (stripe store-assignment, per-locale glossary) plus a fresh `data/import/local/full_<REGION>.yml` that sources **exactly** this minimal set; then `rm -rf` the demo **catalog** dirs the new manifest no longer references — wholesale removal, not row-by-row editing (that orphan minefield is exactly what Clean avoids). It's a fresh clone under git, so the revert is git. Store-definition CSVs already exist from `define-stores` (single-source seeded); reuse them, don't re-author.

**Header-only truncation is clean's core move:** `php "$CSV" filter <file> --where <col>=<value-that-matches-nothing> --in-place` — keeps the header, writes 0 data rows (the importer treats 0 rows as success). `rm -rf` the demo dirs the new manifest no longer references (surface every deletion — `rm` prompts).

## Inputs (`.ai-dev/project-setup.md`, `data.mode = clean`)
`stores[]`, `region`, per-store locales/currencies/country. Standalone without a state file → ask only for these.

## Build the minimal tree

1. **Structural / code-registration CSVs — keep populated, copy shipped verbatim** (these register code, not content): `cms_template`, `cms_slot_template`, `cms_slot`; `category_template`; `navigation` (menu keys); `currency` (all ISO ship), `configuration_value`, `mime_type`; `payment_method`; `shipment`, `shipment_type`, `shipment_method_shipment_type`; `warehouse`, `warehouse_address`.
2. **`category.csv` → the root row only** (the `is_root=1` row). No demo tree.
3. **`product_label.csv` → exactly `NEW` and `SALE`.** These two are wired to `ProductLabelDependencyProvider` updater plugins that have no self-installer; a missing row aborts the install. Both are dynamic (no product SKUs). Do not add the self-installing labels.
4. **`cms_block.csv` → keep ONLY the `cms-block-email--*` rows (~54).** They are the transactional-email bodies the Mail module renders via `renderCmsBlockAsTwig`; dropping them throws on every registration/order/password mail. `csv filter <cms_block.csv> --where name=cms-block-email-- --match prefix --in-place` (prefix match; confirm the set first with `distinct --column name --plain`). Drop all other (home/nav/catalog) blocks.
5. **`tax.csv` → regenerate for the project's countries** across the shipped tax-set names (Standard / Shipment / Tax Exempt / MOV pattern). The shipped file covers only DE/AT, so any other project country breaks checkout tax. Placeholder rates are fine (flag as a follow-up).
6. **Stripe store assignment (project-local).** The vendor `payment_method_store.csv` hardcodes `stripe,DE`/`stripe,AT` → install abort, and `vendor/` is absent pre-boot (materialized in-container during boot). Author only `data/import/common/stripe/payment_method_store.csv` (header `payment_method_key,store`; one `stripe,<STORE>` row per project store) and a `data/import/common/stripe/stripe.yml` that imports `payment-method` + `glossary` straight from the vendor paths (they resolve in-container) and `payment-method-store` from the local file. Repoint the `stripe` step in `config/install/{docker,destructive,production}.yml` at it. Do not omit `payment-method-store` (Stripe would then appear in no store's checkout).
7. **Glossary — one file per locale.** Extract en_US once (`csv filter <glossary.csv> --where locale=en_US --out glossary.en_US.csv`), then per project locale copy+relabel (`csv set glossary.en_US.csv --column locale --value <locale> --out glossary.<locale>.csv`). English copy is translation debt (flag it). Not one shared multi-locale file.
8. **Header-only content — keep the header, drop every row** (the importer treats 0 rows as success): `cms_page`, `cms_slot_block`, `content_banner`, `content_navigation`, `navigation_node`; and the per-store catalog scaffolds `product_abstract_store`, `product_price`, `product_price_schedule`, `product_label_store`, `product_relation_store`, `product_measurement_sales_unit_store`, `product_option_price`, `discount_store`, `discount_amount`, `shipment_price`, `sales_order_threshold`. Preserve exact demoshop headers (price files carry the store's currency columns).
9. **Store relations — populate per store** from one template store dir, one row-set per project store (detect the store column from each header — `store`/`store_name`/`included_store_names` vary): `category_store` (root only — children inherit), `cms_block_store` (the kept email blocks × store), `cms_page_store` (header-only), `payment_method_store`, `shipment_method_store`, `shipment_type_store`, `warehouse_store`.
10. **Optional:** a `gtc` T&C CMS page stub — recommended (the checkout T&C link soft-404s without it; not a boot blocker).
11. **Fresh manifest.** With the built-in Edit tool, write `data/import/local/full_<REGION>.yml` sourcing **only** the store-definition CSVs (from `define-stores`) + everything above, in the **shipped dependency order** (`currency` before `currency-store`, `store`/`locale`/`currency` before every `*-store`, `product-label` before `product-label-store`, base tables before relations — never reorder). Delete the shipped alternate/region manifests that now dangle. `rm -rf` the demo content dirs no source references.

## Validate
- `php "$VALIDATE" paths data/import/local/full_<REGION>.yml` → every `source:` resolves (a stripped file the manifest still names is a boot-blocker). (The yml is a positional arg — no `--config` flag.)
- `php "$VALIDATE" refs <each *_store.csv> --column <store-col> --in <stores>` → store values ⊆ declared project stores.
- Confirm `category.csv` = one root row; `product_label.csv` = exactly `NEW`,`SALE`; `cms_block.csv` = only `cms-block-email--*`; header-only files have 0 data rows (`rowCount`).
## Apply — pre-boot OR post-boot (this is NOT a pre-boot-only skill)
- **Pre-boot** (un-booted clone, e.g. wizard `data.mode: clean`): the files above ARE the state; the first boot imports them — hand off to `boot-and-verify` (empty catalog, functional email/tax/payment/shipment, project stores; every page 200, missing CMS page → soft 404).
- **Post-boot** (the project is already booted — a common standalone case, e.g. "strip this shop to minimal now"): the same file edits, then reflect the emptied catalog via the **reset ladder** (`boot-and-verify` §3b for full detail) — `docker/sdk console data:import -c <config>` to confirm no orphan, then a DB drop via **`docker/sdk reset`** (a plain `data:import` won't delete the already-imported catalog). **`reset` needs a TTY — run `script -q .ai-dev/reset.log docker/sdk reset` in background, never a plain background shell (else `failed to get console`); and confirm what `reset` does in this SDK first — it may be a full destructive teardown (wipes volumes), as heavy as `clean-data`+`up`.** Then **drain the queues** + re-verify (the reset's install re-emits events — no manual `publish:trigger-events`). Emptying a populated DB needs the DB drop — file edits alone don't remove imported rows.

> Reshaping the demo catalog is the **adapt** strategy (`adapt.md`); authoring a themed catalog is **generate** (`generate.md`); store definitions / region / config literals are `../define-stores`. See the parent router.
