# Adapt strategy (project-data)

> The adapt-specific method. Shared tooling, command discipline, current-state reading, the apply/reset ladder, and the cross-cutting invariants live in the parent `../SKILL.md` — not repeated here. Per-column-family detail and the two make-or-break chains are in `adapt-strategy.md` (same folder).

**Adapt-mode** (the wizard's "adapted demo data" option): take the shipped demo catalog and re-shape it to the project's stores/locales/currencies, English content everywhere (real translations are the optional [[translate-content]] pass, later). **Adapt edits the shipped demo import in place** — the store dirs already exist (`define-stores` seeded **every** project store from the one canonical `common/DE` source and deleted the other demo dirs — see its single-source rule); adapt **fills and reshapes their content CSVs** (add project locale columns, rewrite store-scoped values, convert currencies) and edits the existing import config. It does **not** rename or create store dirs (that's `define-stores`), and it does **not** blanket-"drop dirt" (see the convert-first rule in step 3). **Do not create a `data/import/<project>/` tree.** It is a fresh clone under git, so the diff and the revert come from git — not a parallel copy + cleanup step. `csv.php … --out <same-file>` writes the change back over the file being adapted.

> The tools this skill drives (`duplicate-columns`/`duplicate-rows`/`set`/`replace`/`scale`/`drop-columns`) are in place and exercised on real data. Treat the enumerated file/entity names below as a starting set to verify against the real clone, not a closed inventory — the demoshop evolves.

## Inputs (`.ai-dev/project-setup.md`, `data.mode = adapt`)

`stores[]`, `region` — the store→currency assignments (incl. defaults) come from each store's `currencies`/`default_currency` in `stores[]`; `rate_table` (currency → rate vs source) — the **only** interview input adapt needs beyond the stores (drives price conversion). No keep/drop edge policies: adapt carries the demo data; the one exception is store-bound activity (orders/carts), removed with a warning (step 4). Locales come from `stores[]` — validated one-per-language; URL prefix = the 2-char language code (derived, not free-form).

## The file/entity/column names below are a KNOWN set, not exhaustive

Every list of files, entities, columns, or price surfaces in this skill and in `references/adapt-strategy.md` is **the known set from the demoshop as observed** — a starting point, not a complete inventory. The demoshop evolves; a project may carry more. **Discover the actual set by inspecting the data, don't stop at the names here:**
- Locale content = any CSV with a `.<locale>`-suffixed column (find with `php "$CSV" columns <file>`), not just the listed files.
- Store-scoped data = any CSV with a store column (`store`/`store_name`/`included_store_names`/…) — detect from headers.
- Price surfaces = any CSV with a currency + value column.
Scan `data/import/**` for these shapes; treat the enumerated names as examples that must exist, plus whatever else the scan finds.

## Do (drive the general tools per the strategy map)

1. **Locale columns/rows** — on the wide files (product/category/cms/navigation/content), for the project locales:
   - `php "$CSV" duplicate-columns <all wide files> --from en_US --to <loc1>,<loc2>,… --in-place` — **one call: every file × every project locale** (list `--to` + multi-file `--in-place`, no loop). Copies all families incl. `is_searchable.<locale>` — **load-bearing: must be copied, never blank** (blank imports as silently unsearchable); confirm with `$VALIDATE required … --column is_searchable.<locale>`.
   - Then fix the URL family (verbatim copies collide on uniqueness): `php "$CSV" replace <file> --column url.<locale> --search '#^/<src-lang>/#' --with '/<locale-lang>/' --regex --out <file>`. Distinct language prefixes keep URLs unique across locales (one locale per language per store). **Verify no collisions: `php "$VALIDATE" unique <file> --column url.<locale>`** — a duplicate URL fails the import. **Do this on EVERY file with a `url.<locale>` column — discover them by scanning `data/import/**` with `columns --plain`, never a fixed list.** `spy_url` is globally unique across all entities, so one missed file (real boot-blocker: **`merchant.csv`**) aborts the 30–60 min install. Known carriers: `product_abstract`, `category`, `cms_page`, `navigation_node`, `product_set`, `merchant` — plus whatever the scan finds.
   - **Order + targeting matter:** `url.<locale>` exists only *after* `duplicate-columns` has run on **that** file — `replace`/`unique` on a file with no url family errors (`no 'url.<locale>' column`). So only touch files that actually have a `url.*` family (check `columns --plain` first), and always run `replace`/`unique` on the **project file you just wrote — never the demo source** (source `url.en_US` can carry pre-existing dups that are not yours to fix).
   - **Hybrid files carry locale as BOTH a row-tag AND `.<locale>` columns — handle both passes; don't classify a file as only one.** The clearest case is `product_image.csv`: it has a `locale` **column** (each row is tagged de_DE/en_US, and image *sets* are defined per-locale-row) **and** `alt_text_small.<locale>` / `alt_text_large.<locale>` **column families**. The importer, for a row with `locale=X`, reads the alt-text column **named for that row's locale** (`alt_text_*.X`). So a project locale needs **both**: (a) the `alt_text_*.<locale>` columns added by the `duplicate-columns` pass above (do **not** exclude `product_image` from it — classifying it as "just a locale-row file" was a real miss), and (b) per-locale **rows** so each image set exists for the locale — `php "$CSV" duplicate-rows product_image.csv --column locale --from en_US --to <loc1>,<loc2>,…` (clone the en_US rows per project locale; the cloned row's `locale=X` then aligns with its `alt_text_*.X` column). Because image sets are row-defined, prefer duplicating the en_US rows over relying on the shipped de_DE rows — and never drop a locale's rows that *define* sets referenced elsewhere (step 5 caution). Scan for other hybrids the same way (a `locale` column **and** `.<locale>` columns in the same file).
   - Glossary — split the shipped interleaved `glossary.csv` into **one file per locale** in its existing bucket (e.g. `data/import/common/common/glossary.en_US.csv`, `…de_DE.csv`), not one shared multi-locale file. Cleaner review, self-contained locales (nothing shared), and the translate-content skill edits one file per language. Extract the source locale once — `php "$CSV" filter <bucket>/glossary.csv --where locale=en_US --out <bucket>/glossary.en_US.csv` — then per project locale copy+relabel — `php "$CSV" set <bucket>/glossary.en_US.csv --column locale --value <locale> --out <bucket>/glossary.<locale>.csv` (English content = translation debt, flagged). Repoint the config's `glossary` source(s) at the per-locale files.
     - **Then DELETE the original interleaved `glossary.csv` — the split only *reads* `en_US`, so the original still carries every shipped locale's rows (e.g. thousands of `de_DE` rows) as dead data.** It's no longer referenced by the config (you repointed at the per-locale files), so it's an orphaned source sitting inside an active bucket — the exact leftover the strip sweep (step 5) and the reader can't tell from real data. Remove it explicitly (deletion prompts — surface it). For example, `common/common/glossary.csv` left behind with 3,659 `de_DE` rows after a clean split. The rule generalizes: **when you split a shipped multi-value source into per-value files and repoint the config, delete the original** — a split-without-delete leaves the whole non-project remainder on disk.
     - **The split ALWAYS produces and imports `glossary.en_US.csv` — even when no project store uses en_US.** It carries the full en_US key set (plus the step-3 store×currency threshold keys in en_US) alongside the per-store-locale glossaries, and the manifest sources it unconditionally. It is the universal **Zed-side technical glossary** matching `TRANSLATION_ZED_FALLBACK_LOCALES = en_US` (see `../../define-stores/references/literal-sweep.md`) — not a storefront locale, so no store needing it is not a reason to drop it. **Consequence of deleting it:** `Call to a member function has() on null` in the messenger translator fall-through (7 Calculation-suite errors observed), and it is invisible on any project that happens to keep en_US as a store locale. Scope it precisely: only the **glossary** layer is unconditional — en_US **catalog/content** `.<locale>` columns still follow the step-5 strip pass.
       - *Tried and rejected — do not re-derive:* a `config/Shared/config_default-devtest.php` OAuth overlay and a `TranslatorServiceHelper` each make this symptom disappear, and each **masks** the real causes (the missing `-t` boot and this en_US glossary data).
     - **Seed the language/locale-NAME keys with the NATIVE name, in EVERY locale's file — unconditionally, not gated on the localization opt-out.** After the split, set each project locale's display-name value to that locale's **own** native name (`de_DE` → `Deutsch`, `it_IT` → `Italiano`, `es_ES` → `Español`, `uk_UA` → `Українська`) in all of them — the same value in every file, not a per-locale translation. A locale display name is **not translatable prose**: "Deutsch" is "Deutsch" in every locale, so an English copy or a raw key makes the **language switcher render wrong in every locale**, including the ones you did localize. Find the keys by their shipped **values** (grep the split en_US file for the shipped locale names, e.g. `English`/`German`), never by guessing key names.
2. **Stores** — store-definition CSVs (per `define-stores`' shapes) and, for each `*_store.csv` relation, replicate **the ONE canonical source store's** rows (the single source `define-stores` seeded every store dir from — the EU/`DE` one) onto each project store with `csv set --column <store-col> --value <STORE>` (detect the store column from the header). Marketplace layer too (`merchant_store`, `merchant_product_offer_store`, commissions) if present. **Every project store derives from the SAME source**, so all stores are structurally identical (same SKUs, same price rows, same relations) — they differ only by store name, currency, locale, country. **Never seed different stores from different demo dirs** (`DE`/`AT`/`US` differ in price convention and currency) — that produced structurally inconsistent stores (see `define-stores`' seeding rule; the biggest failure of a prior run).
   - **Address-bearing CSVs carry a COUNTRY dimension — relocalize it.** Detect every CSV with a country column (`country`, `iso2_code`, `country_name`) **by header scan across `data/import/**`, never a fixed list** (`columns --plain`). Known carriers: **`company_unit_address.csv`** (the one that bit), plus audit `warehouse_address.csv` (entity `stock-address`), `service_point_address.csv`, `merchant_profile_address.csv`, and `customer_address` if present. Rewrite each to a project country — `php "$CSV" set <file> --column <country-col> --value <ISO2> --in-place` — then assert the result ⊆ the project's `country_store.csv` set (`php "$VALIDATE" refs <file> --column <country-col> --in <project countries>`). **Consequence if missed:** an address in a non-project country silently falls back to Spryker's core **19% German** tax default at checkout, because the project's `tax.csv` defines rates only for project countries — the first verified FR checkout was charged 19% German tax. Invisible on a DE/AT demoshop, wrong in every other country. Country is a **fourth dimension** alongside store/locale/currency; it has its own must-fix output in step 3 (tax).
   - **Scan SHARED (non-store-dir) files for a `store` column too — not just the per-store dirs.** A file in `common/common` (or another shared bucket) can carry a hardcoded demo `store` value that the region/store-dir remap never touches → `Store with name DE not found` at import. For example, `sales_order.csv` in `common/common` had `store=DE`. Detect every CSV with a store column across **all** of `data/import/**` (headers), and remap or drop the demo store value — a shared file pointing at a demo store you renamed away is a boot-blocker.
   - **A store dir seeded by COPY shares the source's global keys — but the files this affected are auto-removed anyway.** Under single-source seeding every store beyond the first is a copy of the canonical dir, so it carries the source's non-store-scoped *keyed* demo files (`multi_cart`, `shared_cart`, `comment`) whose global keys would collide on import — but those are **store-coupled activity, auto-removed in step 4**, so the collision is moot in adapt. If you ever replicate *other* globally-keyed data across copied stores, re-key or omit it for the copies.
   - **Don't copy relations blindly — validate & repair referential integrity.** Renaming/replicating a `*_store` relation faithfully also carries over any broken cross-entity link the demoshop happened to ship. General rule: **wherever a child entity is assigned to a store, its parent must be assigned to that store too** — derive the required assignments from the data and add any missing ones, rather than trusting the shipped relation to be complete. (Shape example: a merchant whose offer is assigned to a store must have a `merchant_store` row for that store.) Apply to every parent-via-store relation you find, not a fixed list. **Verify with the composite check:** `php "$VALIDATE" refs <child-store-file> --column <parent> --column store --ref-file <parent_store-file> --ref-column <parent> --ref-column store --composite` — the `(parent, store)` tuple must exist in the parent's store relation (plain `refs` misses this — it passes if each part exists independently).
3. **Currencies** — `currency_store.csv` per the store currencies. Expand every price surface (`product_price`, `price_product_offer`, `price_product_merchant_relationship`, `product_option_price`, `shipment_price`, `discount_amount`, `sales_order_threshold` + per-merchant, `product_price_schedule`, `merchant_commission_amount`) for the **assigned store↔currency pairs only**. For each pair, take the source-currency rows and convert:
   - flat value columns (e.g. `value_net`, `value_gross`): `php "$CSV" scale <all price files> --column <value-col> --rates <CUR1>=<rate1>,<CUR2>=<rate2> --in-place` — **one call converts every currency's rows by its own rate** (`--currency-column` if not `currency`); integer minor units → default rounding.
   - the embedded volume-price tiers in `price_data.volume_prices`: `php "$CSV" scale <file> --column price_data.volume_prices --by <rate> --json-keys net_price,gross_price --out <file>` (string-pattern scaler — tolerates the demoshop's partially-empty JSON, leaves empty fields alone).
   With single-source seeding there is **one** source currency (EUR from the `DE` canonical dir) and one rate per target — no per-file currency mix to untangle. Currency definitions need nothing (all 285 ISO ship in `currency.csv`).
   - **NEVER blind-delete rows of a currency you're not keeping — convert, or you may delete a product's ONLY price.** The old "drop demo dirt rather than propagate" rule is dangerous: in the `US` dir the "stray EUR/CHF rows" were the **only** price rows for four products, and deleting them left those products priceless. Before dropping any price row of an unassigned currency, **check the SKU still has a price in a kept currency**; if it does not, **convert that row** to a project currency instead of deleting it. (Single-source seeding from `DE` mostly removes this hazard — it's a one-currency source — but keep the guard for any residual off-currency row.)
   - **Assert price completeness per store after expansion — a green boot does NOT catch a priceless store.** For every price file × every store, `php "$VALIDATE" required <file> --column value_gross --column value_net` — **both** columns non-empty. Watch for two "missing" conventions: an **empty** cell AND a literal **`0`** (the demo mixes them; `scale` skips empty cells, so an empty gross imports as 0 = no price rendered). Treat empty-OR-zero as missing for price columns. For example, a store seeded from the net-only `US` dir booted green with 4,124 `gross=0` rows and rendered **no prices**; every structural check passed. No `csv` op computes one column from another (gross = net × VAT) — if a source is net-only, derive gross from net by the store's VAT factor (a targeted fill), don't leave it empty.
   - **Store/currency-templated glossary (runtime-blocker if missed).** Regular Sales-Order-Threshold builds its message key at runtime from store+currency: `sales-order-threshold.{hard-minimum,soft-minimum,hard-maximum}-threshold.<store_lc>.<cur_lc>.message`, and looks it up unconditionally. The empty `message_glossary_key` column in `sales_order_threshold.csv` is **not** an exemption — a blank cell reads as "no message to author," but the key is derived, not taken from that column. The importer does NOT auto-create the keys — seed them for each project store×currency pair, with a translation row in **every project locale of that store** (the key is store+currency, but the glossary value is per-locale, so a miss on one locale throws only when that locale adds to cart). Remove the demo `de/at/us × eur/chf/usd` keys (detect by the `\.(de|at|us)\.(eur|chf|usd)\.` pattern). A green boot won't catch a miss — it throws `MissingTranslationException` at **add-to-cart** in the offending store/locale. Deterministic pre-boot check: `php "$VALIDATE" threshold-glossary <manifest> --locales <project locales>` — for every threshold row it derives the key and asserts it resolves in each project locale's glossary (exit 2 on any miss; excludes the auto-generated merchant-relationship thresholds). `merchant-relationship-threshold.*` is auto-generated by its importer — never seed those. (See adapt-strategy → Prices.)
   - **Tax follows the countries, and it is a must-fix, not a warning.** Regenerate `tax.csv` for the project's countries across **every** shipped tax-set name (the Standard / Shipment / Tax Exempt / MOV pattern) — the shipped file covers only **DE/AT**, so any other project country has no rate at all. Same rule as `clean.md` step 5; adapt owes the identical output. Then **assert every `tax_set_name` referenced anywhere** — `product_abstract`, `product_option*`, `shipment*`, offers — has a rate row for **every** project country: `php "$CSV" distinct <each referencing file> --column tax_set_name --plain`, then confirm each value appears in `tax.csv` once per project country. **Mechanism:** the importer **auto-creates a referenced-but-undefined tax set RATELESS**, so the import stays green and checkout then falls back to the core **19%** default — invisible on a German demoshop, wrong everywhere else. Placeholder rates are fine pre-go-live (flag for `curate-golive-data`); a **missing country row is not**. Corollary: once your countries differ from DE/AT, a `tax_set_name` preflight warning is **not** the harmless shipped quirk it is documented as elsewhere — triage it as this defect.
4. **Locale-row data** — files where `locale`/`locale_name` is a *row* value need real project-locale rows: `product_image` (real names; `locale=default` rejected), `customer` (`locale_name` ∈ project locales), `product_review`. (The demo customers, B2B org graph, reviews and shopping-lists are store-agnostic — adapt just carries them like any other demo data; nothing to decide.)
   - **`product_attachment` is a locale-ROW file too, and easy to miss** — it uses a `locale` column (values `default` and `de_DE`), not `.<locale>` columns, so neither the `duplicate-columns` list nor the `drop-columns --suffix` pass touches it, yet it IS in the active manifest (the strip sweep still found `de_DE` in it). Handle it as a locale-row file (duplicate/relabel rows per project locale, drop the demo `de_DE` rows). **Note the conventions differ per file:** `product_attachment` accepts `locale=default` legitimately, whereas `product_image` rejects `default`. Don't assume one locale-row rule for all — match by the file's actual values. (General principle already stated: match by shape, not a fixed name list — `product_attachment` is just one more known member.)
   - **Store-bound demo activity can't be carried to new stores — remove it and WARN (not a question).** Renaming the stores orphans records tied to a store (or a frozen store+currency transaction): demo **orders** (`sales_order` — verified `store=DE`; `shipment`), **carts** (`multi_cart`, `shared_cart`), **comments** (`comment`), and **quote requests** (`quote_request`, `quote_request_version` — actively imported, and their store binding hides **inside the serialized `quote` JSON cell** (`{"store":{"name":"DE"},…}` plus currency and SKUs), so a store-COLUMN scan passes them clean). **Detect by scanning for a store column AND by grepping JSON-bearing cells for `"store"` tokens** (don't trust a fixed list — a shared `common/common/sales_order.csv` with `store=DE` is a real boot-blocker; the quote-request blob is the known column-scan escapee). Remove **both** their `source:` entries and the CSV files, and **tell the developer in one line**: "some demo data (orders/carts tied to the old stores) can't be persisted under the new stores and was removed." It's a warning, not a keep/drop question — the store they belonged to no longer exists. (`rm` prompts — surface the deletion.)
   - **Do NOT remove configuration the shop needs** (these only *look* transactional): `sales_order_threshold*` (min/max order thresholds — carry the runtime store×currency glossary keys, step 3), `shipment_type`/`shipment_method`/`shipment_price`, `payment_method*`, `order_source`. Match the exact activity entities by their store-coupling, not any name containing `order`/`shipment`.
5. **Strip demo leftovers** (a finished project contains ONLY its own stores/locales/currencies — see adapt-strategy → "Strip demo leftovers"). After the add passes, remove: (a) every `.<locale>` column whose locale is not in the project set — **one call: `php "$CSV" drop-columns <all wide files> --suffix .de_DE --in-place`** (`--suffix` drops a whole locale family across every file; add a `--suffix` per non-project locale). Detect shipped locales by scanning column suffixes; keep exactly the project locales, **+ `en_US` always for the GLOSSARY layer** — `glossary.en_US.csv` (step 1) is **never** in the strip pass, no matter which locales the stores use, because it is the Zed fallback glossary and deleting it throws `Call to a member function has() on null` in the messenger translator. For **non-glossary** wide files, en_US `.<locale>` columns are dropped like any other non-project locale. **The `<all wide files>` list MUST be symmetric with the `duplicate-columns` add pass (step 1) — every file that got `.<locale>` columns added must be in this drop list, hybrids included.** The classic miss is `product_image.csv`: step 1 is emphatic it's a hybrid that MUST get the added `alt_text_*.<locale>` columns — but it's just as easy to omit from THIS drop pass, leaving `alt_text_small.de_DE`/`alt_text_large.de_DE` behind in a **live-imported** file (observed). Derive the drop list from the same scan as the add list (`columns --plain` → every file carrying a `.<non-project-locale>` suffix), not a hand-kept subset — add and drop are two directions of one operation on the same file set. (b) the demo `de/at/us × eur/chf/usd` threshold glossary keys (step 3). These import as inert dead data if left. Verify with an `absent` sweep for the shipped-not-project tokens (`DE`/`AT`/`US`, `de_DE`, `eur`/`chf`/`usd`) — **scope the sweep to the ACTIVE manifest's bucket** (the dirs `full_<REGION>.yml` actually imports), **not blindly `data/import/**`.** The tree also holds CI/fixture buckets — `b2b_common/`, `robot/`, `b2b_robot/`, and non-active files like `combined_product.csv`, `*_internal.csv` — that the active boot never imports and that this adapt pass never touched; sweeping them raises false "not clean" hits (they still carry `DE`/`de_DE`). Decide explicitly: either exclude those buckets from the "clean" bar, or make adapting/dropping them a stated choice (if the project runs that CI lane). Within the active bucket, a finished project should be essentially clean; the fixture buckets are a separate, explicit decision — not silent dirt.
   - **Before deleting a non-project locale's ROWS (not columns), check whether those rows DEFINE an entity referenced elsewhere.** Dropping columns is safe; dropping *rows* keyed by a locale can delete a definition. For example, `product_image.csv` interleaves configurable-bundle-template image **sets** across locales (odd set keys defined on `de_DE` rows, even on `en_US`); deleting the `de_DE` rows removed image sets 1/3/5, so `configurable-bundle-template-image` failed with `Could not find product image set`. If a to-be-dropped locale's rows define entities (image sets, etc.) that other files reference, re-create those definitions under a kept locale (`en_US`) before dropping — don't just delete.
6. **Import config** — edit the shipped config in place with the **built-in Edit tool** (anchored, format-preserving) — **never regenerate or regex-rewrite the YAML with `python`/`ruby`/`sed`**. Rename `data/import/local/full_<SRC-REGION>.yml` (e.g. `full_EU.yml`) to `full_<REGION>.yml` and repoint its `source:` paths at the adapted files and renamed store dirs; remove sources for dropped demo stores/dirt, add the per-locale glossary sources. **Keep the shipped dependency order verbatim — do not reorder** (the base-before-relation detail is the rule below; the shipped file already has it right, so don't "improve" it). Entity names must keep matching the importers. Don't pre-validate the YAML with an external tool — `validate.php paths` confirms every `source:` resolves, and `docker/sdk bootstrap` proves validity. This skill owns the import config; `define-stores` adapts the store-definition CSVs but not the config.
   - **Strip the shipped ALTERNATE manifests that now dangle.** `data/import/local/` ships several region/lane manifests besides the one you renamed — e.g. `full_US.yml`, `b2b_full_<SRC>.yml`, `full_ROBOT.yml`, `b2b_full_ROBOT.yml`. After you rename the active one to `full_<REGION>.yml` and delete the demo region dirs, these others still `source:` the deleted/renamed dirs → **dangling and internally broken**. They're **harmless** (the dev boot invokes only `full_${SPRYKER_REGION}.yml`), but a finished project shouldn't carry broken manifests. Delete the ones no active lane uses (verify against the recipes: `config/install/*.yml`), and flag the CI ones (`*_ROBOT`) if the project doesn't run that CI lane. Deletion prompts (`rm` isn't allowlisted) — surface it as a cleanup step, don't force it.
   - **KEEP the shipped import order — do NOT reorder it.** The shipped manifest already encodes the correct dependency order (`currency` before `currency-store`, `locale` before `locale-store`, `store` before every `*-store`, all store definitions before the catalog, `product-label` before `product-label-store`, …). You break it **only by reordering** — so don't. When you substitute paths/stores/values or **add** a store, keep every source in the **same relative position** the shipped order already uses (a new store's definition sources go in the existing store-definition group, not appended at the end, not hoisted above the base tables). Two failure modes, both from reordering: appending a 3rd store's `locale-store` after the catalog leaves its locale with **zero** content (catalog binds only locales already store-bound → silent empty store, green boot); and "all definitions at the top" hoisting `currency-store` above `currency` → `Currency not found` abort. If you never move a line out of its shipped order, neither happens. Verify per the store×locale content check in `boot-and-verify` step 4 (store-level counts hide a skipped locale).
   - **Reference data must CONTAIN what a relation references.** Same principle, one step deeper: `locale-store` needs each project locale to already exist in the base `locale` reference (`spy_locale` ← the shipped `locale.csv`), or it fails `Locale not found`. Spryker ships many locales but maybe not an exotic one; can't be checked against the DB pre-boot, so **verify each project locale is present in the shipped `locale` source and add any missing row there.**

## Validate & apply

- `validate.php` paths / refs (store & currency) / required (`is_searchable`). **URL-uniqueness sweep — run `unique` on `url.<locale>` for EVERY url-family file (scan), not just a few** — this catches the `spy_url` collisions (e.g. `merchant.csv`) that abort the boot. Absent-sweep the shipped-not-project tokens to confirm the strip pass (step 5). Triage: dropped demo dirt is expected (listed), not an error.
- **Pre-boot** (wizard flow): done — the boot proves it.
- **Running project** (standalone): targeted `docker/sdk console data:import --config=...` (the importers emit publish events automatically) then **drain the queue workers** so KV/search catch up. Only run `publish:trigger-events` to recover an out-of-sync read model (or after a search-index rebuild), not routinely. The `haveTables` gate does NOT apply to manual imports.
- Follow-up flags: English-copy locales (incl. glossary), Spryker-CDN demo imagery (fine for dev, go-live flag), demo customer passwords if customers adopted, dropped dirt.

> Removing a catalog subset is the **reduce** strategy (`reduce.md`); removing whole domains is **cleanup** (`cleanup.md`); a fresh themed catalog is **generate** (`generate.md`). See the parent router.
