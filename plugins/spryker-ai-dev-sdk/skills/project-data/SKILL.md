# project-data

The universal skill for everything under the project's `data/import/**`. It owns one job — **get the project's import data into the shape the project needs** — and it does that through one of five **strategies**. You **pick the strategy** from the interview (`.ai-dev/project-setup.md` `data.mode`) or from what the user asks in plain terms, apply the **shared core** below (tools, discipline, state-reading, apply-ladder, invariants — the same for every strategy), then follow that strategy's **reference file** for the method.

You drive the `spryker-import-tools` scripts (`csv.php` + `validate.php`) with judgment; the tools are concept-free (they know nothing about stores/locales/currencies) — the judgment is what this skill supplies. (Failure-signature triage for the data steps lives in the Known-traps catalog: `../project-starter-wizard/references/pitfalls.md`.)

## Pick the strategy (interview or plain-language intent → strategy)

| The user wants to… | Strategy | Method reference |
|---|---|---|
| Reshape the **shipped demo catalog** to the project's stores/locales/currencies (English content everywhere) | **adapt** | `references/adapt.md` (+ `references/adapt-strategy.md`) |
| **Author a fresh themed catalog** in the project's own vertical — "add demo data", "generate ~20 products from these images", "create CMS blocks from these pictures" | **generate** ⚠ *(experimental — supervised only; see reference)* | `references/generate.md` <!-- count-ok: ~20 is an operator-chosen target, not a demo fact --> |
| Start with **no demo catalog** — a minimal shop that still boots green (working email/tax/payment/shipment, project stores, empty catalog) | **clean** | `references/clean.md` (spec: `../define-stores/references/minimal-baseline.md`) |
| Keep **only part** of the demo catalog and remove the rest ("we sell X, drop the other categories") | **reduce** | `references/reduce.md` |
| **Remove whole demo domains** — customers, merchants, reviews, wishlists, CMS, discounts, transactional activity, … | **cleanup** | `references/cleanup.md` |
| **Remove a locale/language** — "drop German", "we don't need de_DE" | **adapt's strip pass**, standalone | `references/adapt.md` step 5 (columns via `drop-columns --suffix`, locale-ROW files, glossary rows, hybrids like `product_image` whose rows *define* image sets) |

Ad-hoc **add / edit / filter / one-off remove** on import data that isn't one of the above is the same tools driven directly (`csv filter`/`delete`/`set`/`duplicate-*` → `validate` → apply) — no separate strategy; use the shared core and the closest reference for the cascade rules.

- Standalone (a user asks directly), classify their words against the table — **never make them name a strategy or a file.** "Add demo data for my shop" → generate. "Drop the demo customers" → cleanup. "We only sell heat-recovery" → reduce. If the request is ambiguous, ask one plain question.
- In the **wizard**, `data.mode` picks it: `adapt`→adapt, `clean`→clean, `generate`→generate, `leave`→skip entirely; plus a `reduce` pass after adapt if `reduce_catalog ≠ keep:all`. `generate` carries a **`source` axis**: `authored` (interactive authoring — the not-hands-off warning attaches here) or `dataset: <path>` (a supplied structured catalogue: the path plus a field mapping; conversion into the import CSVs goes through `php <CSV> append`/`add-row`, and where a JSON→CSV conversion needs a script, state it as a deviation in the step report with the reason, write LF, and run `php <VALIDATE> preflight <manifest>` right after). Never record an invented marker (`authoring: none`) to mean "dataset" — use the axis.

## Strategies compose

These are operations on the current data, runnable **in any order, whenever**: adapt now and later replace with generate; clean the catalog and then generate onto the cleared base; reduce after adapting. So **do not assume a starting state** — the same request means different work depending on what's already there. Every strategy therefore begins by reading the **current** state (below). Merging a fresh themed catalog *alongside* a still-full adapted catalog (both live at once, sharing namespaces) is not supported — clean or reduce first, then generate.

## Shared core (applies to every strategy)

### Tools & command discipline
Follow **`spryker-import-tools` → "Invocation & command discipline"** (the authoritative copy). In short: invoke `csv.php`/`validate.php` by their literal path from the project cwd (`$CSV`/`$VALIDATE` and `<CSV>`/`<VALIDATE>` in the references = that path, substituted inline — never a shell variable, never `cd`); one op over many files = one command with `--in-place`, never a shell loop or operator; count via `rowCount`/`matchedRows`; explore with the built-in Read/Grep/Glob; YAML via the built-in Edit tool; every `rm` surfaced as an explicit deletion step. Work from real files: discover columns with `csv columns`, never hardcode a header. Rules specific to this skill:
- **Run the command a skill or reference names.** When this skill or a reference names a command (`csv.php set …`, `validate.php manifest-refs`, …), run that command, not a hand-written script that does the same thing; the step report names the command, and its literal output goes to `.ai-dev/evidence/project-data.md` (in a wizard run — the report stays three lines and cites that path; standalone, put it in the reply). A step report that describes an outcome without the named command's output on record does not meet this rule.
- **Before the first data edit, list the whole tool surface:** run `php <CSV>` and `php <VALIDATE>` with no arguments — each prints every op/check. The commands named in prose are a subset of the surface; checks such as `manifest-refs`, `threshold-glossary` and `product-refs` appear only in that listing.
- **Authoring rows = `append`/`add-row`, never a second source file and never a hand-rolled writer.** A glossary key the shipped file lacks, an extra product label, a new store row: `php <CSV> add-row <file> --set col=value [--set col2=value …] --in-place` (unknown column = hard error; unset columns empty) or, for a batch, `php <CSV> append <file> --from <rows.csv> [--dedupe-on <col>] --in-place` (the `--from` header is a subset of the target's; `--dedupe-on` skips keys already present). One file per entity per scope stays intact — a `glossary_project.csv` overlay is the `duplicateEntitySources` finding. If a script is unavoidable (a JSON→CSV conversion), it writes LF (`lineterminator='\n'` — Python's `csv` default is CRLF, the repo is LF; `preflight` group `lineEndings` catches it) and the step report names the deviation and its reason.
- **Read the shipped contract from git; never restore data from it.** `git show HEAD:<shipped file>` on a shipped file's header and values is the correct way to learn an importer's contract — the real `template_name`s, `tax_set_name`s, label `name` keys (an invented value fails the import and costs a rebuild). What stays forbidden is reconstructing or restoring data from history instead of working from the current files (`csv read`/Read): reading the contract is fine, `git checkout <file>`/`git show … > file` as a data source is not. It's a fresh git clone, so **git is the undo for file edits** — never hand-roll a `cp`-into-scratchpad backup. But git does **not** restore a database or a search volume — a `reset`/`clean-data` wipe is not git-recoverable (see the destructive-op gate below).

### When a change breaks something, suspect your own data delta first
If the storefront worked in the fresh demoshop and breaks after your import edits (empty menu, missing homepage blocks, unbuyable product), the file **you just changed/dropped** is the prime suspect — **not** vendor/core code. Diff your delta (`git diff -- data/import config`) and re-check completeness (`preflight`, `refs`, per-store×locale counts) **before** reading any vendor package. When the fresh demo shop worked, the delta is the first cause to rule out (full diagnostic order: `boot-and-verify` intro). A dropped navigation import set, for instance, presents as a broken menu that looks like a vendor bug but is your delta.

### Record progress for resume (wizard runs)
The data strategies are the longest steps of a wizard run. When running under the wizard, set the state-file step to `in-progress` and update its `note` after each major pass (e.g. `locales done, currencies pending`) — an interrupted run then resumes from the note instead of re-running from the start, which matters most for the deletion/strip passes (not idempotent).

### Read the current state first
Before deciding what to do, determine what's actually in `data/import/**` **now** — `csv count <live catalog files> --plain` on the active import dirs and/or the booted search-doc count. **Never trust `.ai-dev/project-setup.md` for the current catalog state** — it's a snapshot that a later cleanup/adapt may have invalidated (it can still show a stale "full demo" count long after a cleanup stripped the catalog). What each strategy means depends on the live base (e.g. generate onto a cleaned base = plain add; against a full demo = replace).

### Destructive operations — preview and announce; ask only when real data is at stake
The policy is the one in `spryker-import-tools` → Invocation & command discipline (`reset`/`clean-data` weight + escape hatch: `boot-and-verify` §3b). What it means for this skill: preview every in-place removal (`csv filter`/`delete` with no `--out`/`--in-place` reports `matchedRows` without writing) and announce it in one plain line before it runs; a removal the confirmed answer set decided (`data.mode: clean`/`reduce`, D4 `data.existing_data`, a demo run's `sample_products`) is logged and proceeds; the question is kept for real data git cannot restore.

### Apply — pre-boot OR post-boot (the reset ladder)
Every strategy works both **pre-boot** (un-booted clone, e.g. the wizard — the files are the state; the first boot imports them) and **post-boot** (already-booted project — edit files, then reflect). Post-boot follow the **reset ladder** — full detail in `boot-and-verify` §3b:
1. `docker/sdk console data:import -c <config>` — validates the edits leave no orphan (fast, collects all failures, no teardown).
2. **Adds and value-safe updates:** the same `data:import -c <config>` applied for real — it upserts, and the importers emit publish events.
3. For **deletions**, a plain `data:import` only upserts and won't remove already-imported rows → reflect them with **`docker/sdk reset`** (drops the DB and re-imports). `reset` needs a **TTY**: run `script -q .ai-dev/reset.log docker/sdk reset` in the background, never a plain background shell (else `failed to get console`); and **confirm what `reset` does in this SDK first — in some it's a full destructive teardown (wipes volumes)**.
4. **`clean-data` + full `up`** — code/deploy/service changes only, never for data (~30–60 min).

After whichever rung ran, **drain the queue workers** so KV/search catch up. Imports emit publish events automatically — `publish:trigger-events` is **recovery-only** (out-of-sync read model / after a search-index rebuild), never routine.

**Add-only importers — rung 1 cannot move or remove, and two of them raise no error:**
- **`cms-slot-block` is add-only and raises no error.** Changing an existing row's `slot_key` and re-importing **adds** a second `(slot, block)` relation and leaves the old one — the block renders twice on the page, `gate` stays clean (the CSV holds one correct row; the duplicate lives only in `spy_cms_slot_block`). Reorder within a slot by `position` freely; moving a block between slots on a live stack needs a `reset`, or a relation-row delete + publish per the next bullet. Contrast the insert-only importers that throw (`discount-amount`, `cms-block` on a template change — a unique-constraint error you can see).
- **`*_store` relation tables: the importer adds, only a `reset` or a manual delete removes.** `CmsBlockStoreWriterStep` and its siblings use `findOneOrCreate()`, so deleting the CSV row and re-importing changes nothing — a per-store split of existing entities needs one of the two, and the CSV must be updated regardless so a later `reset` reproduces it. Before assuming a reset, **read the entity's storage writer** (Grep the publisher for `pairRemaining…`/`deleteStorageEntity`): a writer that prunes orphans makes a relation delete + publish safe. Known-safe: delete the `spy_cms_block_store` relation rows, then `docker/sdk console publish:trigger-events -r cms_block` — `CmsBlockStorageWriter::pairRemainingCmsBlockStorageEntities()` pairs the orphaned storage rows with a null block and `deleteStorageEntity()` pushes the removal to the sync queue, so `spy_cms_block_storage` and Redis are pruned correctly. Known-unsafe: deleting a `spy_cms_block` row and re-importing it (see `boot-and-verify` §3b). Route the SQL per `../boot-and-verify/references/verify-recipes.md`.

**Insert-on-change importers — after a value change, never use rung 1 for `product-price`, `product-price-schedule`, `discount-amount` and `cms-block`; all four go straight to rung 3 (`reset`).** Each looks the existing row up by its *values*, not its key, so a changed value never finds it and a new row is written. What happens next depends on whether the table has a unique key to stop it:
- **Silent duplicate — `product-price`, `product-price-schedule`.** `PriceProductWriterStep` keeps an existing `spy_price_product_store` row only when gross, net and the price-data checksum all match, otherwise it saves a new one; `PriceProductScheduleWriterStep` runs `findOneOrCreate()` filtered on the prices and dates. Neither table carries a unique key over (price product, store, currency), so the re-import **adds a second row instead of updating the first** — the symptom is a table that grows after an import meant to update in place. Do not re-import to test for the duplicate: a full import doubles the price table and needs a reset to recover.
- **Visible throw — `discount-amount`, `cms-block` (on a template change).** `DiscountAmountWriterStep` looks up (discount, currency, gross, net), and the new row hits `spy_discount_amount`'s unique (currency, discount) → `Unable to execute INSERT`. `cms-block` builds its glossary keys from the template name, so a template change inserts a second key mapping for the same placeholder against the unique (block, placeholder); a changed placeholder text on the same template updates in place and is rung-2 safe.
- **Not in this set — `*_store` relation tables.** They carry a unique (entity, store) key and use `findOneOrCreate()`, so they never duplicate; they only fail to *remove* (the add-only bullet above).

**Gate every rung before it runs.** Before any `docker/sdk reset|clean-data|up|data:import`, run `php <VALIDATE> gate` and stop on a gating finding. With a gate baseline on file (`.ai-dev/gate-baseline.json`), only findings the baseline does not hold count; without a baseline, any gating finding stops the rebuilds (`reset`/`clean-data`/`up`) and `data:import` proceeds. Trusted rebuilds — a demo clone, first setup, or a recorded `standing_approval: { scope: rebuilds }` — run without a question (announce each in one line with its expected duration); on a project that already has real data, ask once before the first rebuild; before the third and every later rebuild on a project, write `rebuild #N: <why rung 1 cannot show it>` to the decision log, then continue. `data:import` needs no question, so rung 1 stays cheap. Never run a rung-3 `reset` before a clean rung-1 `data:import -c <config>`, except for the insert-on-change importers above: inverting the ladder spends rebuild cycles that rung 1 makes unnecessary. Count the rebuilds you run and state the count in the step report; the evidence file records why each was necessary; a count above two is itself a finding.

### Cross-cutting invariants (they apply to more than one strategy)
**Don't check these by hand file-by-file — run `php <VALIDATE> gate` (= `paths` + `preflight` + `manifest-refs` + `threshold-glossary` + `duplicate-keys` + `cms-block-store` (gating), `orphan-files` (gates only with `--strict`), and six warning-only checks, one call, exit `0` clean, `1` warnings only, `2` gating finding); `preflight` alone sweeps the first four across every file the manifest imports** (url-uniqueness, is_searchable, price completeness, import order), returning one grouped verdict. The list below is what it enforces and what to drill into per-file when it flags something:
- **`spy_url` is globally unique across all entities** — one duplicate `url.<locale>` aborts the 30–60 min install. Run `validate unique` on **every** url-family file (scan for them; `merchant.csv` is easy to miss and blocks the boot), not a fixed list.
- **`is_searchable.<locale>` is required** — blank imports as silently unsearchable; must be copied, never left empty (`validate required`).
- **A blank per-locale cell is a finding until proven to be a legitimate inherit.** Two known cases follow this rule: blank `is_searchable.<locale>` imports as silently unsearchable (above), and `product-concrete`'s localized-attribute triplet (`name`/`description`/`is_searchable`) is **all-or-nothing per locale** — one blank drops the whole locale bucket (`references/generate.md` C9; `content-banner`'s locale buckets behave the same). So for **every** `.<locale>` column set: an empty cell is either a proven inherit (name the importer that inherits it) or a defect. Check with `validate required <file> --column <col>.<locale>` per project locale; for price columns treat a literal `0` as blank too.
- **Account for every row of a structural file you rewrite (as opposed to add to)** — keep, retarget, or consciously drop **with a reason**, and report the counts. Applies to `navigation_node`, `cms_slot_block`, `content_navigation`, `navigation`, `cms_block`, `cms_page`, and every other file a strategy rewrites rather than appends to. Rewriting only the rows a brief names drops the rest silently: for example, replacing three category links in `navigation_node` also removes the footer's Imprint/GTC/Privacy links, social icons and payment-partner logos unless those rows are carried over, and a green boot does not notice, because the surviving rows import fine. Classify by the file's own type column where it has one (`navigation_node.node_type`: `category`/`cms_page` are retargetable, `external_url`/`link` are **structural keeps carried verbatim**). Detectable: `in-count` must equal `kept + retargeted + dropped`, in writing.
- **Keep the shipped import dependency order — never reorder** (`currency` before `currency-store`, `locale` before `locale-store`, `store`/base tables before every `*-store`, `product-label` before `product-label-store`, all store definitions before the catalog). Reordering breaks it two ways (empty store, `Currency not found`).
- **Price completeness = neither empty nor literal `0`** — a green boot does not catch a priceless store. The check that enforces empty-OR-`0` is **`preflight`'s price check** (across every manifest file in one call); plain `validate required` only catches *empty* cells — a literal `0` passes it, so never rely on `required` alone for prices.
- **Parent-in-store integrity** — a child assigned to a store needs its parent assigned to that store too (`validate refs --composite`; plain `refs` misses the tuple).
- **Glossary = one file per locale** (`filter --where locale=en_US` → `set --value <locale>`), never one shared multi-locale file — checked: `preflight` group `glossaryMultiLocale` flags any `glossary` source with more than one distinct `locale` value (a shared file imports fine, so nothing flags it); **and delete the original interleaved source after splitting** (it still carries every non-project locale's rows).
- **Money is integer minor units everywhere** — `product_price`, `price_product_offer`, `budget`, thresholds, credit limits, discount amounts: `4199000` is €41,990.00. A decimal major-unit value imports, publishes and renders at 1/100 scale with nothing flagging it. Checked: `preflight` group `priceNonInteger`. **And for any money-valued entity that gates checkout** (budgets, thresholds, credit limits) compare its magnitude with the catalogue's price range — `php <CSV> distinct <price file> --column value_gross --plain` beside `php <CSV> read <budget|threshold file>` — and write the comparison into the evidence file. A gate two orders of magnitude below the cheapest product counts as a data defect (for example, budgets an order of magnitude below the catalogue's prices block every order with "exceeds the allocated budget", although each value is individually valid).
- **Navigation & content references survive category/page changes** — `navigation_node` (`node_type` = `category`/`cms_page`/`external_url`/`link`), `content_navigation`, and CMS links reference **category keys and CMS pages by key**, and they are actively imported (the shipped `full_<REGION>.yml` imports `navigation`/`navigation-node`/`content-navigation`). So any strategy that **changes the category tree** (`generate` authors a fresh one) or **drops categories/pages** (`reduce`/`cleanup`) must regenerate or prune these too — otherwise the storefront **main menu points at dead nodes** (empty/broken menu) and a green boot does not catch it (the nodes import fine; the targets just don't exist). These files also carry `.<locale>`/`url.<locale>` columns, so the locale-strip and `spy_url`-uniqueness invariants apply to them as well. Verify node targets resolve: every `navigation_node` `category` node's key ⊆ your `category.csv` keys, every `cms_page` node's key ⊆ your `cms_page.csv`.
- **A new SKU must enter every file its peers are already in.** `manifest-refs`/`refs` prove every key that is present resolves; nothing in them asks which file a SKU is missing from. A product added to `product_abstract`/`_concrete`/`_price`/`_stock`/`_image`/`_abstract_store`/`_abstract_approval_status` but missed in `merchant_product.csv` loses "Sold by" on the PDP and splits into its own shipment; missed in `product_shipment_type.csv` it shows "No shipping types available for this product." — `gate --strict` stays green throughout; the defect shows only on screen. **After every product add:** run `php <VALIDATE> sku-coverage <manifest> [--base dir]` (compares each SKU's file membership against the modal set; reports the files a SKU is missing from that its peers are in — `gate` runs it as a warning, non-gating, so read it, don't wait for exit 2) **and** diff the new SKU's file membership against a shipped product of the same shape (`Grep` the peer SKU across `data/import/**` → the new SKU must hit the same file list).
- **Never compose a category or facet URL from a key.** Slugs are generated from the localized `name`, not `category_key` (`/category-a/sub-category`, not `/shorts-3-4-shorts`) — read them from `spy_url`; facet values come from `product_management_attribute.csv` (`php <CSV> distinct <file> --column value_translations.<locale> --plain`), not from what the attribute is expected to have (an attribute can carry fewer values than declared, or none). Then **fetch each URL and count the rendered product links** — the category page prints `0 Items` regardless of content, so never read that string. A facet with one distinct value (`attr-a=yes` inside an already-attr-a category) or none is a dead filter that looks alive in the CSV; name it in the report.
- **A finished project contains only its own stores/locales/currencies** — applies to every strategy, not just adapt: `generate` and `reduce` reuse shipped demo files wholesale, and those files still carry foreign `.<locale>` columns (e.g. `.de_DE`) and `locale`-row values a project store never uses (reused `cms_block.csv` / `product_label.csv` keep `de_DE` and ship `en_US`+`de_DE` with no project locale at all → silent English fallback). The add half (`duplicate-columns`) and the drop half (`drop-columns --suffix .<locale>` + row-filtering `locale` files) must be symmetric. Mechanical check: `validate preflight <manifest> --locales <project locales>` flags foreign `.<locale>` columns and foreign `locale` rows across every imported file (the `absent` sweep is scoped to `config/`+`src/` and misses `data/import/**`). The one exemption is `glossary.en_US.csv`: it is the translator fallback layer and is always imported (`references/adapt.md` step 1), so its rows are never counted as foreign.
- **Some rows import clean and still do nothing on screen** — `references/storefront-effects.md`, read before touching any of these: a discount clause `shipment-method`/`shipment-carrier` written with a name (both compare ids; `preflight` `discountShipmentByName`), a category added to an existing shop with no `category_store` row of its own (`categoryStoreIncomplete`), `is_in_menu = 0` (hides a category from the menu tree and filter sidebar, not its page), a navigation node switched off with `is_active = 0` (ignored by the importer; use a past `valid_to`, or remove the row and reset), and B2B feature imports (cost centers, budgets) dropped while the feature stays wired.

### Consolidate & clean up (the tail of the data work — runs after adapt's in-place rule ends)
Sequencing: adapt's "do not create a `data/import/<project>/` tree" governs **during** its in-place transform (git is the diff/revert there); this consolidation runs **after** the strategy completes, and moving to one project tree is then correct. This pass runs at the end of every strategy (adapt, generate, clean, reduce), and its purpose is a tree a developer can read. Without it, the imported sources are scattered across several trees (`common/<REGION>/`, `common/<STORE>/`, `common/common/`, a themed `<project>/catalog/`): live generated data sits under `data/import/<project>/` while reused-but-retargeted structural files stay in `common/**`. `define-stores`' `cp -r` single-source seeding also copies the whole canonical dir per store, so each seeded store dir carries **stale demo files the manifest never imports** — a **second, plausible-looking source of truth** (a large `product_price.csv`, demo SKUs, demo merchants/offer-prices) that masks other problems and leaves unclear which data is actually imported.

The active manifest (`full_<REGION>.yml`) is the single source of truth; after this pass the on-disk tree matches it. Any file under the import roots that no active manifest references is removed — unless it's a deliberately-kept CI/fixture bucket (`b2b_common/`, `robot/`), which is noted in the summary.

- **One tree.** Every `source:` the active manifest imports lives under one project tree: `data/import/<project>/{stores/{REGION,STORE…},shared,catalog,cms,stripe}/`. This includes the reused structural files: generate keeps them in place while authoring, and this pass moves the retargeted ones into the project tree and repoints the manifest, leaving `common/**` with nothing the run depends on.
- **Move, never overwrite.** The move onto the project tree refuses an existing target: before each `mv`, confirm the target path does not exist (Glob/Read the target — a hit is a file you already authored there, and `mv` would silently replace it with an emptied demo copy), and compare row counts before/after with `php <CSV> count <source> <target> --plain`; a count that changed is an overwritten file (otherwise only a later duplicate-source check reveals the loss).
- **Rewrite embedded paths, not only the manifest.** `data/import/...` paths also live inside CSV values — `workflow.csv`'s `definition` column (state-machine XML), SSP `files/*.pdf` — so repoint those with `php <CSV> replace <file> --column <col> --search <old prefix> --with <new prefix> --in-place` as well as the manifest `source:` keys. **Never `rm -rf` a legacy tree until `gate --strict` is clean** — its `embeddedPathsMissing` (preflight: a `data/import/...` path inside a cell that does not exist on disk) and `orphan-files` (walks every file type, XML/PDF included, and counts CSV-embedded paths as referenced) are what protect the non-CSV assets; a CSV-only orphan check reads green while a reset still aborts on `Workflow definition file … company_onboarding.xml was not found`. Both checks resolve **relative** embedded paths too (`file.csv`'s `path` column holds `common/common/files/X.pdf`, relative to the import root) against the base dir, `data/import/` and the CSV's own directory — so a referenced PDF is never declared an orphan. If an `orphan-files` finding names an asset a CSV cell mentions, that is a tool defect to report, not a file to delete.
- **Delete stale unreferenced files — no header-only sources.** After the `cp -r` seeding described above, most of each seeded store dir is demo files the manifest never imports; remove those and any leftover demo dirs. Checkable rule: **no manifest source may be header-only** (`preflight` group `headerOnlySources` — a source with 0 data rows). Empty a file to its header only while iterating; remove the file AND its manifest action before the step is `done` (unless the importer requires the entity present — then name that importer in the report). An empty source imports fine, so header-only sources raise no error however many there are. Surface each `rm`/`rm -rf` per the destructive-op gate.
- **One file per entity per scope.** An entity is imported from several sources only when they are meaningfully distinct (per-store, per-locale). Authoring passes (`product_abstract.csv` + `product_abstract_extra.csv`, and the same for concrete/image/stock/price/`_store`) are merged into one file before `done` — an `_extra`-style split inside one directory is the `preflight` group `duplicateEntitySources` finding.
- **Close-out = four artifacts written to `.ai-dev/evidence/project-data.md` (the file the three-line step report cites), not one green gate.** Every check in the suite is referential or structural, never semantic — a manifest can be 100% internally consistent and still be the demo's shop. `gate --strict` stays green while the manifest still imports, for example, the Self-Service-Portal **assets** and models, the demo's service points, demo-merchant warehouses assigned to the project store, and demo sales orders the interview marked `drop`. Checks do not replace reading the data; the inventory step requires that read. Before `done`:
  1. **`php <VALIDATE> gate --strict`** — `paths` + `preflight` + `manifest-refs` + `threshold-glossary` + `duplicate-keys` + `cms-block-store` (gating), `orphan-files` (gates only with `--strict`), and six warning-only checks in one call; exit `0` clean, `1` warnings only, `2` gating finding (`--strict` also gates `orphan-files`). Record command and output. Proves the tree equals the manifest — nothing more.
  2. **`php <VALIDATE> inventory <manifest> [--base dir] [--plain]`** — one line per manifest source: `data_entity`, source path, row count, a sample of its free-text values. Record it and **classify every line** `project` / `generic-plumbing` / `demo-leftover`, in writing. Any `demo-leftover` is a source to remove (file AND manifest action) before `done`. Read the sample cells — that is where "Example Asset A" shows up.
  3. **Diff the interview's `data.existing_data` dispositions against the final manifest** — for each entity the interview recorded (`keep`/`rebuild`/`drop` — `rebuild` means the entity is re-authored, so the manifest must point at the new source, not the shipped one), find its manifest action. An entity recorded `drop` that still has a manifest action is a finding (for example, a `sales-order` action under a recorded `sales_order: drop`).
  4. **A non-empty `## Deviations` block carries a decision per line** — for each deviation, either the developer's recorded answer (what you asked, what they said) or an explicit `not asked` note. A listed deviation from the state file's own values has no approval until the developer's answer is recorded next to it. `Deviations: none` stays the normal case (contract: `../project-starter-wizard/SKILL.md` §3).
  Do not set the `project-data` step to `done` in `.ai-dev/project-setup.md` while `gate --strict` fails, and do not run `reset`/`clean-data`/`up` while `gate` fails; a written claim of verification does not replace a passing gate run. A green gate alone does not close project-data either: the classified inventory and the other close-out artifacts are also required.
