# Project Starter — Wizard

You turn an **unmodified** clone of a Spryker b2b / b2b-marketplace demoshop into the customer's project. The clone may already be booted — what matters is that nobody has customized it yet. You own the conversation and the flow; the transformation work is done by the other skills (which drive the `spryker-import-tools` tools with parameters — never hardcode file lists).

Work only from real files and real command output. Never assume Spryker specifics from memory — inspect the clone.

In a demo run, the person this skill calls "the developer" is usually a demo preparer, not an engineer (`demo-prep-wizard` → "Who runs this"): plain words, your recommended option first, and every technical judgement yours.

## Communication (applies to EVERY message — the developer will not read walls of text)

Keep output **short**: in a long status message, a required action or a blocker is easily missed. Five hard rules:

1. **A required human action is the FIRST thing in the message, alone, unmissable.** Lead with a single `⚠ ACTION NEEDED:` line and the exact command — before any status, table, or summary. A prerequisite buried under a validation table or a "✅ N of M complete" header reads as status, not a request, and the run stalls on an unread ask. Never phrase a prerequisite as "whenever" or "I'll tell you when I get there."
2. **Issues/blockers are HIGHLIGHTED, not narrated.** Surface a problem as its own short, flagged line (`⚠`/`❌`) — never mixed into a paragraph of prose. One glance should tell the developer: action needed? issue? or just progress?
3. **Default to terse.** Report the outcome, not the play-by-play. A finished step = one line. Save detail for when it's asked, or for the skill-improvement log (which is dev scaffolding, not something the developer reads for actions). Verbose reasoning belongs in your own thinking, not the output.
4. **Close-out contract — mode-dependent, and it never manufactures a stop:**
   - **Before the first autonomous turn, read [references/autonomous-runs.md](references/autonomous-runs.md)** — how a stop is judged, why a denied sub-agent call is not a cancelled instruction, what every sub-agent prompt must carry, and what "done" requires.
   - **`autonomous`:** a turn that needs nothing from the developer does **not** hand control back at all — it continues in the same message (the step-completion protocol, §3). Never ask them to say "continue"; that is not autonomous. Control returns **only** for a genuinely blocking human action, and then the turn ends with `⚠ NEEDS YOU:` followed by **numbered** concrete actions — each one an **exact command** or a **yes/no**, each naming **what declining costs** — e.g. "1. Run `sudo … >> /etc/hosts` — declining leaves the browser ACs BLOCKED; the server-side checks still run."
   - **`collaborative`:** a turn that returns control ends with EXACTLY ONE of that same `⚠ NEEDS YOU:` line or `✅ NEEDS NOTHING — say "continue".`
   **Banned as closing lines in both modes:** "Ready when you are", "Shall I continue?", "Let me know how you'd like to proceed", and an unprompted options menu. Failure signature: the last line of a turn is a pleasantry, a recap, or a question the developer never asked for — that turn has handed back control without saying what it needs, and the run stalls.
5. **A developer question is answered, not acted on.** Answer it, state what you *would* change and what that costs, then wait. This is **not** a mode violation: autonomous governs unprompted decision points between steps and says nothing about how to respond when the developer speaks. A criticism inside a question ("why is it called `shared`?", "is this file even imported?") is still a question. **Never reorganise a layout or tree the developer did not ask to change, including to justify a name**: moving an import tree to answer a naming question leaves manifest sources dangling, turns a green `gate --strict` red, and requires a `git mv` revert plus a re-gate. **Check:** if the developer's last message is a question, the turn contains no mutating tool call (a request phrased as "can you …?" counts as an instruction).

These rules decide whether an unattended run completes or waits on an unread ask.

## 0. Pre-flight (stop if any fails)

- **Flavor:** confirm this is b2b or b2b-marketplace (check `composer.json` name/packages). Reject anything else.
- **Still an unmodified demoshop — the question that decides this gate.** This run deletes CI files, region dirs, catalog rows and (at boot) re-imports data. On an untouched demoshop that destroys nothing. On a project someone has already customized it destroys their work. So the gate is **"has this been customized into a project?"** — not "has it been booted" and not "is the tree clean".
  - **Not blockers — say so and continue:** a **booted** clone (a fresh demoshop someone ran `docker/sdk up` on is still an unmodified demoshop); the **AI Dev SDK onboarding delta** (tracked `composer.json` / `composer.lock` / `ConsoleDependencyProvider.php` plus untracked `.ai-dev/`, `CLAUDE.md`, `.claude/`); untracked tooling (`.cursor/`, `.windsurf*`, `.github/agents|skills/`, `.mcp.json`, `AGENTS.md`, editor configs). **Never require a commit** (suggesting one is fine).
  - **Blockers — the clone is already a project.** Any of: tracked modifications under `src/`, `data/import/`, `config/` beyond the SDK delta above; a **customer's own namespace already registered** — a namespace in `PROJECT_NAMESPACES` that the branch does not ship (a demo branch legitimately ships its own, e.g. `Demo` ahead of `Pyz`; that is not a blocker); stores/locales already differing from the shipped set; or an untracked pile of data/CSV/patch files. Post-boot, also: **real business data** (orders/customers beyond the demo seed). **Ask, don't guess** when the shape is ambiguous — "is this still the demoshop, or your project?" is one question; ask it whenever the evidence is unclear.
  - **Booted + unmodified → proceed, and say what it costs:** the file transformations only reach the shop through a re-import, so the run will need `docker/sdk clean-data` + a re-boot. Announce that blast radius (it wipes demo data only), then continue — during first setup this is normal, not a gated destructive action.
  - **If `.ai-dev/project-setup.md` already exists, this is an earlier run of this wizard — do NOT stop; go straight to the Resume section** (continue from the first not-`done` step; Resume decides from `answers_confirmed_at` whether the interview is skipped or restarted).
  - A confirmed already-customized project is the hard stop, and it must hand over the **"Return to fresh" recipe (§ below)**, never a bare refusal.
- **Un-booted, no volume collision, and a host that can finish the boot.** Attribute every container, volume or env value to its owner before concluding from it. A Docker VOLUME collision on the resolved namespace is a **BLOCKER** — offer the ranked fix hierarchy, never force a rename. Then probe Docker and PHP, ports, composer auth and connectivity (the GitHub rate limit kills the in-container install), disk, the platform, the git remote, and a `docker/sdk` checked out at the pinned version (never `master`). Each check, its failure signature and its fix: **[references/preflight.md](references/preflight.md)** — run every one of them.
- **Classify every pre-flight finding into three buckets** — **stop** (not fresh/wrong flavor), **fix-myself** (clone the SDK, php-docker fallback), or **developer-must-do-before-step-N** (start Docker/OrbStack; add the allowlist). Anything in the third bucket becomes a single up-front ask at the top of the interview, per the **Communication** rules (§ top) — surfaced once, unmissable, not a parenthetical. **The bucket is spoken TWICE, and both times are mandatory:** (1) the up-front ask at the top of the interview, and (2) again as an **exact-command checklist** in the `⚠ NEEDS YOU:` close-out of the step report **immediately preceding the step that consumes it**. *A prerequisite discovered at minute 0 for a step 40 minutes away is still an up-front ask.* Failure signature: the bucket exists in `.ai-dev/project-setup.md` and the developer asks "is there anything you need from me?" — that question means neither speaking happened.
- **Host names — check `/etc/hosts` now, before any question.** Read the host names in the clone's `deploy.dev.yml` and look each one up in `/etc/hosts` (a read — no `sudo`). Record which are present. A demo keeps the domain and region `deploy.dev.yml` already has, so these are exactly the names it will use — a machine that has run this demoshop before usually needs nothing. Any name missing is raised once, up front, with the exact command (detail: `references/preflight.md`) — never as a discovery after the boot.
- **Permission allowlist — recommend, never install.** Name the exact commands from the plugin's `hooks/settings.example.json`, and never claim the run is unattended without it (detail: `references/preflight.md`).
- **Inventory (needed for collision checks and the CI section of the interview):** list the shipped regions and stores — scan `deploy.*.yml` (region keys), `data/import/local/full_*.yml`, `config/install/*/`. Record what already exists (the demoshop ships an EU region **and** a dormant US region). Also scan `.github/workflows/` for the CI jobs/suites actually present — interview §8 offers only what was found.
- **Gate baseline — this must happen HERE, because this is the last moment the clone is untouched.** On the pristine clone run `php <VALIDATE> gate --save .ai-dev/gate-baseline.json` (`<VALIDATE>` = `<plugin>/skills/spryker-import-tools/scripts/validate.php`, resolved in reasoning, never a shell variable; no other arguments — it discovers the booted region's manifest, the install recipe's vendor configs and the project locales itself). `--save` writes the report **after** the checks ran and **refuses** to save one that could not run them (`baselineSafe: false`). **Never `gate > .ai-dev/gate-baseline.json`, and never the Write tool from a pasted body either — because the result would be incorrect:** the shell creates and truncates the redirect target *before* `validate.php` starts; the gate then auto-discovers that empty file as its baseline, pushes `cannot read baseline` errors, aborts its content checks, and serialises `findings: []` — a falsely clean report of a state that never existed. The empty baseline raises nothing during the interview and then blocks the step-8 boot with every shipped quirk unsuppressed. (A redirect also prompts every time; that is secondary.) Every later `gate` in the run picks the saved file up automatically, so only **NEW** findings gate — across preflight, `manifest-refs` and `threshold-glossary` alike. A `.ai-dev/preflight-baseline.json` is also honoured, for the preflight groups only.
  - **Check, immediately after saving — Read the file:** `baselineSafe: true`, `errors: []`, and findings in at least one group. **A baseline reporting 0 findings on an unmodified demoshop is always wrong** — the shipped clone is not gate-clean on any group (URL duplicates, `tax_set_name` mismatches, dangling manifest refs). All-empty = the gate did not run; fix the invocation and re-run before touching anything.
  - Failure signature: `boot-and-verify` §1 triaging the shipped demoshop's own quirks as damage this run caused — that is a missing or poisoned baseline, not a data defect, and it leads to a fix on data that was never yours.

If the clone is **already a customized project** (per the demoshop gate above) **and there is no `.ai-dev/project-setup.md`**, **stop and hand over the "Return to fresh" recipe** (§ Abort, change an answer, return to fresh) — do not half-apply, and do not leave the developer with a bare refusal. A booted-but-unmodified demoshop is NOT this case. (An existing state file → Resume, per above.)

## 1. Collect the answers — questionnaire fast-path, or interview

**A demo takes neither route below:** with `purpose: demo`, run the **demo fast path** in `references/interview.md` — at most five plain questions and a confirmation, everything technical derived. **Run from `demo-prep-wizard`** (`.ai-dev/demo-prep.md` carries `up_front_confirmed_at`), it **asks nothing and shows no confirmation**: that one sitting already asked and confirmed the set, so the state file takes its values from `demo-prep.md` with `answers_source: demo-prep` (interview.md → "Run from `demo-prep-wizard`").

Otherwise the nine decisions can arrive **two ways**, and the fast-path is the default preference:

- **A filled questionnaire (`references/questionnaire.md`) — no interview.** It is the canonical
  fillable question list (groups P/N/S/T/D/C/L/Q + run-config R, every question carrying its default
  inline). **Minimum viable set: `P1` (project name), `R1` (mode), `R2` (hard-stop ack)** — with those
  three the run proceeds on shipped defaults for everything else. It counts as supplied **only when the
  answers are keyed by question ID** (a path, pasted text, or a `yaml` block with `P1:`/`R1:`… keys).
- **A live interview** — the batched AskUserQuestion path, in every other case. **A prose brief
  ("Store United Kingdom, English, EUR, brand red, replace the catalogue…") does not count as a questionnaire:** it
  pre-fills the candidates you offer, and every section is still asked and the whole set confirmed.
  Reading a brief as a questionnaire records unasked values as agreed.

**Read `references/interview.md` BEFORE asking the first question.** It carries the collection rules
that decide between those paths (**Rule 0** — filled/partial/missing detection and the parsing rules;
**Rule 1** — offer "fill it yourself vs interview me"), the AskUserQuestion mechanics (structured
options with the default first, pre-computed candidates for free-text values, batched sections), and the **nine-section decision catalog**: identity, namespace,
services/applications, stores + region, demo-data mode, catalog scope, localization, CI, and run mode.

Three rules bind both paths:

- **A blank is a default, not a question — on a QUESTIONNAIRE.** Every question except `P1`/`R1`/`R2`
  has a working default. Under `run_mode: autonomous` a questionnaire blank is resolved to that default
  — or, where there's a genuine fork, **decided and logged to `.ai-dev/decision-log.md`** — never
  asked. Under `collaborative` the blanks are asked. On an autonomous run, blanks are never turned back
  into questions. **This rule never applies to the interview path:** autonomy governs what happens
  *after* the answers are agreed; it is not a licence to skip asking them.
- **`R1` is the one answer with no safe default.** If a questionnaire arrives without it, ask that one
  question and nothing else — it decides whether every other blank becomes a question or a decision.
  (Not on the `demo-prep` path: there `run_mode` is copied from `demo-prep.md`, never asked.)
- **A questionnaire skips questions, never checks.** Pre-flight (§0) runs in full either way, and its
  developer-must-do findings are still surfaced as `⚠ ACTION NEEDED`. Re-run the namespace/volume
  collision check as soon as `P1` is known.

Keep the two files in sync: `questionnaire.md` is the question bank, `interview.md` is how to collect
it. A decision added to one must be added to the other.

## Two rules that bind EVERY edit of the run (interview through execution)

**Surgical edits only — never tidy adjacent config.** When editing a shipped file (deploy.dev.yml, config, YAML, recipes), change **only** the exact keys the current step owns; do not reorganise, reformat, "clean up", or move neighbouring blocks you were not asked to touch. Everything else stays byte-for-byte as shipped. (For example, a step that owns `docker.testing.region` changes that key only; the adjacent `docker.mount.mutagen` block stays as shipped, because deleting it moves macOS to `native` mounts and cripples the Mac dev env.)

**Environment limits are NOT project defects.** A failure caused by *your run environment* — no TTY for an interactive command, the 10-minute tool timeout, shell word-splitting (zsh vs bash), a detached/background process, `/dev/null` stdin — is a limit of how *you* are running, not a bug in the project. **Never diagnose a sandbox limit as a project problem, and never edit project files to accommodate it.** When a command needs a real terminal or exceeds the tool cap (notably `docker/sdk up`), hand it to the developer to run — do not fake a TTY, background it to dodge the cap, or "fix" the project to make it run headless. If unsure whether a failure is the project or the environment, assume the environment and surface it, rather than mutating the project.

## 2. Confirm & write state

Summarise every answer. Get explicit confirmation of the **whole** resolved answer set (on the `demo-prep` path that confirmation already happened in `demo-prep-wizard` — below). Then write `.ai-dev/project-setup.md` **exactly per the template at the end of `references/interview.md`** — the frontmatter (project / namespace / services / stores / data / reduce_catalog / localize) plus the **Steps table** that §3 and Resume operate on.

**The confirmation is a hard precondition.** Whatever `answers_source` says, with one exception, write `.ai-dev/project-setup.md` for the first time only when the transcript shows **(a)** a questionnaire the developer supplied (ID-tagged answer lines such as `P1: …`) **or** the interview asked through `AskUserQuestion`, **and (b)** a confirmation question (an `AskUserQuestion` that asks the developer to confirm) after the answers were collected. So on every path but `demo-prep` the last thing before writing state is: one `AskUserQuestion` that lists every resolved value and asks the developer to confirm the set. A value the developer never stated is a **question, not a default** — `answers_source: interview` with invented answers (for example, a few batched rounds followed by a dozen answers recorded as agreed, `P1` and `R2` among them) is the failure this precondition prevents. **Check coverage before writing:** on an interview run `answers_defaulted` must be empty (there are no blanks, only unasked questions), and every `[REQUIRED]` ID (`P1`, `R1`, `R2`) must appear in a question you actually asked. Failure signature: an `answers_defaulted` list longer than the number of questions asked. Questionnaire runs (`answers_source: questionnaire`) are exempt: list every taken default in `answers_defaulted`. **The one exception — `answers_source: demo-prep`:** run from `demo-prep-wizard`, the wizard asks nothing and asks no confirm question; it writes the state file when `.ai-dev/demo-prep.md` carries `up_front_confirmed_at`, which is copied into `answers_confirmed_at` (with `run_mode`, `up_front.reference_sites` → `project.reference_sites`, `audience` → `project.audience`, and D4 derived from `up_front.sample_products` — interview.md → "Run from `demo-prep-wizard`").

**Two consistency refusals at state-write time** (refuse to write; ask the one question that resolves it):
- **Wording vs `localize`.** A brief or answer that names specific UI wording — a register or variant of the same language (`en_US → en_GB`, cart → basket, catalog → catalogue) or a different language — with `localize: { locales: [] }` is self-contradictory: that wording is glossary work `translate-content` owns (interview §7 / `L1`), and recording it elsewhere as a note (`cart_wording: basket`) while `L1` defaults to `no` silently drops the regional-English glossary review.
- **`data.existing_data` present whenever it is owed.** If `data.mode` is `clean`/`generate`/a dataset, or `reduce_catalog` removes branches, the state file carries the interview-§5 `D4` disposition table (derived from `php <VALIDATE> inventory`, never abstract) — a catalog replacement with no decision on quotes, shopping lists, product lists, orders, customers, CMS and navigation ships B2B screens that import clean and 404 at demo time.

In the same pass, create `.ai-dev/run.log` with the interview summary as its first line (see §3 → Run logging). Every step from here on appends to it.

## 3. Run the steps in order

**Run mode governs execution cadence between steps 1–9 while the developer has not spoken. It never governs answer collection (§1–§2 — an interview has no blanks, only unasked questions), and it never governs how to respond to a developer question (Communication rule 5 — answer, don't act).**

**Run mode — questionnaire `R1` / interview §9 (`run_mode: autonomous | collaborative` in the state file; `supervised` is an accepted alias for `collaborative`).** It governs only how control is handed back *between* decisions; it changes nothing about WHAT each step does, and it never relaxes the hard-stops below.

- **Autonomous** — run steps 1–9 as **one continuous pass**; after a non-gated step completes, proceed to the next in the same turn. At any **reversible, in-project decision point** — which value to pick, how to resolve a dangling reference, a strategy fork the questionnaire didn't pin down, **or a questionnaire question left blank** — choose the best option, **record it in the decision log** (below), and keep going. The default is continue. **Asking a configuration question mid-run is a mode violation**: the answers were collected up front precisely so this pass needs none.
  - **`done` is a claim backed by evidence.** Before flipping `define-stores`, `project-data`, `boot-and-verify`, `rehearsal` or `demo-run-sheet` to `done` in the Steps table, run `php <VALIDATE> gate` (`--strict` for project-data, boot-and-verify and rehearsal) and write `done` only when it passes (with a baseline, only new findings count). `boot-and-verify → done` also requires `.ai-dev/verifier-report.md` (the `spryker-verifier` verdict, §4c — the executor's own probes are not a substitute), and a step that edited a theme template or stylesheet requires a current `.ai-dev/design-acceptance.md`. Write the gate command and its literal output to the step's evidence file (`.ai-dev/evidence/<step>.md`, with Write/Edit) *before* editing the row, and cite that path in the step report. A step whose gate is red is `in-progress (<what is left>)`, never `done`.
  - **Gate before every rebuild or import.** Before `docker/sdk reset|clean-data|up` or `console data:import`, run `php <VALIDATE> gate`; with a gate baseline, a new gating finding stops the command until the data is fixed; without a baseline, a gating finding stops a rebuild (`reset`/`clean-data`/`up`) and `data:import` proceeds — capture the baseline on the untouched clone first.
  - **Count rebuilds yourself.** Every step report that involved a `reset`/`clean-data`/`up` states the project's rebuild count so far (per project, across steps) and why each rebuild was necessary — above two is itself the failure signature. Before the third rebuild, write `rebuild #N: <why rung 1 cannot show it>` to the decision log, then continue (not a hard stop).
  - **`## Deviations` — mandatory in every step report.** One line per named command the skill prescribed and you did NOT run: the command, the substitute, the reason. `Deviations: none` is the normal case and fits the three-line report; a non-empty section is a **finding the developer sees now**, while they can still object — not at the end of the run. Failure signature: a run whose reports all say `none` while the transcript shows a `>` redirect, a heredoc, or a skipped `spryker-verifier` — exactly the deviations this section exists to surface.
  - **Step-completion protocol — three acts, ONE message, in this order:** (1) update the step's row in `.ai-dev/project-setup.md`; (2) append the `| END` line to `.ai-dev/run.log`; (3) **invoke the next step's `Skill` call in that same message.** Failure signature: a turn whose last tool call was the `Edit` of `run.log` — the protocol stopped at act 2 and the run is now stalled.
  - **Never end a message with "Continuing to `<step>`" or any other forward-looking announcement.** If you have written that sentence, **the next skill's tool call belongs in the same message.** The *shape* of the message ends the turn: a message shaped like a finished deliverable hands back control.
  - **The step report is a log line — at most 3 lines:** outcome / gates hit / deferred, `Deviations: none` (or the list), then the mandatory `Next step needs from you:` line (below). Failure signature: a step report carrying a table, a "✅ N of M complete" header, or more than ~80 words.
  - **Evidence lives in a file, not in the message.** Everything a step is asked to paste — gate output, the classified `inventory`, the dispositions diff, the rebuild count's reasons — goes to `.ai-dev/evidence/<step>.md` (Write/Edit, appended per pass), and the report's gates line cites that path (`gate --strict ok — .ai-dev/evidence/project-data.md`). The cap keeps the message readable; the file keeps the proof auditable after the conversation is gone. A step report that cites no evidence file for a step that ran a named check is the failure signature.
  - **`Next step needs from you:`** — the last line of every step report, resolved for **step N+1** specifically (the exact command, or the yes/no it will gate on), or the literal word `nothing`. Never "I'll tell you when I get there".
  - **A question whose options reduce to {continue, stop} is a mode violation, not a decision point.** The default is continue; a real decision point offers **substantive alternatives** (which value, which file, which strategy). Failure signature: an `AskUserQuestion` whose options are "keep going" / "pause and review", including after the developer pre-approved the run. It is neither a step report nor a configuration question, yet it hands back control in the same way.
- **Collaborative** — do **not** silently stop, and do **not** run straight through. At each **step boundary**, end the turn with a one-line result and the Communication rule 4 close-out — `✅ NEEDS NOTHING — say "continue".` (naming the next step in the result line), or `⚠ NEEDS YOU:` when step N+1 has a prerequisite — and wait. A closing question ("Continue to `<next step>`?") is the banned "Shall I continue?" shape: it hands back control without saying what is needed. At any **decision point**, surface it as a question with the options and your recommendation (`AskUserQuestion`) and wait — never decide silently, never halt without a question. Record the answers in the decision log too, so a resume keeps the rationale.

**Hard-stops — control returns to the developer in BOTH modes** (autonomy never overrides these; collaborative asks anyway). These are what questionnaire `R2` acknowledges — a filled questionnaire is never a promise of an uninterrupted run:
- **(a) a `⚠ ACTION NEEDED` prerequisite** — something only the developer can do (start Docker/OrbStack, add the `/etc/hosts` line, supply a token). Surface it per the Communication rules and wait.
- **(b) an IRRECOVERABLE action on real data — gated in BOTH modes.** The destructive-operation policy is the one in `spryker-import-tools` → Invocation & command discipline: always preview and announce in one plain line; ask only when real data git cannot restore is at stake and the confirmed answer set did not already decide it. So during first setup (un-booted, or iterating on the first boot), on a demo clone, and for trusted rebuilds, `reset` / `clean-data` are **normal operations**: announce the blast radius in one line and proceed — there is no customer data to lose. The gate is **recoverability, not the word "delete"**: if `git checkout -- <paths>` restores the pre-action state, the action is a recoverable edit and needs no gate. What still returns control: `sudo`, publishing outside the clone, any DB/volume drop (`reset`/`clean-data`, `docker volume rm`) or data deletion on a project that already carries real data, and **deleting files git cannot restore** (`git clean`, or `rm` of anything the diff doesn't show as tracked — delete only files git can restore or that this run created; leave any other file and list it in the final report for the developer). In-place row/column removal (`csv delete` / `filter --in-place` / `drop-columns --in-place`) does **NOT** prompt at the OS level, so this policy — not a shell prompt — is what covers it: preview, present the concrete blast radius (the file list, the row/column count, or what the drop wipes), and ask where the policy says to ask. **Autonomous performs and logs recoverable actions on its own** (value transforms, added columns, file writes, and deletions that are recoverable per the rule below) **but never an irrecoverable one unattended.**
  - **Before treating a deletion as recoverable under this carve-out, read [references/hard-stops.md](references/hard-stops.md):** when a file deletion and when a DB drop counts as recoverable, batching multi-pass deletions into ONE gate, the proof a decision-log entry must carry, and why catalog scope is settled at interview time and is never a mid-run gate.
- **(c) a step failure** — stop with guidance, per the failure rule below.
- **Standing approval** — the developer may pre-approve a bounded **class** of actions; its scope, recording and expiry are in [references/hard-stops.md](references/hard-stops.md). Never invent one.

**Decision log (`.ai-dev/decision-log.md`) — the autonomous run's audit trail (and collaborative's answer record).** Append one terse entry per decision: the step, what was decided, why (the evidence), the alternatives rejected, and **how to reverse it** (the git path, or the specific file/rows). **Questionnaire blanks are accounted for in exactly one of two places — never both.** A blank that resolved to its **documented default** (S2 → keep all dev services) is recorded *only* as an ID in the state file's `answers_defaulted` list; it does NOT get a decision-log entry, because a mechanical default carries no rationale and listing all ~15 of them here would bury the real decisions. A blank that required a **genuine fork** — no documented default, or the default doesn't fit the answers (e.g. a region token whose literal candidate collides with a shipped one) — gets a full entry here *and* is listed in the run.log's `decided=[…]`. If you can point at the questionnaire text that names the value, it's a default; if you had to reason, it's a decision. Like the skill-improvement log it is dev scaffolding, not developer-facing status — it lets a reversible but wrong autonomous call be found and reverted instead of leaving a silently broken shop. The developer reads it to audit or override the run's choices after the fact.

### Run logging — `.ai-dev/run.log`

The run's timeline: what ran, in what order, and how each step ended. Create it in §2, in the same pass as the state file. One line per step boundary (`| START`, `| END <status>`, `| RESUME`), written with Write/Edit as you go — never reconstructed at the end, and never a step logged green that wasn't. Line format and every line type: **[references/run-logging.md](references/run-logging.md)** — read it before writing the first line.

### The steps
**Before step 1, confirm `.ai-dev/gate-baseline.json` exists and is sound** — Read it: `baselineSafe: true`, `errors: []`, findings in at least one group (captured in §0, on the pristine clone; a `preflight-baseline.json` is also acceptable). An all-empty or `baselineSafe: false` file is a poisoned baseline (§0) and counts as missing. If it is missing, say so and do NOT capture one now — the clone is no longer untouched, and a late "baseline" records this run's own damage as shipped state. Re-check the execution pre-flight (still fresh/un-booted — the SDK onboarding delta stays tolerated) before writing anything. Then run, updating each step's status in the state file as you go. **Long steps record intra-step progress in the `note` column** — set the step to `in-progress` and update the note after each major pass (e.g. `in-progress: locales done, currencies pending, strip not started`), so an interrupted run can resume precisely instead of blindly re-running (most passes are idempotent; the deletion passes are NOT — a blind re-run of those is the thing the note prevents).

1. **project-ci-generator** — turn the repo's inherited product/vendor CI (`.github/workflows/ci.yml`) into a single lean project pipeline.
   - Runs **first and pre-boot** (pure CI-file work — no boot, namespace, or data needed), so it's **unmissable** rather than an end-of-run afterthought.
   - **The decisions were already collected in interview §8 (the `ci:` block)** — this step executes that plan against the discovered CI; it does NOT re-run the questionnaire. **It deletes CI files** — tracked files git restores, behind the backup tag `project-ci-generator` takes, and the confirmed `ci:` block already decided which ones go. So the destructive-operation policy (`spryker-import-tools` → Invocation & command discipline) applies: announce the concrete file list derived from the plan in one line, then proceed. The wizard never silently skips the step. If there's no CI to transform, say so and move on.
   - **Also owned by this step — read [references/steps.md](references/steps.md) §1 before running it:** the `ci.keep_suites` decision is the robot/acceptance-fixture lane decision (derived, never asked); removing a dropped suite's whole footprint; and the bare-runner store trap for green CI on a non-`DE`/`AT`/`US` store.
2. **configure-codebase** — namespace registration + FE/test wiring, incl. the **PHP/codeception** test infrastructure (skip if `namespace.mode: keep-shipped` — the option is named for what it does: keep whatever namespace the clone ships, which is `Pyz` on a stock demoshop and may be something else on a partner clone; render the resolved value in the confirmation, e.g. "keep the shipped namespace, which here is `Demo`"). `keep-pyz` is also accepted as an alias.
3. **brand-project (identity only)** — composer/README/docker-namespace/domain, and drop the logo asset into place. Its **theming half is post-boot** (colours, logo wiring, BO/MP ymls, `configuration:sync`, rendered verification) — it needs `vendor/` + an initialized DB, so it runs in step 8, same split as configure-codebase.
4. **configure-services** — optional dev services + app enable/disable into `deploy.dev.yml` (infra engines are fixed; they are never swapped).
5. **define-stores** — region, store-definition CSVs + the store-definition manifest (`store_<REGION>.yml`), literal sweep. The catalog import-config assembly belongs to `project-data` (step 6), not here. **Skip if `data.mode = leave`** (demo stores kept unchanged → nothing to redefine).
6. **project-data** — the data step; it picks the strategy by `data.mode` (each assembles its own import config):
   - **adapt** — reshape the demo catalog to the project stores/locales/currencies.
   - **clean** — build the minimal bootable import (no demo catalog).
   - **generate** — author a themed catalog in the project's vertical.
   - **`leave`** — skip entirely; the shipped demo data stands (rebrand-only path).
   Then, **adapt only** and only if `reduce_catalog` ≠ `keep: all`, run the **reduce** strategy to trim the demo catalog to the project's subset **pre-boot** (no reset), before boot. N/A to clean/generate/leave.
   - **`generate` reads `data.source`:** `authored` is the interactive, experimental authoring path (not hands-off); `dataset: <path>` builds the catalog from the supplied files and `data.dataset_mapping`, with no authoring — safe for autonomous. The not-hands-off warning belongs to `authored` only.
   - **Before `done`, three derived checks — never remembered lists:** (1) `php <VALIDATE> inventory <manifest>` — write its output to `.ai-dev/evidence/project-data.md` (every manifest source with entity, row count, text sample) and classify each source **project / generic-plumbing / demo-leftover**; a `demo-leftover` in the final manifest is a defect. (2) Diff `data.existing_data` (interview D4) against that inventory: every group marked `drop` is absent, every `keep`/`rebuild` group's sources are present and reference only SKUs/categories the final catalog contains (`product-refs`, `refs --ref-file`). (3) `refs --ref-file` for **every parent set the project replaced — the list comes from `inventory`/the manifest** (every source that moved into the project tree), not from what you happen to recall; parents that are easy to miss include demo-merchant warehouses and stale `cms_slot_block` category keys, and each one missed aborts the import.
7. **cypress-migration** — the **E2E (Cypress) half of test infrastructure**: removes the inherited Spryker demo suites' **Composer packages** (`cypress-tests`/`robotframework-suite-tests`), vendors the proven `tests/cypress-boilerplate/`, wires Cypress CI, and generates the companion `cypress-tests` skill. (The inherited suites' CI jobs + deploy/install-pipeline/fixture configs are removed by `project-ci-generator` at step 1, not here — see step 1.) Always run it (the orchestration boundary lives here, not in it). **Tooling note:** it uses its own conventions (`python3 -c "import yaml…"`, `rsync`, `grep … | wc -l`, `cd … && npm ci`) that don't follow this plugin's one-simple-command rule — so **expect its commands to prompt**. That is an open conformance item, not a blocker (the commands work); the conforming route is the grep-pre-boot / `symfony/yaml`-post-boot YAML route ci-generator §5 uses. **Runs last of the pre-boot steps — deliberately, because it depends on the output of the ones before it:**
   - **Ordering, pre-/post-boot split and gating — [references/steps.md](references/steps.md) §7:** it runs after steps 1, 3, 4, 5 and 6 because each changes what it builds from; its file work is pre-boot and its tooling proofs post-boot; it deletes packages and CI files, so the destructive-op gate applies even in autonomous mode.

> **Ordering gate — before starting step 8, every one of steps 1–7 must be `done` or explicitly `skipped` in the state-file Steps table.** Read the table and confirm it; if any pre-boot step is still `pending`/`in-progress`, finish it first. Note `cypress-migration` (7) in particular: its proof (`cy:run`) is post-boot, but its file work (composer removal, vendoring, CI, companion skill) is pre-boot, so it must complete before the boot. This is what keeps the §3 continuous-run directive from turning "keep going" into "skip ahead".

8. **boot-and-verify** — validate everything, first boot, per-store verification, and the **post-boot passes (mandatory, on the checklist alongside the endpoint checks):** brand-project's theming half (colours, logo wiring, BO/MP ymls, `configuration:sync`, rendered colour/logo gate), the codeception seed's green `codecept run` (configure-codebase), and cypress-migration's `cy:run` smoke. The authoritative PASS/FAIL comes from the independent `spryker-verifier` sub-agent (shipped in this plugin's `agents/`, driven by the bundled `spryker-qa-coverage`/`spryker-runtime` skills), not the executor's self-assessment (boot-and-verify §4c). Its browser ACs need `/etc/hosts`, surfaced as a `⚠ ACTION NEEDED` prerequisite before the gate; if declined, the server-side checks (`curl --resolve`) still stand and the step completes in a **terminal** state — `done (browser ACs BLOCKED — /etc/hosts declined)` — so the run finishes rather than parking forever (never a permanent `in-progress`). This is the one prerequisite whose decline is terminal, not a hard-stop wait — spell that out so an autonomous run doesn't stall on it.
9. **translate-content** (optional — only if `localize.locales` is non-empty) — translate the chosen locale(s) after a green boot; default is skip (English copies stand). Never blocks setup.

On any step failure: **stop with guidance**, leave the state file recording where it stopped, and log the failure line in `.ai-dev/run.log` (the step, the signature, the matched `pitfalls.md` entry if there is one) before you hand back — when a run stops, its timeline is the first thing read. Do not proceed past a failed step.

**Triage reference — the Known-traps catalog (`references/pitfalls.md`).** It collects every known failure signature across the whole run (cross-cutting + per-step: volume/namespace collision, mutagen-down, boot aborts, "green but empty" post-boot, read-model recovery) as *signature → cause → fix*. On any failure or suspicious-but-green signal, match it there before diagnosing from scratch. Each step-skill also carries the one-line trigger inline for standalone use; this catalog is the shared depth and the single home for the cross-cutting traps.

When blocked on a human action, apply the **Communication** rules at the top: lead with the single `⚠ ACTION NEEDED:` line and exact command, alone, above any status; never bury it, never say "whenever".

## Resume

If invoked with an existing `.ai-dev/project-setup.md`, skip the interview and continue from the first step whose status is not `done` or `skipped` (covers the `/etc/hosts` and boot interruptions). **Append a `RESUME` line to `.ai-dev/run.log`** (never start a new log — one run, one timeline) recording which step you are resuming from and the progress note you resumed against. **Re-read `run_mode` from the state file first** — a resumed run honours the mode chosen at collection time (autonomous vs collaborative), and any `## Required follow-ups` recorded there. **Resume from the frontmatter ONLY when it records a confirmation timestamp (`answers_confirmed_at`).** With one present, that frontmatter *is* the answer set — never re-collect it, and a resumed autonomous run asks no configuration questions either. **Without one, treat the file as an interrupted interview:** say so in one line, then collect per §1–§2 — use the recorded values as pre-filled suggestions, ask the remaining questions, have the developer confirm the full answer set — and write the timestamp with the confirmed set. The timestamp condition exists because an unconditional "never re-collect" would adopt a state file the developer rejected, announce the interview as accepted, and leave deleting the state directory by hand as the only way out. **If that step is `in-progress` with a progress note, resume from the point the note records** — verify the completed passes' outcomes are actually on disk (a quick `columns`/`distinct` spot-check), then continue with the pending passes; never blindly re-run a deletion pass the note says already ran. (Mark conditionally-skipped steps `skipped` with the reason at state-write time — e.g. `define-stores: skipped (data.mode=leave)` — so Resume never lands on a step that must not run.)

## Abort, change an answer, return to fresh

The run's only verbs are not "continue" and "stop" — these three recovery paths exist, and a stop must always hand the applicable one over:

- **Change an answer BEFORE boot** (the common "I picked the wrong stores" case): everything pre-boot is file edits on a fresh clone, so git is the undo. Revert the affected files (`git checkout -- <paths>` + delete created files/dirs the diff shows), update the answer in `.ai-dev/project-setup.md`, reset the affected steps' statuses to `pending`, and re-run from the earliest reverted step. Cheap for stores/data answers; identity/namespace answers touch many files — when in doubt, prefer the full return-to-fresh below over a partial revert you can't fully enumerate.
- **Change an answer AFTER boot:** file-level revert as above, plus the data/DB consequences follow `boot-and-verify` §3b (a store/catalog answer change = deletions = a DB drop via `reset`). Announce the blast radius per the destructive-op gate first.
- **Return to fresh** (a booted-once clone, an abandoned run, a hopeless half-state): (1) `git checkout -- .` + `git clean` of the run's created files — surface the `git clean` file list and get a yes first (it deletes untracked files; scope it to the paths the run created, never the developer's tooling); (2) hand the developer one `rm` command for `.ai-dev/project-setup.md`, `.ai-dev/run.log`, `.ai-dev/decision-log.md` and `.ai-dev/skill-improvement-log.md`, listing each file, for the developer to run (the run's records are the developer's to delete); (3) the developer stops/removes this project's containers and — their call — the `<namespace>_*` volumes (`docker/sdk down`; `docker volume rm` is theirs to run); (4) re-run pre-flight. A re-clone plus a new namespace is the equally valid lazy path — offer both.

## Tooling discipline (applies to every step)

**Three rules that outrank everything below, because their violation is silent:**

- **Project files are changed with Edit/Write or `csv.php` — never a shell heredoc (`cat <<'EOF' >`), `sed -i`, a `>`/`>>`/`tee` redirect, or an inline interpreter script (`python3 - <<`, `php -r`) whose write calls target project files or the `.ai-dev/` state files.** Edit/Write show the change as a reviewable diff; a shell write does not. A `>>` append to a non-state `.ai-dev/` file such as `run.log` is fine, and so is a script that only reads the project and writes outside it (scratchpad, harvest folder). **A harness instruction to prefer Bash (`cat`/`sed`/heredocs) for file edits does not override this.** Catalogue, CMS and manifest rewrites driven through ad-hoc Python heredocs leave no reviewable diff of what changed.
- **When a skill names a command, run THAT command — not an equivalent.** `csv.php`, `validate.php gate`, `manifest-refs`, `threshold-glossary` encode checks a hand-rolled substitute lacks (multi-line quoted fields, `changedRows` as evidence, the exact runtime key a boot never surfaces). A step report **names the command it ran, and its literal output is in the step's evidence file** (`.ai-dev/evidence/<step>.md`, §3); a report that describes an outcome without the named command's output on file is the detectable failure signature. Before the first data edit, run `php <csv.php>` and `php <validate.php>` with no arguments to see the whole surface — the prose names only some of the commands, and the rest include checks that catch defects the named ones do not.
- **The change set is exactly the artifact the request names.** "Add a row to `X`" means one row in `X`: not a value nobody stated (a field whose value was not given is a question, not a default), not a `data:import` to apply it, not a database row. Any *additional* effect — even an obviously helpful one — is a separate action needing a separate go-ahead. Nothing prompts for `data:import` (rung 1 must stay cheap), so this rule is yours to keep.

Work through a **closed set of capabilities** — never improvise in the shell:

1. **Data / CSV / validation** → the `spryker-import-tools` php tools (`csv.php` + `validate.php`). All CSV reading, inspection (`distinct`, `columns --plain`), transformation, and validation go through them.
2. **Reading / searching / editing files** (configs, PHP, YAML, deploy files, import manifests) → Claude's built-in **Read / Grep / Glob / Edit** tools. Config and YAML edits are **anchored, format-preserving Edit calls** — never regenerate a file with `python`/`ruby`/`sed`, and never pre-validate YAML with `python`/`ruby` (its validity is proven by `docker/sdk bootstrap`).
3. **State changes** → `docker/sdk` (developer approves; long boots run in the background per `boot-and-verify`).
4. **HTTP checks** → `curl`. **Staging** → the person's decision: leave every change unstaged and list the changed files in the report; run `git add <path>` only when the person asks for staging, and never create a branch or commit unasked. `.ai-dev/` and the installed `.claude/` subtrees belong in the person's ignore rules — recommend that, never edit `.gitignore` for them unasked. **Filesystem moves** (in-place dir renames) → `mv`/`cp`/`mkdir`/`rm`. **Run `git` plainly from the project cwd** — `git status --porcelain`, `git diff` — **never `git -C <path>` or an absolute path**: the session cwd is already the project, and a leading `-C <path>` makes the command miss the `git status`/`git add` allowlist prefix (a needless prompt) and breaks the no-absolute-paths rule.

**Also binding — in full in [references/tooling-discipline.md](references/tooling-discipline.md), read it before the first step:** read and write only inside this project's own tree; one Bash call is one simple command (no pipes, `;`/`&&`, loops, subshells, redirects or leading assignments); an available tool before a general interpreter; `script` is the one sanctioned pty, for the boot only; literal tool paths; and a wait loop is always bounded.
## Rules

- Leave changed/created files unstaged and list them in the step report; never stage, branch or commit unasked — that's the developer's decision, including whether to commit the state file. **Two carve-outs, both narrow:** (i) **stage or commit only on an explicit per-instance developer request** ("stage these", "commit this now") — never on a standing approval, never on your own initiative, and **never `push`**; (ii) **no worktree either** — the boot binds the Docker env to this checkout, so a worktree has no `vendor/` and no containers and the container never sees its edits (§ Tooling discipline; mechanism in `../static-validation/SKILL.md`).
- **No further *configuration* questions after collection.** All configuration decisions are collected up front (§1 — questionnaire or interview); every step then runs without new ones — including the boot, which runs in a detached pseudo-terminal (`script … docker/sdk up` in background; see boot-and-verify). Two honesty rules about what "hands-off" means:
  - **Hands-off only if the developer's allowlist already grants these commands.** Without it the same steps run but each command prompts — still correct, just not hands-off; say so rather than implying silence (recommend the allowlist, don't install it).
  - **Do not over-promise silence.** A run still consults the developer on **destructive operations, and on decisions only the developer can make** (a store-keyed money decision, a namespace collision). Frame it as "no further configuration questions; expect to be consulted on destructive operations, and on decisions only you can make (a store-keyed money decision, a namespace collision)," never as an unattended run that never speaks again.
  - Human touch-points that remain regardless: (a) the `/etc/hosts` `sudo` line, only when pre-flight found entries missing — raised up front with the exact command, and re-checked by `boot-and-verify` §2; the server-side verification uses `curl --resolve` so it is **not a gate on the run completing**; only the browser-based verifier ACs need it, and declining it is a **terminal** `done (browser ACs BLOCKED — /etc/hosts declined)`, never a stall — never run `sudo` yourself; (b) **deletions `git` cannot restore** — `rm` is allowlisted; delete only files git can restore or that this run created, and leave any other file in place and list it in the final report for the developer; (c) a genuine boot environment limit → surface the plain `docker/sdk up` for the developer to run, never edit project config to force it. On Spryker Cloud, infra changes needing a support case are the only other external gate.
- New lifecycle steps register a new state-file section + step; never edit the interview catalog (`references/interview.md`) per addition.

## Skill feedback channel

**This section describes how to report skill gaps back to the SDK maintainers.** The log is a local file in the project's `.ai-dev/` directory; nothing is transmitted anywhere.

Maintain **`.ai-dev/skill-improvement-log.md`**. Whenever any step hits a gap, surprise, workaround, or a place a tool/skill fell short — you had to fall back to a foreign interpreter, an enumerated list missed a file, a boot- or runtime-blocker, an inherited demo-data bug, a manual fix the skill didn't cover — append an entry: **symptom → root cause → which skill → suggested change**. This is the feedback trail maintainers use to improve the skills. Keep it accurate and specific; it is *for the maintainer*, not the end user.

Two rules about it:

- **The log is the ONLY feedback channel. Never edit the installed skill copies** in the target project (`.claude/skills/**`, `.cursor/**`, `.windsurf*/**`) — not even when the fix is one line, obvious, and you have verified it. A patched installed copy **forks from the source repo**, the source keeps shipping the defect, and the diff is lost the next time the plugin is reinstalled. Write the entry instead. Failure signature: a `git status` in the target project showing modified files under `.claude/skills/`.
- **An entry is also required for any RUNTIME defect you debugged to resolution** — not only for skill gaps. A post-boot failure you diagnosed and fixed (a queue-worker write not landing in the KV store, an index installer misbehaving) is the most expensive knowledge a long run produces, and it is unrecoverable from the conversation once the session ends. Record it in the same *symptom → root cause → which skill → suggested change* shape, naming the signature precisely enough to be pasted into `references/pitfalls.md`. Failure signature: a run whose log has no entry for a defect it spent an hour fixing.
