The single catalog of failure modes across every step. Each skill keeps a one-line **trigger** inline at its decision point (so it fires on a standalone invocation too); the **full triage + fix lives here**, and the cross-cutting traps live here once instead of being restated per skill. Format: **signature → cause → fix.** Grouped by area.

## Cross-cutting (any step)

- **Docker VOLUME / namespace collision.** `docker/sdk up` drops and recreates the DB but reuses named volumes; the deploy `namespace:` derives from the project name, so `<namespace>_*` volumes left by an earlier project under the same namespace put a fresh DB beside stale KV/search/broker read models. Every signal then reads correct while carrying foreign data (for example, store IDs that do not match `spy_store`). Pre-flight checks `docker volume ls` **on the resolved namespace — also when the operator keeps the shipped project name**: the shipped namespace is the one most likely to collide on a shared dev box, and a check limited to new namespaces skips it. Second signature of the same cause: **OpenSearch unhealthy at boot, `IndexFormatTooOldException: … created with Lucene 8.x while the current version is 10.x`** = a stale search volume from an older stack under the shipped namespace. **Ranked fix (never force a rename):** (1) developer removes their own confirmed-stale volumes (`docker volume rm <namespace>_*`); (2) override only the deploy `namespace:` token; (3) a different project name. All three rank above `clean-data`/`reset` — but when `docker volume rm` is not available to the agent and the project is still being set up, `docker/sdk clean-data` is the sanctioned fallback (ungated during first setup, see below).
- **mutagen daemon down after a container restart** (`up`/`up --assets`/`up --build`/`restart`) → host edits never reach the container, so every verification in that window runs against code that is not there and still prints green console output. `mutagen sync list` must show the project session `Connected: Yes` on both alpha and beta; running the command also restarts a dead daemon. Verify a file's presence in the CONTAINER (`docker exec <ns>_cli_1 ls /data/<path>`), not on the host.
- **Diagnose your own delta first.** When something that worked in the fresh demoshop breaks after the transformation, your own data/config change is the prime suspect — not vendor/core. Diff the delta (`git diff -- data/import config src`) and re-verify completeness (`preflight`, `refs`, per-store×locale counts) before opening a vendor file. A feature that worked before your changes locates the defect in your changes.
- **Destructive actions follow the one destructive-operation policy (`spryker-import-tools` → Invocation & command discipline) in BOTH run modes.** Deleting files/dirs (`rm`, `git clean`), removing rows/columns in place (`csv delete`/`filter`/`drop-columns --in-place` — these don't prompt at the OS level) and `reset`/`clean-data`: preview, announce the blast radius in one line, then proceed. Ask first only when data git cannot restore is at stake — untracked or modified files, a DB/volume drop on a project that already carries real data — and the confirmed answer set did not decide it. First setup, demo clones, `answers_confirmed_at` decisions and trusted rebuilds proceed after the announcement. `sudo` and publishing outside the clone always need an explicit yes; autonomous performs and logs reversible edits itself, never a `sudo` or an outward-facing publish unattended.
- **Never mutate the developer's Docker/host env** (memory/CPU limits, `docker system prune`, `docker volume rm`, daemon restart) — recommend, never do. Never edit project config (`deploy.dev.yml`, `docker.mount`/`mutagen`, recipes) to force a boot past a TTY/mount/timeout limit; switching macOS off `mutagen` cripples the Mac dev env.
- **Turn ends with a step report and "Continuing to step N", or with `✅ NEEDS NOTHING — say "continue"`, on an `autonomous` run; nothing runs until the developer replies** → the step-completion protocol stopped after the `run.log` append, and a message shaped like a finished deliverable ends the turn → in `autonomous` a turn that needs nothing never hands back control: the next skill's `Skill` call belongs in the SAME message as the state-row update and the `| END` line. The "say continue" close-out is a `collaborative`-only line.
- **An `AskUserQuestion` whose options reduce to "keep going" / "pause" on an `autonomous` run** → a mode violation presented as a decision point; it breaks both the step-report ban and the configuration-question ban → the default is continue; a real decision point offers substantive alternatives.
- **The developer asks "is there anything you need from me?" while a prerequisite list sits recorded in `.ai-dev/project-setup.md`** → the developer-must-do bucket was *recorded* instead of *spoken* → speak it twice: the up-front ask, then as an exact-command checklist in the step report before the consuming step.
- **`until grep …; do sleep 8; done` still polling a ZERO-BYTE log after minutes or hours** → the producer died at start (often `script` on a command that needs no TTY) → a zero-byte log means the producer is dead; bound the loop or gate it on `kill -0 <pid>`. When switching strategies, kill the existing watchers.
- **`tcgetattr/ioctl: Operation not supported on socket` plus a zero-byte log** → `script` wrapped a command that allocates no TTY (`docker/sdk console …`, `npx cypress run`) → run it directly; `script` is only for `docker/sdk up`/`reset`/interactive shells. The empty log comes from the wrapper failing; the import itself did not run.
- **Pre-flight blocked for minutes on a single disk probe** → `docker system df` walks every image and volume, which is slow on a shared dev box → use `df -h /`; run `docker system df` only as a backgrounded follow-up when `df -h` is already nearly full.
- **A store/region/namespace value justified by "the live Docker environment already expects `<TOKEN>`" on a clone that never booted** → a foreign project's containers read as this project's provisioning → match the namespace prefix or `com.docker.compose.project` label before concluding; verify with `docker inspect`, and never escalate an unverified observation to the operator as a decision.
- **A worktree or branch proposed for a run whose verification is post-boot, which then has no `vendor/`, no running containers and no local PHP CLI** → the Docker env is bound to the checkout the boot ran in, so a linked worktree's edits are invisible to the mounted container → never propose a worktree or branch for a run whose verification is post-boot.
- **A destructive act run on the strength of an approval granted much earlier for a different class of action** → standing approval treated as unbounded → record its scope in the state file; once the project carries real data, irreversible actions are re-announced with blast radius and re-approved every time, unless the developer approved rebuilds (`standing_approval: { scope: rebuilds }`).
- **`git status` in the target project shows modified files under `.claude/skills/`** → an installed skill copy was patched instead of the gap being logged → the skill-improvement log is the only feedback channel; a patched installed copy forks from the source repo and the diff is lost on reinstall.
- **A state file whose `answers_defaulted` list is longer than the questions actually asked (or non-empty on `answers_source: interview`)** → "a blank is a default" was applied to an interview run, where there are no blanks — only unasked questions; the hook counts calls rather than coverage, so rounds that never asked `P1` still pass it → autonomy begins after the catalog is covered and confirmed; refuse the write, ask the unasked sections (interview.md Rule 0).
- **Tool calls that mutate the project while the developer's last message ended in `?`** → a question was executed as an instruction (a criticism inside a question also reads as a defect report to fix); in the extreme case a question about naming turns into a reorganisation of the import tree that breaks a green `gate --strict` → a developer question is answered, not acted on: answer, state what you would change and its cost, wait (SKILL.md Communication rule 5). The `guard-*` hooks DENY a mutation while the developer's last message is a question (a request phrased as "can you …?" counts as an instruction) — that denial is the signature.
- **A Bash call containing `<<'EOF'`, `sed -i`, or `>`/`>>`/`tee` targeting a path under the project root** → a file write routed around `guard-files.php`, which matches only `Edit|Write|MultiEdit` — the same bypass as `docker exec` around `gate-docker-sdk.php`; `guard-bash.php` denies shell writes into project files and guarded `.ai-dev/` state files (a `>>` append to a non-state `.ai-dev/` file such as `run.log` is allowed) → change project files with Edit/Write only; a harness preference for shell edits does not override a project whose hooks key off the edit tools.
- **The developer's next message begins "no", "I meant", or "I asked about…"** → the words of a short request were executed and its goal missed (for example, a request to hide a label whose underlying problem is a duplicated shipment type, or a cart template edited when the PDP was meant) → before any change under ~fifteen words naming a UI symptom, restate in one line *who* (actor/store/locale), *where* (exact page), *what should be true after*, and ask "is the stated fix the goal or a symptom?"; proceed only when all three are known.
- **Wizard pre-flight refuses a clone that is only *booted*, or that carries the AI Dev SDK install** → the gate was read as "un-booted and clean" when it asks **"still an unmodified demoshop?"** → neither is a blocker: a booted demoshop just needs `clean-data` + a re-boot for the data changes to land, and the SDK delta (`composer.json`/`composer.lock`/`ConsoleDependencyProvider.php` + untracked `.ai-dev/`/`CLAUDE.md`/`.claude/`) is expected. **Stop only when the clone is already someone's project** — tracked changes under `src/`/`data/import/`/`config/`, a registered custom namespace, changed stores, or real business data. Never `git reset` the SDK delta — that un-installs the SDK.
- **A project-layer change is present in `src/Pyz/…` and absent from running behaviour** → the higher-precedence namespace (`PROJECT_NAMESPACES[0]`) resolves first and shadows the Pyz edit → move the change to `src/<Ns>/…`, extending the Pyz class when one exists; leave `src/Pyz` pristine. This is a runtime diagnostic, not a precondition: it does not require a `src/<Ns>/…` sibling to already exist, and new code with no counterpart anywhere also belongs in `PROJECT_NAMESPACES[0]`. A near-empty `src/<Ns>/` is expected on a new project and does not indicate the namespace is unused.
- **The full review fan-out, independent QA and local CI are required for a 1-line diff, and the developer deviates from them** → gate weight is not proportional to diff size, so skipping the gates becomes the only proportional path → record `size` at intake and scale reviewer count and QA scope by it. Gate weight scales with size; every gate still runs.
- **A regression test's "fails before, passes after" claim on a suite that was already red** (e.g. a missing `request_stack` service in a suite the change never touched) → pre-existing failures are indistinguishable from fix-induced damage → baseline the suite before authoring, attribute failures against the pre-fix state, record `pre_existing_rot`, and repair it as a separately scoped decision outside the attempt budget.
- **A plugin works under `deploy.dev.yml` and throws `MalformedUriException` (the URL is literally `http://`) on every click under another deploy file** → the plugin was copied from a shipped example and kept the example's env var names (`SPRYKER_<FEATURE>_CONFIGURATOR_HOST`/`_PORT`), which only that one deploy file defines; `getenv()` returns false and `?: ''` yields an empty host. A second instance sits behind it: the redirect-host whitelist in `config/Shared/config_default.php` lists only the example's host, so the return redirect is rejected as external once the URL is fixed → pre-deploy: for every `getenv('SPRYKER_*')` under `src/`, grep the name against EVERY `deploy.*.yml`; a name present in exactly one deploy file is the signature. Sweep the whitelist with the same names.
- **"No Back Office UI exists for this" concluded from the absence of a `*-gui` module, with raw SQL offered as the only route** → several modules ship their own `Communication/Controller` + `Presentation/`. For example, `ProductSearch` serves `/product-search/search-preferences`: its "Deactivate all" button deletes only that one attribute's `spy_product_search_attribute_map` rows (`cleanAction`), `syncAction` rebuilds the documents, and the table lists every attribute key, mapped or not, so the button has no effect on unmapped ones → grep vendor for a controller touching the table before stating that SQL is the only route.
- **Yves frontend — suppressing a Symfony form field fails silently in two ways:** skipping its `form_row` does not remove it, because `form_rest()` renders it at the end of the form, unstyled and visible; hiding the wrapper with `is-hidden` is undone at runtime, because `address-item-form` passes that class to the JS as `elements-to-toggle-class`, which strips it again → working shape: render the field, unchecked, hide its wrapper, and omit the JS-targeted class from the wrapper. Neither failure shows on a successful render or from reading the template alone.

## Boot — flow gotchas

- **A gate baseline reporting 0 findings on an unmodified demoshop** → always wrong — the shipped clone is not gate-clean on any group. Cause: `gate > .ai-dev/gate-baseline.json`; the shell truncates the target before the gate runs, the gate discovers the empty file as its own baseline, errors `cannot read baseline`, aborts its content checks and serialises `findings: []`. The empty baseline raises nothing during the interview and then blocks the step-8 boot with every shipped quirk unsuppressed → `gate --save .ai-dev/gate-baseline.json` (writes after running; refuses `baselineSafe: false`), then Read the file: `errors: []` and findings in at least one group, or re-run.
- **The shipped demoshop is NOT preflight-clean** — it carries pre-existing quirks (URL dups "not yours to fix") that read as self-inflicted damage. Capture a `preflight` baseline on the untouched clone and gate only NEW findings against it. **The baseline never suppresses a finding whose severity depends on the project's own config** — a `tax_set_name` mismatch is a shipped quirk on DE/AT and a live tax defect everywhere else (see "Project data"). If the shipped value was correct for DE/AT and your project is not DE/AT, it is yours.
- **Demo-data-once gate.** Demo data loads only into a table-less DB; after a partial/aborted boot, a plain re-`up` logs `[LOADED]` and **silently skips the entire demodata section**. Verify from the log that the section actually ran; if not, re-run the whole recipe from a dropped database — never a plain re-`up`, and never hand-run the recipe tail. First iterate a data-import error with `data:import -c` before spending any rebuild.
- **`clean-data` + `up` prescribed for an aborted install without considering `reset`** → the most expensive rung (4) chosen for a rung-3 problem, while §3b's ladder says climb to the cheapest rung that does the job → once rung 1 (`data:import -c`) is clean, read what `reset` does in THIS SDK (`docker/sdk` source: light drop-and-reimport vs `down` + `cleanVolumes` + full `up --build`); where it is the light variant it is the answer, where it is the full teardown the blast radius equals `clean-data`+`up` and you say so before choosing. The developer redirecting "run docker/sdk reset instead" is the signature.
- **Don't arm a `tail -f | grep` monitor on `boot.log`** — `script` fills it with BuildKit ANSI redraw frames, so a filtered tail fires dozens of useless notifications and gets rate-limited. Wait for the boot's own completion re-invocation.

## Boot aborts — environment limits (the developer acts; "run plain `docker/sdk up`" fixes none)

| Signature | Cause | Fix (developer's, not yours) |
|---|---|---|
| `port is already allocated` / `address already in use`, minute 0 | another project holds 80/443 | developer stops those containers (pre-flight probes this) |
| composer death ~min 40 — `Could not authenticate against github.com`, `API rate limit exceeded`, `401`/`403` | missing/exhausted composer auth token | developer adds the token (pre-flight probes this) |
| `no space left on device` | disk full | developer frees space — never prune for them |
| exit 137 / a service repeatedly restarting | OOM | recommend more Docker memory — never change their settings |

## Boot aborts — build phase

- **`Cannot find module '<x>'` during any `frontend:*:build`** → `node_modules` never populated; the shipped `package-lock.json` can be out of sync (`npm ci` fails `Missing: <pkg> from lock file`). Run `npm ci` directly in the `cli` container to see the real error, then `npm install` to repair the lock — a dependency-manifest fix, not a project-config edit. (A demoshop shipping a stale lockfile can't `npm ci` out of the box — worth reporting upstream.)
- **A recipe step `cmd | tail -N` cannot fail the install** — its exit status is `tail`'s and the error text is discarded. When an abort surfaces in a build step, check the *preceding* step for pipe-masking; re-run it without the pipe. Durable recipe fix: `set -o pipefail` or drop the `| tail`.
- **`docker/sdk reset`/`up` dies in the build phase at exactly 600s, BEFORE the data-import section, leaving the stack down with an empty DB — and the `script`-wrapped run still exits 0** → `zed-build-frontend` in `config/install/docker.yml` carries no `timeout:` while its siblings in the same section (`merchant-portal-build-frontend`, `storybook-build-frontend`) carry `timeout: 1600`, so it inherits the 600s default → add `timeout: 1600` to `zed-build-frontend` in BOTH the production and development blocks (a recipe inconsistency fix, not the forbidden "raise a limit to force a boot" edit). Grep the log for `exceeded the timeout` / `In Process.php` — never trust the exit code.

## Boot aborts — data import

- **The named importer is usually NOT the culprit — an EARLIER one is.** A `… on null` / `not found` abort surfaces where a downstream writer dereferences a missing row while the real defect was an earlier importer loading 0 rows silently. Diagnose with a single-importer run: `docker/sdk console data:import <importer> --config=<config>` (prints the per-row reason the install log swallows).
- **Grep the real strings.** Success = `Overall Import status: OK` + no `Aborted install`; failure = `Product with SKU … not found` / `not found in permanent storage` / `Overall Import status:*Failed` / `Aborted` / `SQLSTATE`. One substring is a false green.
- **An empty `message_glossary_key` does not exempt a threshold** — Sales-Order-Threshold derives its key from type+store+currency (`sales-order-threshold.<type>.<store_lc>.<cur_lc>.message`) and looks it up unconditionally; a miss throws `MissingTranslationException` at add-to-cart. The key needs a translation in **every project locale of the store** (the value is per-locale). `merchant-relationship-sales-order-threshold` is **auto-generated — never seed those**. Pre-boot gate: `validate.php threshold-glossary <manifest> --locales <project locales>`.
- **`spy_url` is globally unique across every entity** — one un-rewritten `url.<locale>` (for example in `merchant.csv`) aborts the 30–60-min install. Run `unique` on every url-family file discovered by a `columns --plain` scan, not a fixed list.
- **A shared-bucket file with a `store` column** (e.g. `common/common/sales_order.csv` with `store=DE`) → `Store not found` at import even though the per-store dirs were remapped. Scan ALL of `data/import/**` for store columns, not just the per-store dirs.
- **A `locale-store` row for a locale absent from base `locale.csv`** → `Locale not found`. Add exotic project locales to the base locale set first.

## Post-boot — verification false signals & probe traps

- **`rabbitmqctl list_queues` against the default `/` vhost returns an empty list** = a false "drained". Target the project vhost: `-p <broker-namespace>`.
- **`queue:worker:start --stop-when-empty` (or `queue:task:start`, `publish:trigger-events`) prints only the env banner, exits 0, and the queues stay full** → missing `APPLICATION_STORE`, not a broken publisher: in DMS the queue and publish commands resolve their store from that variable and process nothing without it. Exit 0 plus a banner reads as success and points the diagnosis at the publisher → `docker/sdk cli "APPLICATION_STORE=<STORE> vendor/bin/console queue:worker:start --stop-when-empty"`, **once per store**; pair every drain with a broker depth assertion (discover the container name — `<namespace>_broker_1`, never a hardcoded `spryker_broker_1`). A queue counts as drained only when its depth fell.
- **The developer sends a screenshot right after a visual change was reported complete** → the change was verified with `grep` on the fetched HTML, never by looking: markup containing the string proves presence, not legibility, alignment or size, so the developer's screenshot becomes the first visual check → for any visual acceptance criterion open the page in the browser, screenshot, compare against the reference, and **measure** (`getBoundingClientRect`/`getComputedStyle`) before reporting; a measurement identifies the fix directly.
- **A small, STABLE `publish.*.error` count** is usually a benign duplicate-key publish race (two listeners insert the same `*_page_search` row), not a failure — verify the underlying rows exist; only worry if the count grows across reboots.
- **An aggregate total hides a broken slice.** A store with a full `product_abstract_store` count can still have one locale at **zero** localized rows (skipped-locale) or a few products with no price (net-only seed). Assert the full grid — per store × each locale, per store × product — and name the grid you checked (`<stores> × <locales> × <products>`), never a total.
- **URL contract is `/<STORE>/<lang>/…`.** A bare `/<lang>/…` silently falls back to the default store+locale → false negatives ("store unreachable", "wrong `<html lang>`"). Always probe with the store prefix.
- **Glue selects the store from the `Store` request header (or `?_store=<STORE>`)** — probe each store with `-H 'Store: <STORE>'` on the single host; no per-store hosts needed. A same-currency-for-every-store result means a missing/wrong `Store` header or a stale read model, not a host limit. Source: `vendor/spryker/stores-api/.../StoreResolver.php` (`HEADER_STORE_NAME='Store'`).
- **ES `_cat/indices docs.count` lags the segment merge** → false "index nearly empty". Assert search health with `/<index>/_count` or `/_search`, never `_cat`.
- **KV `db 0` is empty** because the store is namespaced into a numbered Redis DB (often `db 1`) → a false "missing data". Query the namespaced index; `valkey-cli` lives in the KV container, not `cli`.
- **add-to-cart curl false-fails** for harness reasons, not project defects: the action is guest-restricted (log in first); `login_check` 500s without a `Referer`; company users 1–2 hold no role ("forbidden"); the URL needs the **CONCRETE** sku; the CSRF field is namespaced (`add_to_cart_form[_token]`) but payload fields are plain; a **separate** fetch of the redirect target destroys the flash message. Follow the recipe, `-L` on one cookie jar, read the flash first, and use anchored selectors (`kr` matches "bac**kr**est").
- **Anonymous `/{STORE}/{locale}/customer/overview` → 500 `getIdCustomer() on null` while `/multi-cart` → 200 and renders, and `/{STORE}/en/…` → 302 to login** → `CustomerConstants::CUSTOMER_SECURED_PATTERN` hardcodes the language segment to `(en|de)`, so `CustomerPageSecurityPlugin` never engages on other languages → assert **302-to-login** (not "not 500") per store×locale; retarget the regex alternation AND its `/en`|`/de` path fragments. Invisible because `en_US` is always kept, so the `en` path keeps working.
- **Every API Platform request 500s `Validation cache is enabled, but cache file is not found` after a fully green boot** → a stale generated artifact keyed by the OLD region/store/bucket token survived (`src/Generated/Glue/Validator/validationEU.cache` while the bucket resolves to `EUROPE`); `src/Generated/**` and `data/cache/**` are gitignored and in no sweep → post-boot, `find src/Generated data/cache -name '*<OLD_TOKEN>*'` must return nothing; regenerate and delete the stale sibling. Discover by token match, not by a fixed list.
- **Glue Backend declared "dead" — every probed path 404s and `src/Generated/Api/Backend` is empty** → probes derived from plausibility instead of registered plugins; an empty generated-API dir is the shipped legacy-REST default, and `404`/`406` on a bare root is CORRECT → derive the resource list from `new *ResourcePlugin` in the GlueBackend dependency provider, use the declared method and `Content-Type: application/vnd.api+json`, and require a positive control before declaring an app dead.
- **Add-to-cart returns 302 back to the PDP with a ~120-byte quote and no flash naming a field, on a marketplace product** → `product_offer_reference` and/or `shipment_type_uuid` omitted (the offer-field spelling also varies) → read `name=` attributes off the RENDERED form and POST them verbatim; the form is flat except the namespaced `_token`.
- **A login POST 500s `ForbiddenExternalRedirectException: URL home is invalid` (Yves AND Backoffice)** → missing `Referer`; the authentication itself succeeded → grep the audit log for `Successful Login` before diagnosing, and send a referer.
- **`10% off $100+` rendered on EUR-only stores** → a hardcoded foreign currency in authored CMS/promo copy, invisible to price-selector assertions → detect a foreign symbol **adjacent to a digit** (never a bare symbol grep — `kr` hides inside "ba*ckr*est"), and scan CMS copy too.
- **"Search dead + PDP dead while everything else is green" reported as a pre-existing platform bug** → on a transformed catalog that is the known signature of a DELTA defect, not a platform one → rule out the delta in order (approval status, `category_store`, abstract-level price, per-store `*_page` `/_count`), then require a positive control (untransformed demoshop or fresh index) before "pre-existing" or "unrelated to our data" may appear in a report.
- **A red gate on a customer-facing surface offered to the operator as "fix now / leave as known issue"** → asking permission turns a FAIL into a closed run → operator consent cannot clear a red gate; the step records `failed`/`in-progress` and the defect goes to go-live debt. A declined `/etc/hosts` entry is the only terminal-with-caveat state.

## Post-boot — "green but empty" (every server signal reads correct, the page/feature is empty)

- **`src/Generated/Shared/DataBuilder` empty after a green boot** → `cy:run` `/dynamic-fixtures` 500 `ClassNotFoundError … Generated\Shared\DataBuilder\*`. Fix: `docker/sdk console transfer:databuilder:generate`. Not a data or Cypress-config defect.
- **BO product list empty on a project with no en_US/de_DE store locale** → the admin locale has no localized-attribute rows and `VariantTable` inner-joins on it → the `getBackofficeUILocales()` override is required.
- **search returns 0 docs while import/queues/DB all read green** → missing `product-approval-status` → the `page_product_abstract` publisher writes nothing. Assert per-store `*_page` `/_count` > 0 as a named gate.
- **Theming/logo green-but-empty** (empty `:root { }`, a logo that renders at 0×0, BO on the Spryker teal) → see **Branding & theming**.
- **A rendered widget does not prove its backing data imported** — a selector (e.g. packaging-unit) renders with zero backing data. Confirm entities by row count, never by the DOM.
- **The storefront root returns 200 with the right `<html lang=` and renders zero slot blocks** → the keep-list stripped the non-email CMS blocks and nothing rebuilt them; a reachability probe passes a wholly empty homepage → count rendered slot blocks (`slt-2` carousel slides plus ≥1 below-the-fold section); 200-with-zero-blocks is a FAIL, and hero-only is a partial-restore FAIL.
- **A kept Glue/`glue-backend` app passes every gate while its API returns 500 on every endpoint** → the probe list modelled Glue as the Yves *fallback*, so it is never probed when Yves is kept → probe EVERY application not in `services.applications_disabled`; `POST /access-tokens` (not the raw OAuth `/token`, which works even when API Platform is broken) then one authenticated resource fetch.

## Post-boot — read-model / recovery / iteration ladder

- **A direct SQL mutation orphans the read model.** SQL `DELETE`/`UPDATE` bypasses the event-behaviour that queues publish events, so `publish:trigger-events` does NOT rebuild the stale storage — only a DB drop + re-import restores coherence. `publish:trigger-events` is a recovery tool, not a routine resync.
- **Rebuild the RIGHT resource** — `publish:trigger-events -r price_product_abstract` for price KV, NOT `product_abstract`.
- **Not every importer upserts.** `discount-amount` and `cms-block` are INSERT-only; re-importing existing rows fails `Unable to execute INSERT …`. A unique-constraint INSERT error on an entity you didn't add rows to = insert-only → needs a `reset`, not a CSV fix. **A value change to an already-imported row duplicates** (`spy_price_product_store` has no unique key on price_product×store×currency) → also needs a `reset`.
- **`docker/sdk reset` needs a TTY** — a plain background shell dies `ERROR: failed to get console` at the rebuild, AFTER already wiping the data. Run it via `script -q .ai-dev/reset.log docker/sdk reset` in background, and confirm what `reset` does in this SDK (light re-import vs full teardown) first.
- **A post-boot `.scss`/`.ts` change** — `docker/sdk cli "ls -d /data/node_modules"` decides the rung: **present** → `docker/sdk console frontend:yves:build` (seconds); **absent** → `docker/sdk up --assets` (minutes) — `frontend:*:build` dies `Cannot find module` only when `node_modules` is missing (`../../boot-and-verify/references/iteration-ladder.md`, `spryker-refresher`). Never `npm install` in `cli` — mutagen pushes `node_modules` onto the host sync. Twig-only changes need no build — but see the Twig-cache trap below.
- **A `.twig` fix has no visible effect — the file is correct on disk AND in the container, yet the rendered page is the old one** → the compiled Twig cache serves the stale template; `docker/sdk up --assets` does not clear it → `docker/sdk cli "rm -rf src/Generated/Yves/Twig/codeBucket"` and reload; for a NEW override file also `twig:cache:warmer` (the template path map). This sits beside opcache in the "change appears to do nothing" triage: clear both BEFORE concluding "the change had no effect" and writing a second, unnecessary fix. **Never delete `data/cache/Yves/<env>`** — it is the Symfony DI container, not the Twig cache, and removing it gives transient 500s.
- **A new project class override, strict order:** write file → confirm it exists in the container → `cache:class-resolver:build` → confirm the FQCN is in the resolver cache. Rebuilding the cache before the mutagen sync lands bakes a cache WITHOUT the class.
- **`Class "…" not found` from a generated `get…ConsoleService.php` (e.g. `queue:worker:start` refuses to start) while the class is referenced nowhere in `src/`, `config/` or `vendor/`** → leftovers of an earlier attempt on this machine, in TWO places: `src/Generated/OpenTelemetry/Hooks/*` + its `classmap.php` on the host, and the compiled DI container on the CONTAINER side under `/data/data/cache/Zed` → clear the `src/Generated/**` leftovers AND `docker exec <ns>_cli_1 rm -rf /data/data/cache/Zed /data/data/cache/console/command-map.php`. `cache:empty-all` removes NEITHER. This is the one sanctioned case for clearing the compiled container: a stale container after generated-code changes — never as a Twig cache clear, which goes through `src/Generated/Yves/Twig/codeBucket` (`../../boot-and-verify/references/iteration-ladder.md`).
- **Every category page 500s `Search failed … failed to find nested object under path [integer-facet] [reason: all shards failed]`, and later `search:setup:sources` itself dies `analyzer [suggestion_analyzer] has not been configured in mappings`** → the first boot died before search setup and a later sync created the indices implicitly, WITHOUT the custom analyzer settings; setup cannot add analyzers to a live index → delete the `<namespace>_*` indices, then `search:setup:sources` (creates them WITH settings), then `search:setup:index-map`, then sync. The implicitly-created index is the cause; the symptom surfaces as a storefront 500 far from it.

## Generate strategy (project-data/references/generate.md)

- **A category tree with no `category_store` rows shows in no store** — categories are store-assigned exactly like products.
- **Price authored at CONCRETE only, not ABSTRACT** → catalog/PLP/search read the abstract price → 0 products in listings. Author the abstract price too.
- **Navigation is a 4-layer chain** (`navigation`/`navigation_node`/`content_navigation` + the nodes' targets) — carrying one file → empty menus. The home PAGE must be store-assigned via `cms_page_store`, and its CMS blocks must survive the keep-list, or the homepage is empty.
- **`content_banner` title > 64 / subtitle > 128 codepoints** → the whole import fails (`This value is too long`). Author within the limits.
- **A hand-written keep-list drops behavioural plumbing.** The demo ships far more entities than any keep-list you would write by hand, and a near-miss like `product-shipment-type` (~1-per-concrete = required) breaks silently. Enumerate the shipped manifest's `data_entity` list (`grep -hoE "data_entity: *[a-z-]+" data/import/local/full_<REGION>.yml | sort -u`), diff it with `manifest-diff`, and rank omissions by coverage density (rows ≈ population = required; rows ≪ population = opt-in garnish).
- **Do NOT run url-uniqueness on `navigation_node.csv`** — a nav node's `url` is a link target, legitimately repeated across menus; flagging it is a false positive.
- **C1 — `color_code` required** or the row imports as **0 rows silently**, surfacing ~10 steps later as `getIdProductAbstract() on null`.
- **C2 — `merchant-stock` DERIVES the stock name** and ignores the `stock_name` you supply; downstream references must use the derived string.
- **C3 — `merchant-user` only LINKS an existing Zed user** — seed the user (`getInstallerUsers()`) first.
- **C4 — `product_management_attribute.visibility` is an ENUM** (PDP/PLP/Cart), not a boolean; `1` fails every row.
- **C6 — `merchant-product` is separate from `merchant-product-offer`** — without it the PDP shows no seller.
- **C7 — a variant differentiator needs `is_super=1`** or the variants are inert (no variant selector) while every count/refs check passes.
- **C8 — `attribute_key_N.<locale>` is a MACHINE KEY despite the suffix** — it must equal the unsuffixed key; a label there 500s the BO product-attribute page for every product. The label lives only in `product_management_attribute.csv` `key_translation.<locale>`.
- **C9 — `product-concrete` needs the full localized-attribute triplet** (name + description + is_searchable) per store-locale, all-or-nothing; the error names a different column than the one actually missing.

## Localization (translate-content)

- **`attribute_key_N.<locale>` is a machine key — never translate it** (the C8 trap): translating it breaks the localized-attributes map and 500s the BO product-attribute page. `key_translation.<locale>` in `product_management_attribute.csv` IS the display label — translate that (easy to miss → English label beside a translated value).
- **Glossary values that are navigational paths** (`page.terms.url`, `main_slider_*.url`, …) are locale-specific — re-prefix them per target locale, don't leave the source prefix (see the project-data 307 trap). Exempt `/assets/`.
- **The SEO half of localization** (localized URL slugs, sitemap, `hreflang`, robots) is owned by no skill — a "localized" store ships English slugs and no locale signals until flagged. Name it in the close.
- **Storefront nav 404s on every category link while the import reports `Overall Import status: Successful` and queues drain clean** → translating a category `name` makes Spryker regenerate its URL from the localized name and 301 the old slug; the 301's `to_url` drops the DMS store prefix, so it does not act as a fallback → harvest old→new from `spy_url_redirect`, re-point every `url.<loc>` with a same-column `apply-translations`, re-import, drain, and assert nav links return 200 not 301.
- **One locale of N renders English UI chrome beside correctly translated category names, after a clean import and zero-length queues** → that locale's publish never ran; its `kv:translation:<loc>:*` entries still carry the boot-time `_timestamp` → compare KV `_timestamp`/`value` ACROSS locales (not just one), then `publish:trigger-events -r translation` + a second drain. A successful import with drained queues does not prove the read model updated.
- **Footer legal links 404 in it/es after a glossary path rewrite** → `cms_page.csv` is `en_US`-only (and an ES-only store has no `en_US` locale at all), so a well-formed `/it/gtc` has no page behind it → assert the referent before rewriting a path value (`validate refs` the `.url` glossary keys against `cms_page.csv url.<locale>`), localize the CMS page first, and confirm the locale is served per `locale_store.csv`.
- **`content_banner` import fails `This value should not be blank` right after filling one localized column** → any single `X.<locale>` flips that whole locale bucket from absent to present, making the rest required → fill the complete set (`title`/`subtitle`/`click_url`/`imageUrl`/`altText`) or leave the locale entirely absent.
- **Fluent English strings on a fully translated locale, with no raw dot-notation keys anywhere** → the template passes the English sentence AS the glossary key, so the translator echoes the key; the data-side coverage model cannot see it and the fallback is fluent English → `grep -rnoE "'[A-Z][^']{4,80}'\\s*\\|\\s*trans" src/` and report every hit as untranslatable-by-construction. Glossary changes cannot fix it.
- **The same provider or brand string translated in one locale and left English in another** → brand/proper-name classification was fanned out per chunk worker, and the coverage gate is set-membership so it is structurally blind to a disagreement → decide the preserve-list ONCE up front, shared across all locales, and add a cross-locale verbatim-vs-changed diff.
- **Concurrent translator sub-agents read back each other's content, or a chunk output vanishes mid-run** → a shared output directory with generic temp names (`raw1.txt`) → unique per-agent output paths plus private `work/<locale>/<NN>/` intermediates, and a pre-apply script-family gate (Cyrillic required in `uk_UA`, forbidden in `es_ES`/`pl_PL`/`cs_CZ`) — a contaminated map is silently valid to `apply-translations`.

## E2E / Cypress (cypress-migration)

- **`cy:run` dies `spawn Xvfb ENOENT`** → the Alpine/arm64 CLI container has no display. Run `cy:run` on the host or a CI runner with a display; `npm ci` in the container is fine.
- **A storefront checkout spec hangs on a payment radio that never renders** → it selects `dummyMarketplacePaymentInvoice`, filtered out until a merchant offer is in the cart. Storefront checkout specs on a plain-product fixture must use a non-marketplace method (`dummyPaymentInvoice`).
- **`/dynamic-fixtures` DSL constraints** (invisible until a `#key` reference explodes): a `#key` must reference a helper returning an `AbstractTransfer`/`ArrayObject` (a scalar-returning helper is silently discarded → `Undefined array key`); references are one level deep and can't index arrays; resolve store facts via **glue-backend** `/dynamic-fixtures` (`getAllowedStore`), never storefront Glue (it's an optional app); send `Content-Type: application/vnd.api+json` (else a bare 404 that reads as a missing route).
- **Store facts must NOT live in `.envs`** — they're resolved from the shop; a hand-set value is a second source of truth. `GLUE_BACKEND_URL` is mandatory. `PROJECT_LOCATION` set only for CI silently no-ops CLI-exec steps locally. Fixtures created mid-run need a **continuous** `queue:worker:start` (search isn't synchronous). A B2B purchasing-control customer makes Glue-API setup 422.
- **`code:check` (`eslint . ; prettier .`) masks a real ESLint failure** — the `;` makes prettier's exit status win. Run lint and prettier separately.

## Services (configure-services)

- **A disabled app still burns boot time** (e.g. Storybook building after `static` was disabled) → the install recipe runs its build/asset/cache steps unconditionally. For each app in `services.applications_disabled`, also remove its recipe steps, not just its deploy endpoint.
- **`applications_disabled` prunes must target the region group that exists at this step** (the shipped `EU`), not the project's target region — this step runs before `define-stores` renames it.

## CI generation (project-ci-generator)

- **A dropped test-suite's support files** — near-identical kept-vs-dropped filenames (`…cypress-boilerplate.yml` kept vs `…cypress.yml` dropped: delete by which surviving job references it), and a `*_ROBOT.yml` fixture config that may be shared with the regular demodata pipeline (grep the literal filename and read `source:`/`command:` before deleting).
- **The kept `.github/deploy/*.yml` region tokens** must be written to `## Required follow-ups` in `.ai-dev/project-setup.md` for `define-stores`/`brand-project` to sweep — otherwise the workflow retargets and the deploy files silently don't.
- **`data/import/<name>/{…}` holds dozens of CSVs that no surviving import manifest references, found later by a dangling-manifest sweep** → the suite drop deleted the manifests before the fixture closure was resolved, cutting the only reference chain to the fixture tree → resolve manifest → `source:` dirs into the keep set BEFORE any deletion, then prove it with `validate.php orphan-files <surviving manifest> data/import`.
