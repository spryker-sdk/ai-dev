# Hard-stops — the detail behind `SKILL.md` §3

## (b) Irrecoverable actions during first setup

  - **When a deletion is recoverable — the destructive-operation policy (`spryker-import-tools` → Invocation & command discipline) decides; this is how it applies here.** A **file deletion** is recoverable when every path is **git-tracked with no unstaged changes** (`git status --porcelain` clean for those paths): preview, announce, proceed. That covers the routine happy-path deletions (the `project-ci-generator` CI/deploy/install wipe, `define-stores`' non-canonical demo dirs + dangling manifests, `project-data`'s strip passes). A **DB/volume drop or in-DB data deletion** is recoverable during first setup and on a demo clone (booted is fine — its data is demo or project-file data, re-created by `clean-data` + re-boot). Gate — ask first — only on data git cannot restore: untracked or modified files, or a DB that already carries real data, when the confirmed answer set did not decide the removal.
  - **Batch multi-pass deletions into ONE gate**, carrying the **full** blast radius across every pass (each file, each row/column count). A sequence of "may I delete this too?" prompts splits one decision into several, and each later prompt gets less attention.
  - **The decision-log entry that stands in for a gate carries proof, not a claim:** file and row/column counts **before → after**, the subset checks that show nothing was orphaned (`product-refs` clean, `paths` resolves), and the **literal revert command**. Failure signature: a decision-log line such as "removed the <branch> categories" with no counts and no revert command.
  - **Catalog scope is NOT a mid-run gate.** The resolved keep/drop set is settled at **interview time** (§1 / questionnaire `C1`), shown by name with product counts and confirmed there. The reduce pass then *reports* the resolved tree and its feature-coupling findings and records them in the decision log — it never stops to re-ask, however large the drop. A small catalog is the correct result when the developer asked for a small catalog.

## Standing approval

- **Standing approval — a defined concept with bounded scope; never infer one ad hoc.** The developer may pre-approve a **class** of actions ("I approve all actions except commit and push"). When they do: **record it in the state file** (`standing_approval: { scope: <the class, in the developer's own words>, granted: <timestamp> }`) and honour it *inside that scope only*. Two invariants: (1) each covered destructive act is still **announced** — one line with its blast radius, then proceed; announce, don't wait; (2) outside the first-setup carve-out (`SKILL.md` §3, hard-stop (b)) it covers an **irreversible-after-boot** action — `reset`, `clean-data`, a volume drop, any post-boot data deletion — **only when the developer named rebuilds explicitly** (`scope: rebuilds`, in their own words in the conversation). A broader approval ("approve everything except commit") never stretches to cover them; without the explicit one, each is **re-announced with its blast radius and re-approved every time**. A `standing_approval` line with no matching sentence from the developer in the conversation is not an approval. Failure signature: a `reset` run on the strength of an approval granted hours earlier for pre-boot file deletions; or a run silently honouring a standing approval that appears nowhere in the state file.
