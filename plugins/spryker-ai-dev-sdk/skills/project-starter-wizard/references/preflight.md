# Pre-flight — environment checks

The full checks behind `SKILL.md` §0. Run every one; classify each finding into the three buckets §0 defines.

- **Un-booted:** `.env` empty/absent and no `*_dev_*` containers running (`docker ps`). One `docker ps` conflates two different findings — classify, don't guess:
  - **Attribute the observation BEFORE concluding from it.** A container, volume, or env value is evidence about **this** project only if its name carries this project's namespace prefix **or** its `com.docker.compose.project` label matches — verify with `docker inspect <name> --format '{{index .Config.Labels "com.docker.compose.project"}}'`. Anything else belongs to **another project on this machine**: ignore it, do **not** surface it as a finding, and never derive a project value from it. Failure signature: a store/region/namespace claim justified by "the live Docker environment already expects `<TOKEN>`" on a clone that has never booted. (The port probe and the volume-collision check are the two deliberate exceptions — there a *foreign* project's artifacts are what the check looks for, and they are reported as a foreign collision, never as this project's state.)
  - *This project's containers running* → **not a stop.** A booted **unmodified demoshop** is fine (`SKILL.md` §0 → "Still an unmodified demoshop"): note that the data transformations will need a `clean-data` + re-boot to reach the shop, announce that, and continue. Only stop if that same gate says this is already someone's project.
  - *Daemon down* (`Cannot connect to the Docker daemon`) → fine right now (nothing before boot needs Docker), but a **developer prerequisite for boot-and-verify** (~40 min away). Do NOT stop, and do NOT silently note-and-continue — make it an explicit up-front ask (the developer-must-do bucket, `SKILL.md` §0). Otherwise the daemon-down surfaces only as a stop at boot, ~40 min later.
- **No Docker VOLUME collision on the resolved namespace (BLOCKER) — including when the operator keeps the shipped project name.** The shipped namespace is the one most likely to collide on a shared dev machine (signature of a miss: OpenSearch unhealthy, `IndexFormatTooOldException: created with Lucene 8.x`). Resolve the namespace (`deploy.dev.yml` `namespace:`, or `<project>_dev`), run `docker volume ls`; on **any** `<namespace>_*` hit, **refuse and work down the ranked fix hierarchy below before booting** (the deploy `namespace:` derives from the project name, `<project>` → `<project>_dev`; collisions are the norm on a shared dev machine — ~30 project namespaces are typical). The namespace is chosen in the interview — re-run this check once it is known, and again in the execution pre-flight before boot.
  - *Why a blocker:* `docker/sdk up` drops and recreates the database but **reuses existing named volumes** — a "fresh" first boot silently inherits an earlier project's KV / search / broker read models (foreign store ids, stale indices, reversed store→id maps, an extra RabbitMQ vhost) while the freshly-written DB reads correct. Every signal reads green; the environment is contaminated. This is the one gap `docker ps` doesn't cover.
  - *Fix hierarchy — offer the developer three ranked options, never force a project rename:* (1) **the developer removes their own confirmed-stale volumes** (`docker volume rm <namespace>_*` — theirs to run, per the never-touch-their-docker rule; right when the collision is a leftover experiment); (2) **override only the deploy `namespace:` token** independent of the project name (the name drives branding; the namespace is one YAML key — right when the colliding volumes must survive); (3) a different project name. All three rank above `clean-data`/`reset`, which destroy data without resolving the collision.
- **Docker present:** `docker -v`. **PHP:** `php -v` (else note the docker fallback for lib scripts).
- **Boot-environment probes — the failures at minute 0 and minute 40 that the daemon check doesn't cover.** Each failing probe joins the same developer-must-do-before-boot bucket as "start Docker" (an up-front ask, not a wall-stop mid-boot):
  - **Ports:** the boot binds 80/443 (+ service UIs) — read `docker ps` for OTHER projects' containers publishing `:80->`/`:443->` and ask the developer to stop them before boot (never stop them yourself).
  - **Composer auth/connectivity:** the in-container `composer install` at ~minute 40 dies on a GitHub rate limit or a private-package 401 exactly like a stopped daemon would. Check `~/.composer/auth.json` / `COMPOSER_AUTH` for a `github-oauth` token and `curl -s https://api.github.com/rate_limit` for headroom; missing/exhausted → up-front ask for a token (never handle the token value yourself — the developer adds it).
  - **Disk:** a first boot pulls multi-GB images + volumes; read **`df -h /`** — instant — and flag a nearly-full disk (recommend the developer free space or prune — never prune yourself). `docker system df` is an **optional follow-up, only when `df -h` already shows the disk nearly full**: it walks every image and volume and takes **minutes on a shared dev box**, so if you run it at all, run it with `run_in_background`. Failure signature: pre-flight blocked for minutes on a single disk probe.
- **Platform:** supported hands-off hosts are **macOS (OrbStack/Docker Desktop, mutagen mounts) and Linux (native mounts, no mutagen block)**. On **Windows**, the run must live inside **WSL2** (Linux rules apply; the `/etc/hosts` equivalent is the Windows-side hosts file — say so in the close); native Windows shells are unsupported for the boot — the developer runs `docker/sdk up` themselves.
- **Git remote:** read `git remote -v`. If `origin` still points at the demoshop upstream (`spryker-shop/*`), record it — the close summary must flag "origin still points at the demoshop; point it at the customer's repository before pushing" (never change the remote yourself).
- **Docker SDK present, at the pinned version:** the clone must have a working `docker/sdk`. **Read `.git.docker` FIRST** (the project's SDK pin). It holds **either a tag (`1.76.0`) or a 40-char commit SHA** — and `git clone --branch` accepts a tag but **not** a SHA, so don't assume the tag form. If `docker/sdk` is absent (some clones ship without the submodule), fetch it at the pin with the clone-then-fetch-then-checkout approach the repo's CI uses (works for a tag OR a SHA). **Read `.git.docker` with the Read tool** to get the literal pin `<PIN>`, then run three separate single commands (do NOT chain with `&&` or use `$(cat …)`):
  1. `git clone https://github.com/spryker/docker-sdk.git docker`
  2. `git -C docker fetch --depth 1 origin <PIN>`
  3. `git -C docker checkout <PIN>`
  Never `master` (a master clone has to be removed with `rm -rf docker` and re-cloned at the pin). This is an **accepted exception** to the one-simple-command discipline — `git -C` isn't allowlistable, so these prompt; it's a one-time SDK setup the developer approves once. If `docker/sdk` is present instead, verify its checkout matches `.git.docker`. If `.git.docker` itself is **absent**: derive the pin from an existing `docker/` checkout's tag if present, else ask the developer which SDK version the project targets — never silently take `master` (same reason). Don't defer to the developer and don't boot without it.

## Permission allowlist

- **Permission allowlist — recommend, never install (affects only hands-off-ness):**
  - **You MAY recommend the allowlist, naming the exact commands** — point at the plugin's `hooks/settings.example.json`: `php`, `docker/sdk console|cli|bootstrap|logs`, `curl`, `git status|diff|add|show HEAD:`, `rm`, `python3`/`python` and `magick` under `allow`, and **no `ask` rules at all** (a settings ask outranks a hook allow). `rm` is safe there because `guard-bash.php` denies a deletion git cannot restore (unless it is ignored build output or a file this session created under `data/import`, `config`, `src`, `frontend`, `public` or `tests` (never under `.ai-dev/`)). The **rebuild verbs** (`docker/sdk reset|clean-data|up`, `script`) sit under `allow` because `gate-docker-sdk.php` decides them: trusted rebuilds (a demo clone, first setup, or a recorded `standing_approval: { scope: rebuilds }`) run without a prompt, a project with real data gets one question, and from the third rebuild it denies until the decision log carries `rebuild #N: <why rung 1 cannot show it>` — a permission prompt on top would only double it (`data:import` is never prompted: it is rung 1 of the reset ladder and must stay cheap); `sudo`, `docker volume rm`, `docker system prune`, `git push` under `deny`. **Never recommend a blanket `Bash(docker/sdk:*)`** — that single rule lets an agent spend hours of rebuild time unprompted. The plugin's PreToolUse hook applies the same rebuild rules (and a data-gate `deny`) even when the allowlist is blanket, but a setup install without the plugin has only the settings. What you must **not** do is **create, copy, or modify the developer's `.claude/settings*.json`** yourself: they may already have their own, and their settings are theirs. Without the allowlist the run still works; it just prompts per command.
  - **Never claim the run is unattended if the allowlist isn't in place.** Unattended behaviour depends on the session allowlist granting the project-starter commands (`php`, `docker/sdk`, the `script … docker/sdk up` boot, `git clone` of the SDK, `curl`, read-only helpers) and denying `sudo`, `docker volume rm`, `docker system prune` and `git push`.

## Host names (`/etc/hosts`)

- **Which names:** the `host:` values under the regions and applications of the clone's `deploy.dev.yml`
  (e.g. `yves.eu.spryker.local`, `backoffice.eu.spryker.local`, `glue.eu.spryker.local`, …).
- **Check:** read `/etc/hosts` and look each name up. Reading needs no `sudo`.
- **All present** → nothing to ask; record `hosts: present` in the decision log.
- **Some missing** → show ONE `⚠ ACTION NEEDED` at the top of the interview. A demo keeps the domain
  and region `deploy.dev.yml` already has, so the names checked here are the final ones: one sentence ("lets your browser open the demo shop;
  it asks for your computer password once") and the exact command in its own `bash` block, listing
  only the missing names:

  ```bash
  echo "127.0.0.1 <missing-host-1> <missing-host-2>" | sudo tee -a /etc/hosts
  ```

  Never run `sudo` yourself. `boot-and-verify` §2 re-checks against the line `docker/sdk bootstrap`
  prints — that line is the final word, because a region or domain change alters the names.
